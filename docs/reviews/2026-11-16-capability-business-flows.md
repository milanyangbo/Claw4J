## 两件让它跑不通/跑出假结果的事

### ① A2 不通：单工具 3 次上限与"跨层周报"天生冲突

`ToolCallBudget.MAX_CALLS_PER_TOOL = 3`（**不可配**，注释写明"正常一次查到，留两次给自纠错"）。
而 `examples/subagents/weekly-digest.md` 要求"查本周与上周**同口径**"，再加三区拆分就是 4~6 次
`querySales`——一进门就顶到 3。模型被拦下后的反应是诚实的（"不猜数，要么我自己查要么重派"），
所以用户不会看到假数，但**这条被写进文档的业务流在默认配置下走不完**。

同源的还有整轮上限：`claw4j.agent.tool-call-limit: 6`。实测 Skill 那条流在 6 次下被拦
（"Total tool call limit (6) exceeded"），调到 20 才跑完。也就是说**默认配置与本仓自己的
示范流程不匹配**。

### ② 种子会漂：不重灌就会把"产品 bug"测出来

第一次测 T1 时，模型答"上周华东 99,999.00、其余两区 0"。查库发现问题不在模型：
`V2__business_seed.sql` 的日期是**相对迁移那一刻的本周一**生成的（`date_trunc('week', current_date)`），
而这份库是上周迁移的——于是「上周」窗口里只剩一条本该属于「本周」的订单。
用 SQL 重灌种子之后才有 128400/31500/26000。

含义：`docs/capability-tests.md` 里所有具体数字，**只在一个刚灌过种子的库上成立**。
现在没有任何脚本或文档说明这件事，下次再测的人会重踩（我这次差点把"模型算错"写进报告）。

## 文档自身的三处矛盾（改文档，不改代码）

1. `capability-tests.md` §19 让"摘要一下 sample.md，**三句以内**"，判据却是"**原文句子，不是改写**"。
   这两个要求互斥：我按"三句以内"问，模型把 5 句压成 3 句、第 3 句是合并改写；按"原样贴回来"问，
   逐字对上。判据要改成后者。
2. §4 的"按口径出数"没写前提：**必须先配 `claw4j.agent.directory`**（口径在 persona 的
   `glossary` 里）。没配时模型会正确地"先问口径"——那不是失败，是 Skill 在按正文办事。
3. §1 的三条时间窗数字（128400/99999/77777）依赖 ②，需要一句"先重灌种子"。

## 结论

- **机制层**：五个能力（Tool / MCP / 脚本包 / Skill / RAG）的业务流全部跑通，且数值、口径、出处、
  拒答边界都对得上。
- **编排层**：跨层那条（子 Agent + 多轮查库 + 脚本）**跑不完**，卡在两道预算（单工具 3 次、
  整轮 6 次）与本仓示范流程的规模不匹配。
- **环境层**：种子会随迁移日期漂移，判据数字因此不稳定。
