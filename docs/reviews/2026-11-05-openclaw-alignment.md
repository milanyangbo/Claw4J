# 与 OpenClaw 的对齐评审（2026-11-05）

**这是一份"对齐轴"的报告**，不是 `docs/agents/review.md` 里那两条轴（规范 / 规格）。它回答的问题只有一个：

> 这个功能，行业里已经有实现（主要是 OpenClaw）；我们做的是同一件事，还是做成了另一件事？

之所以单独成轴，是因为前两次出错的姿势都不是"代码写错了"，而是**把一件已经有人做对过的事，按自己的理解重新发明了一遍**：run 被当成"一句话"（ADR-0024）、会话被当成"一个人"（ADR-0025）。两次都不是语法错误、不是测试没写，而是**语义与既有实现分叉**，且分叉当时看不出来——测试全绿，文档还写着"跨轮生效"。

所以这篇的判据是：

1. **有对应物的，比行为**，不比名字。名字一样、行为不同，算不对齐。
2. **没有对应物的，比内部自洽**——挂在它上面的东西是否都按同一个"单位"成立。
3. 每条给文件:行 + 原文。**引不出原句的，标成判断题**，不混进硬结论。

---

## 一、结论

十一条发现，两条 P0。P0 的共同点与前面那两次一模一样：**一把键被用来回答两个不同的问题**。

| # | 发现 | 级 | 证据等级 |

## 二、逐模块总表

"对应"一栏写 OpenClaw 的做法；"我们"一栏只写行为，不写设计意图。

| 模块 | OpenClaw 的做法 | 我们现在的做法 | 判定 |
| --- | --- | --- | --- |
| 会话键 | `agent:<id>:<channel>:dm:<peer>`，群聊 `...:group:<id>`；`dmScope` 默认 `main`，多用户推荐 `per-channel-peer` | `claw4j:user:<owner>:<通道>:<chatId>` | **对齐**（选了推荐档 `per-channel-peer`，且更严：掺了权限指纹） |

## 三、两条 P0

### 3.1 定时任务跑在"创建者的那段对话"里

**四行代码就闭环了，谁都能在 30 秒内复核：**

```text
ChatClientAgentPort:451   delivery.register(run.id(), message.channel(), message.chatId())
ChatClientAgentPort:603   return new DeliveryTarget(channel, message.chatId())
ScheduleTools:181         address.map(DeliveryTarget::channelRef).orElse(null)
ScheduleScanner:176       new InboundMessage(owner, task.channelRef() == null ? task.id() : task.channelRef(), …)
ChatClientAgentPort:240   String sessionId = SessionKeys.sessionIdOf(owner, message.channel(), message.chatId())
```

第一行把"这一轮从哪个会话来"登记成投递地址；第四行把它原样当成定时任务的 `chatId` 交回去；第五行再把它算成会话 id。**于是 `sessionId(cron) ≡ sessionId(创建它的那段对话)`**——不是"看起来像"，是同一个字符串。

`ScheduleFlowTest:392` 那条注释（"定时任务的 chatId 固定，两次运行落在同一段会话里，预算是合成 2"）说明作者知道"两次运行共用一段"，但**没意识到那一段就是用户的对话**。测试里 `createTask` 传的是 `"oc_sched"`（第 419 行），一个谁都不用的 id，所以这个等号在测试里永远看不出来。

后果四条，前两条用户当天就能看见：

1. 早上九点那次任务的问题与回答，**出现在用户自己的聊天记录里**，并且进入之后每一轮提示词。用户没问过那句话。
2. 反过来也成立：定时任务继承用户私聊的上下文作答。"总结今天订单"这句话的提示词里，可能有十分钟前聊的合同条款。
3. **预算互吃。** 预算按会话累计（ADR-0025），所以定时任务烧掉的工具调用计入用户那份 6 次。用户自己一次工具都没调，下一句就被回一句"预算用尽"。
4. 压缩把用户对话挤进摘要：保留窗口是"最近 20 条"，定时任务每天塞两条进去。

OpenClaw 的做法是两种，且都是显式的：

- `sessionTarget: "isolated"` → 会话键 `cron:<jobId>`，**"Each run starts a fresh session id (no prior conversation carry-over)"**；
- `sessionTarget: "main"` → 往主会话塞一条 **system event**，不是伪装成用户提问。

我们现在是第三种：**用主会话的键，塞一条像用户提问的记录，还跨运行累积**。三种里最差的一种。

**改法（最小）**：给定时任务的 `InboundMessage` 一个自己的 `chatId`，形如 `cron:<taskId>`，`channelRef` 只当投递地址用。这不需要动表、不需要动 `SessionKeys`，只需要在 `ScheduleScanner.message(...)` 里把两个用途拆开——它现在用同一个字段回答"送到哪儿"和"这是哪段话"。

**反例**：同一 `chatId` 先问一句，再用 `schedule_task` 建任务并触发，断言 `select count(distinct session_id) from claw4j_run.agent_run` = 2，且定时那条的 `session_id` 不含用户 `chatId`。改回现在的写法，这条必红。

> 这与 A08 是同一个错误家族：**"这把键顺手能拿到"被当成了"这把键语义正确"**。A08 拿 runId 当"往哪写"的坐标；这里拿 chatId 当"这是哪件事"的坐标。

### 3.2 一段会话可以同时跑两个 run

OpenClaw 的原文（`/concepts/queue`）：

> `runEmbeddedPiAgent` enqueues by **session key** (lane `session:<key>`) to guarantee **only one active run per session**.
>
> Each session is still serialized (one run per session key at a time). Default: 1.

我们这边：全仓没有一把按会话的锁（`Grep synchronized|ReentrantLock|Semaphore` 命中的全是 token 刷新、脚本登记这类局部状态），也没有 lane。HTTP 流式池 4~32（`HttpChannelAutoConfiguration:67`），飞书/钉钉/Slack/企微各一个有界池，`InboundDispatcher` 提交即执行。**两条消息 → 两个 run → 同一个 sessionId。**

四个后果，按可见度排：

1. **第二条消息读不到第一条的答案。** 提示词在 `SessionMemoryAdvisor.before` 里就拼好了，而第一条的答案在 `after` 里才落库。用户问"华东多少"、紧接着问"那华南呢"，第二句的上下文里没有华东那个数——模型要么反问，要么编。
2. **写回顺序可能倒置。** 两条 `after` 谁先落库看谁跑得快，聊天记录里可能是"答 B、答 A"。
3. **预算可超发。** `RunBudget:90-100` 是"读 → 判 → 扣"，javadoc 自己写着"**两次读之间也没有原子性**"。单 run 时这只是窄窗口；按会话累计之后，两条并发消息**同时看到 5/6，各自扣一笔，结果是 7/6**。
4. 审计里"这一轮"变成两条并行的 step，`seq` 唯一约束能挡住同号，但读者看不出它们属于同一次用户操作。

**改法**：按 `sessionId` 分 lane 的串行队列，默认并发 1，全局 `maxConcurrent` 可配（对齐 OpenClaw 的形状）。最小可用版是 `ConcurrentHashMap<String, ReentrantLock>` + `lockInterruptibly()`，先解决正确性；`collect` 那套合并语义可以晚一步。

**反例**：同一 `chatId` 并发两条消息，断言第二条的提示词里含第一条的回答。现在就红。

> 这一条也是"run 的寿命"那次留下的债：既然每轮一个 run，就没有任何东西在"同一段会话"这一层排队。

## 四、会话寿命：三个"结束"，只实现了一个

### 4.1 预算的 idle 重置 ≠ 会话结束

`claw4j.run.budget.idle-minutes: 120`（`application.yml:253`）落地的是"两小时没动静，三个数从 0 开始"。这句话本身是对的，也对齐了 OpenClaw 的 `idleMinutes`。

但 OpenClaw 的 idle 是**会话级**事件：它换一个新 sessionId，上下文与用量一起归零。我们的 idle 只清了预算表，**会话历史一行没动**。所以两小时后回来：

- 预算说"这是新的一段对话"（0/6）；
- 记忆说"这还是同一段"（昨天、上周的话都在提示词里）。

两个都叫"会话"，但算的不是同一件事。这不是漏洞，是**同一名词两个寿命**——正是上一轮 `memory-no-leak` 那种"看起来记得住，其实是另一回事"的形状。

要么把 idle 也用在历史上（换新 sessionId，与 OpenClaw 一致），要么在配置注释里明确写"这里的 idle 只作用于额度，不作用于记忆"。现在是后者没写、前者没做。

### 4.2 只有"到期删除"，没有"到期换新"

`spring.ai.session.time-to-live: 30d`（`application.yml:43`）加 `SessionCleanup` 每小时删过期行。OpenClaw 是"每日 4 点重置 + 可选 idle，旧 transcript 留盘"。

两者的差别不在参数，在**语义**：它是"有新对话"，我们是"旧对话被删了"。表现上：

- 每天用的人，第 30 天打开聊天，记忆突然清空——不是"昨天那段结束了"，是"什么都没有了"；
- 清理是后台任务，不挑时机，可能正好在两人对话中间把行删掉。

**未验证项（写在这里免得被当成结论）**：`expires_at` 是否随每次写入刷新，我没能从字节码确认。已经确认的是：`JdbcSessionRepository` 的全部 SQL 常量里，**没有任何一条 UPDATE 触及 `expires_at`**（只有 `event_version` 的乐观锁与 archived 标记），所以"活跃了 29 天就把到期时间往后推"这件事在仓储层没有发生。建行在服务层（仓储没有 INSERT 常量），那一句要单独看一眼才能把这条钉死。

### 4.3 文档仍在说旧的预算口径

`docs/adr/0019-agent-core-run-driven.md:97-98`：

> 裁决：预算按 run 累计……判据：一次 run 跨 3 轮共调 7 次工具 → 第 7 次被拒

`ADR-0025` 已经把这件事整个推翻了（预算挂会话），A04 票也补了说明，**ADR-0019 没改**。`docs/agents/review.md` 把这个仓库的第一大类缺陷定成"文档承诺与代码一致"；这是它的第 N 次复发，而且是 ADR 级的冲突——两份 ADR 对同一个数给出两种说法，后来的人只会信自己先读到的那一份。

## 五、次级偏差

### 5.1 语义缓存的键不含人（判断）

`CacheAdvisor:225-227`：`cache.nearest(fingerprintOf(who), entitySignature(question), embedding)`。`fingerprintOf` 是 `tables + actions` 的哈希——**不含 userId、不含 sessionId**。

按今天的权限模型（表级 + 动作级），两个同角色的人看到的行是同一批，所以**不构成越权**。但这是一个"今天成立、明天不一定"的不变式：一旦出现行级权限（按区域、按负责人）、或者回答里带了"你上次问的那个"这类与个人绑定的话术，缓存就会把 A 的答案发给 B。

判据不是"要不要共享"，而是"**键是否覆盖了所有会改变答案的维度**"。目前覆盖：权限、时间词、数字。没覆盖：人、会话、行级范围。前两个今天不影响答案，第三个今天不存在——**三个都是"还没有"，不是"不需要"**。这一条建议写进 `docs/design/semantic-cache.md` 的"键变了就要改这里"，而不是等它变成缺陷。

### 5.2 群聊会话按"人"分，OpenClaw 按"房间"分（判断）

我们的键是 `owner(userId@权限):通道:chatId`，`owner` 在最前面。所以在同一个项目群里，张三问一句、李四问一句，是**两段会话**——机器人对张三说的"刚才那个数"，李四问的时候它不记得。

OpenClaw 的群聊键是 `agent:<id>:<channel>:group:<id>`，**一个房间一段会话**，因为机器人是房间的参与者。

我们这样做的收益是明确的：李四永远读不到张三的上下文（哪怕同角色）。代价是"群里接着刚才的话说"这件事不成立，用户会觉得机器人"在群里失忆"。这是取舍不是错误，但**要写进文档**——`docs/design/session-memory.md` 现在只写了"私聊与群聊是两段"，没写"群里的两个人也是两段"。

### 5.3 工具档位是"梯子"，OpenClaw 是"抽屉"（判断）

OpenClaw 的 `tools.profile` 四档是四组**互不包含**的集合：`coding` 给 fs/runtime/sessions/memory，**不给** `group:messaging`；`messaging` 给消息类，不给 fs。

我们的 `ToolTier` 是累进的：`CODING` 必然包含 `MESSAGING`。`ToolTier` 的 javadoc 自己承认了——"做不出'只跑脚本、不许读消息'的部署"。

具体后果：一个"能跑脚本但绝对不能发消息"的部署，在我们这里只能先选 `CODING`，再用 `deny` 把消息工具一个个点名排除。能做，但**默认值是错的**：档位的用途就是"选一个安全的默认"，而选 `CODING` 的人多半不想要消息能力。

### 5.4 压缩窗口写死（判断）

`SessionMemoryProperties.DEFAULT_CONTEXT_WINDOW = 65536`，`yml` 里只配了 `cleanup-interval`，所以跑的是一半窗口 = 32768 token 触发。注释写着"deepseek-chat 的上下文窗口是 64k"。

问题不在数字，在**它不跟着模型走**：换到 qwen（128k）会压得太早（丢细节、多花一次摘要调用），换到 32k 的模型会压得太晚（撞窗口）。OpenClaw 从模型目录读 `contextWindow`。我们至少应该在换主模型时让启动日志把"当前窗口 / 触发阈值"打出来——现在这个数只活在代码里。

### 5.5 没有会话级命令（判断）

OpenClaw 有 `/new`、`/reset`、`/stop`、`/compact`、`/status`。我们一个都没有：要清空历史只能等 30 天，要中止只能断 SSE，要看上下文用量没有入口。

这不是"对齐缺陷"，是**产品缺项**：`/new` 是"我现在要换一件事说"的唯一表达方式，没有它，用户只能靠"等两小时"或"开新群"。而我们的会话键里 `chatId` 已经能表达这件事了——差的是一个入口。

## 六、不该照抄的三样

对齐不是"凡它有的我们都要有"。这三样明确不抄，理由写在这里，免得下次评审又提一遍：

1. **session pruning。** OpenClaw 自己默认就是 `mode: "off"`，开起来也只对 Anthropic 的 prompt cache 有意义（"Only active for Anthropic API calls"）。我们用 DeepSeek/千问，没有可省的 cacheWrite。抄过来是一段永远不生效的代码——和 A08 同一个形状。
2. **heartbeat。** `ADR-0021` 已经明确"不做"，理由是这条产品线没有"主动找我"的场景。定时任务覆盖了它的实际用途。
3. **JSONL + 文件存储。** 它是单机个人助手的形态（`~/.openclaw/agents/<id>/sessions/*.jsonl`）。我们是多租户 + Postgres（ADR-0005），会话表已经是共享存储。形状不同，比"存哪儿"没有意义。

## 九、按"是不是同一类"重新分级

前面那两次错误共享四条特征。**命中三条以上的才是同一类**，其余只是偏差：

1. **名字承诺的粒度 ≠ 实现的粒度**（"一件事的预算"实际是"一句话的"、"一个人的会话"实际是"所有对话的"）。
2. **一个键／单位被两个用途共用**（runId 同时是"数据归属"与"往哪写"；userId 同时是"归属"与"对话边界"）。
3. **失效是静默的**——测试全绿、没有报错、只在真实使用里表现为"怎么又忘了"。
4. **别的东西挂在它上面**（预算、审批、审计挂在 run 上；预算、召回、压缩挂在会话上），所以越晚改越贵。

| 发现 | 命中 | 结论 |
| --- | --- | --- |
| 1 定时任务的会话键 | 1、2、3、4 | **必修**：一行改动 + 一条反例 |
| 2 会话无串行化 | 3、4（且是"预算按会话"成立的前提） | **必修**：先有串行化，会话预算才是真的 |
| 6 子代理不并入会话预算 | 1、3、4 | **必修**：与"额度能被多问一句绕过"完全同型，只是换成了"多派一个子代理" |
| 3 + 4 + 11 会话边界 | 1、2、4 | **同一个根**，先定语义再改代码（见下） |
| 5 `ADR-0019` 冲突 | — | 不是同类，但一分钟就能改，留着会误导下一个人 |
| 7 缓存键不含人 | 2（维度今天不存在） | **不改**，立一条不变式：会改变答案的维度变了，键就要加维度 |
| 8 群聊按人分 | 1（"会话"被两个粒度用） | **记账**，不是缺陷：安全取舍已经写清 |
| 9 档位累进 | — | 能力模型取舍，等真实部署需要"只跑脚本"再动 |
| 10 压缩窗口写死 | — | 参数问题，顺手改成读配置即可 |

### 那个根：`会话边界` 没有唯一的主人

它现在有**四个定义，四个使用者**：

```text
SessionKeys / chatId    路由：一段对话的地址，永不过期
claw4j.run.budget.idle  用量：120 分钟没动静就归零
spring.ai.session.ttl   存储：30 天后删行
ScheduleScanner         借用：直接拿创建者的那一份
```

没有一个地方回答"**这段对话到哪儿算完**"。这与 run 那次一模一样——run 也有过四个说法（一句、一轮、一件事、一个任务），最后靠 ADR-0024 钉成"一轮"才收敛。会话现在还没有这一钉。

三个后果连在一起：预算每 2 小时当它是新的、历史永远当它是旧的、web 端 `chatId` 缺省等于 userId（`HttpPrincipalResolver`）所以**用户根本没有"开一段新对话"的手段**。`/new` 因此不是锦上添花，它和"每日重置"是同一个缺失的另一半：**没有结束，就没有真正的开始**。

所以这一组不该拆成三张票修，先写一条决定：会话是"空闲即结束"、"每日 4 点结束"、还是"只有用户说结束"——选一个，然后预算、TTL、`/new`、cron 的会话键四处跟着对齐。选哪个都能自洽，唯独"四处各选一个"不行。

这条决定已经写进 [`docs/adr/0026-session-boundary-lane-and-naming.md`](../adr/0026-session-boundary-lane-and-naming.md)：每日 + 空闲、谁先到算谁；结束 = 换新段，不删行；lane 按"对话地址"加锁；cron 用 `cron:<taskId>` 且每次运行新段。
