# 踩过的坑

> 这一份是给后面接手的人（人和 AI 都算）看的：**这些坑在代码里看不出来，只会再犯一次。**
> 每条都写成"现象 → 根因 → 现在的做法"三段，因为只写现象的话，下次还是会往同一个地方掉。

## 一、主备降级：换供应商时工具会丢

**现象**：主模型失败、备模型接住了，`querySales` 却不见了。真实链路上的回答变成
"我无法直接访问数据库，请确认口径"——没崩、没超时，只是再也查不到数。降级于是只剩
"还能说话"，不再是"还能干活"。

**根因**：各家 `ChatOptions` 互不兼容，降级时必须把参数翻译成备模型那一型（否则强转当场
`ClassCastException`）。而翻译时只搬温度、topP 这类**标量**是不够的——工具回调与工具上下文
不在标量里。

**现在**：主备切换时工具回调与工具上下文跟着一起搬，由模型路由那份测试钉住。
**判据是"备模型看得到工具"，不是"降级没抛异常"**——后者假模型也能给你绿。

## 二、主备降级：模型内部的重试会把降级拖成分钟级

**现象**：真实联调时等了 **4 分 40 秒**还没轮到备模型，用户看到的是一直转圈。

**根因**：两层重试相乘。Spring AI 默认给 `DeepSeekChatModel` 套的重试模板是 10 次、2 秒起、
×5 递增、上限 180 秒；上层还有路由在"换一家"。

**现在**：模型内部只留短重试（`RetryUtils.SHORT_RETRY_TEMPLATE`：10 次 × 100ms，合计约 1 秒），
超时预算花在**换供应商**上，而不是在同一家身上等。通义那侧的 SDK 重试同样关掉（`maxRetries(0)`）。

这两个坑的共同点：**在任何一张假模型测试里都不会红**——假模型既不会真的失败，也不需要真的工具。

## 三、Boot 4 的 Flyway 自动配置搬了家

**现象**：应用起来了、日志干净，但表一直不建。业务侧报"连不上库"，看的人去查网络。

**根因**：Boot 4 把 Flyway 的自动配置拆成了独立 artifact。只有 `flyway-core` 在 classpath 上时，
`spring.flyway.enabled=true` 是一句**没有任何东西在执行**的配置——不报错、不警告，
日志里不出现 Flyway 三个字。

**现在**：显式引 `spring-boot-flyway`，它跟着迁移脚本一起放在能力模块；
"应用起来就迁到最新版"这件事由一条测试盯着。
**教训**：配置了但没生效，比不配置更难查。

## 四、SQL 守卫：两种写法的取舍

**现象**：守卫不是"正则能不能匹配"的问题，是两个具体的坑。

- **注释里夹分号**（`select 1 -- ; drop table t`）：字符串层面看是多语句，数据库层面是一条。
  所以校验前必须先去掉注释与字符串字面量。
- **行上限不能用 `limit` 拼**：模型自带的 `order by ... limit 10` 后面再拼一个 limit 就是语法错误。
- **包装之前要补一个换行**：模型很常写以行注释结尾的语句（`-- 只看华东`），
  紧跟着拼 `)` 会把 `) as claw4j_limited limit N` 整段吞进注释里——合法查询变成语法错误，
  而模型拿到的是一条**与被问的问题无关**的报错，自纠错于是朝错误方向猜。
  补换行不改语义、不需要认识方言；剥注释会改掉模型写的文本条件，所以不剥。

**现在**：行上限**包一层子查询**，包之前保证原句末尾有换行。顺手的好处是把 DML 挡在解析阶段——
PG 的子查询里不能是 `insert` / `update` / `delete`。

## 五、`spring.ai.tools.limits.*` 到不了我们这条链

**现象**：配了预算上限，却回到了默认的 40 / 150（那是给分页取数设计的值），一次提问烧几百次往返。

**根因**：`ChatClient` 是我们自己 `new` 的，五参重载里传进去的 `ToolCallingManager` 才是生效的那个；
自动配置那个只有在使用 Boot 注入的 `ChatClient.Builder` bean 时才用得上。

**现在**：预算由 `ToolCallBudget` 显式收紧，两个数字**各有独立的一条测试钉着**。
哪天改成注入 bean，这两个数字会静默退回默认值——**这条修改本身没有失败信号，只能靠测试。**

## 六、造不出来的场景要用假工具逼出来

上面那条的总数上限（6）比单工具上限（3）大，而当时只注册了一个工具——
"整轮 6 次"在单工具场景下**永远撞不到**。与其留一个没人能证明它在生效的数字，
测试里干脆造了三个假工具把它逼出来（三个各调 2 次，第 7 次落在还没调满的那个上）。

**一条通用做法：红线守的是"还没发生的风险"，就不是靠"跑一遍没红"证明它在生效的，
必须造出它会红的那一刻。**

## 七、Subagent 白名单：一个空名单被当成了"全部权限"

**现象**：示例里那个只该看一条 SQL 的复核员，实际拿到了 `mail_send` 与 `run_script`。
不报错、不告警，没有任何日志比平时多一行。

**根因**：解析借用了社区包的 `MarkdownParser`，它是逐行找 `key: value`，
`- querySales` 这种没有冒号的行**整行丢掉**。于是 `tools:` 解析成空串、`names()` 返回空名单，
而 `selectTools()` 第一行就是"空名单 = 继承全部可用工具"。
两处各自都"合理"，合起来就把一个写坏的配置变成了权限放大。

**现在**：front matter 由本项目自己解析（`FrontMatter`），`- a` 与 `a, b` 都收；
**"没写这一节"与"写了但解析不出名字"严格分开**——前者才是继承全部，后者按定义错误失败。
**教训：任何"空 => 全部"的默认值，都要配一条"空从哪来"的检查**。
默认值本身没错，错在没区分"没写"与"写了但没读懂"。

## 八、主备降级："任何异常都换一家"会把确定的错误拖成两次往返

**现象**：key 失效（401）时，用户等了两轮网络往返，最后拿到几条异常捆在一起的消息，
认不出是哪一家、什么错。

**根因**：`RoutingChatModel` 用 `catch (RuntimeException)` 一刀切，一条确定的错误
被当成"也许下一家行"。省下的解析工作，换成了排查时的一段空白。

**现在**：`ModelFailures` 一处判断（沿 `getCause()` 走完整条链）：429 / 5xx / 连接失败 / 超时降级；
401 / 403 / 400 / 422 / 响应解析不了 / 本地构造错误直接抛并点名哪一家。
**认不出的失败按不降级处理**——降级要保住"只有明确知道换一家可能好时才换"这个能被讲清的含义。

## 九、"通道连上了"不等于"配置读全了"

**现象**：日志一切正常（`飞书通道就绪：长连接已建立`、`Started Claw4jApplication`），
群里 @ 机器人却永远回"没有权限：你的飞书账号还没有在 Claw4J 里登记"——
而那个 `ou_...` 明明已经写进 `application-local.yml` 的 `roles.read-only.users`。

**根因**：启动命令漏了 `-Dspring-boot.run.profiles=local`，`application-local.yml` **整份没被加载**，
`claw4j.channel.feishu.roles.*.users` 于是根本不存在。它照样能连，是因为凭据来自
`set -a && . ./.env` 导出的环境变量，`application.yml` 里 `${FEISHU_APP_ID:}` 直接取到了。
**两条配置来源，一条在、一条不在，而"通道就绪"这个信号对两处都成立**——
凭据对不代表角色表读到了。

**现在**：
- 启动必须带 `-Dspring-boot.run.profiles=local`（否则 local 那份整份不加载）；
  凭据则随模块传递，构建不需要任何额外开关。**"必须记得带个参数才能读到自己写的配置"
  这种前提越少越好**——它只在 `mvn` 那一层存在，换个入口（`java -jar`、IDEA）就没了。
- `spring-boot:run` 的工作目录是**模块目录** `claw4j-app`，而 `compose.yaml` 在仓库根；
  local 又会打开 `spring.docker.compose`，于是启动直接失败
  `IllegalArgumentException: 'files' content [compose.yaml] must exist`。
  库已经在跑时加 `SPRING_DOCKER_COMPOSE_ENABLED=false`——compose 的职责是"帮忙拉起"，
  不是"没有它就不能跑"。同一个工作目录差异也解释了 `.env` 为什么必须有 `./` 与 `../` 两条 import 路径。
- **判据是日志里那行 `The following 1 profile is active: "local"`**。没有它，
  "通道就绪"只能证明凭据对，不能证明角色表读到了；而这两种情况在群里长得完全一样。

## 十、"参数配上了"不等于"有人会调它"

**现象**：`SessionMemoryAdvisor.Builder` 上明明有 `compactionTrigger` 与 `compactionStrategy`
两个参数，配上去、启动不报错、日志也没有异常——长对话却照样把整段历史拼进提示词，
提示词一路涨到上下文上限。

**根因**：`spring-ai-session` 0.10.0 的 `SessionMemoryAdvisor` **从不调用
`SessionService.compact`**（`javap -c` 里一次都没有）。那两个字段只是被存进对象，
没有任何一段代码读它们。`FaultTolerantSessionService.compact` 那条"压缩失败返回 null"
的分支注释里其实已经写了"这条路径不会被走到"——当时把原因归给了 M1 没配 Trigger，
真正的原因是这个 Advisor 根本不压。

**判据**：判断一个框架参数有没有用，不能看 Builder 上有没有那个方法，
要看**谁读它**。`javap -c` 搜一遍方法调用是最快的办法；其次看它文档写的触发时机
与现有代码里有没有对应的调用点。这个仓库已经因为"看着像"踩过一次
（`com.larksuite` 那条永不命中的 ArchUnit 规则）。

**现在**：压缩走自己的 `SessionCompactor`，在 `ChatClientAgentPort` 进模型之前调一次。
`SessionMemoryAdvisor` 上刻意**不配**那两个参数——配了只会让读代码的人以为压缩已经生效。
顺手把 `RecursiveSummarizationCompactionStrategy` 的一个约束记下来：
`overlapSize`（默认 2）必须小于 `maxEventsToKeep`，配成 1 或 2 会在 `build()` 抛异常，
所以 `events-to-keep` 的下限是 3。
