# 语义缓存：同一个问题第二遍不该再算一次

> 设计说明：哪些是框架给的、哪些是我们刻意不做的。决策去 [ADR](../adr/)，判据去
> [alignment](../agents/alignment.md)。

"上周华东成交额多少"这类问题每天被同一个人问好几遍，每次都要打模型、查库、再算一遍。
缓存一层做在 Advisor 链上，命中时**一次模型都不调**。

**整套用框架的**（2026-11-09）：Advisor 是 `SemanticCacheAdvisor`，存储是
`DefaultSemanticCache`（Redis Stack）。我们只负责装配、一个 order、一个阈值。

```
请求 ──► 记忆(写这条消息) ──► 脱敏 ──► 缓存(查/存) ──► 工具循环 ──► 模型
                                          │
                                          └─ 命中：直接返回缓存里的回答，工具与模型都不动
```

## 命中只有两条判据

1. **同一个上下文**。键是 `SHA-256(整份系统提示词)`，由框架的
   `extractContextHash`（private）算出来。权限不进提示词，同一个人设下所有人就共用一个键——
   所以 `PromptComposition` 里加了一段「数据范围」，内容是权限指纹
   （`tables + actions` 排序后的哈希）。
2. **相似度过阈值**。默认 0.93，见下一节。

没有第三条。时间窗、命中标记、命中率指标、副作用判定——官方实现都没有，**我们也不补**
（理由见「刻意不做的东西」）。

## 阈值不是拍的：一张实测表

用 `text-embedding-v3`（dimensions=1024）算余弦。两组基准分别是
「上周华东成交额多少」与「上周华东区成交额多少」（后者多一个"区"字，就是真链路里用的那句）：

| 余弦（两组） | 问句 | 意思 |
| --- | --- | --- |
| 1.0000 | 同一句话 | — |
| 0.9987 | 上周华东成交额是多少 | 只多了个"是" |
| 0.9967 | 华东上周成交额多少 | 词序颠倒 |
| **0.9950 / 0.9956** | **上上周华东成交额多少** | **换时间，意思完全不同** |
| 0.9470 / 0.9501 | 上周华东销售额多少 | 同义（额 → 销售额） |
| **0.9372 / 0.9117** | **华东上周卖了多少** | **同义改写** |
| **0.9187 / 0.9154** | **上周华东订单量多少** | **换指标** |
| 0.8968 / 0.9057 | 上周华南成交额多少 | 换区域 |

只有一个数的前三行是当时只量了一组，不影响结论——结论只用带两个数的那五行。

这张表否掉两个直觉：

- **票面原定的 0.95 太高**：连 0.9470 的同义说法都会落空。
- **"同义改写"与"换指标"的分数在第二组里是反序的**（0.9117 < 0.9154）。也就是说在两组数据上，
  没有任何一个阈值能同时做到"命中所有同义改写、挡住所有换指标"。这不是调参没调到。
  于是问题变成：往哪一边错？

**答案是往"漏"的那一边错。** 0.93 挡得住换区域（0.8968~0.9057）与换指标（0.9154~0.9187），
代价是漏掉措辞差得多的同义改写（0.9117）。漏只是没省到钱，误是给出另一个问题的答案。

**这个结论要诚实地接受**：语义缓存对"数值/时间/指标实体只差一点"的问答本质上不可靠。
它真实的收益场景是"同一个人几分钟内几乎原样再问一遍"（1.0 与 0.99 那一档可靠），
不是"随便换个说法都能命中"。真出问题时的第一反应应该是调高阈值或关掉它。

## 刻意不做的东西

这一节是**防止下一个人重新加一遍**。每一条都曾经做过，2026-11-09 全部删掉，
判据是 `docs/agents/alignment.md`：官方没有的能力，我们不补。

| 不做 | 曾经的理由 | 现在为什么不做 |
| --- | --- | --- |
| 把问题里的时间词与数字编进键（`entities` 列） | 「上周」与「上上周」余弦 0.9950，阈值分不开 | 框架的键只有"系统提示词哈希"一个来源。要这一维就得自己写存储实现 |
| 命中标记「（同上次）」 | 用户分不清答得快是缓存还是模型 | 官方 advisor 命中时原样返回，不加标记 |
| `claw4j.cache.hits` / `misses` 指标 | 要知道命中率 | 同上，官方不报这两个数 |
| 有副作用的一轮不缓存（`sideEffectFree`） | `run_script` 那一轮的答案被复用等于复用执行结果 | 官方 `set` 只判响应非空，没有"这轮调没调工具"的概念 |
| TTL（`expires_at`）与清理任务 | 不删表会一直长 | 官方的 `ttl` 元数据字段是死代码（`set` 从不写、查询也不按它过滤） |
| 唯一键 + upsert | 同一问题问一百遍会躺一百行 | 官方在写入前会先 `findSimilarDocuments` 查重，重复问题不会堆 |
| 两条诊断查询（同权限/全库） | 分清 miss 是换权限还是换时间窗 | 官方接口只给 `(query, ctx)` 两个入参，拿不到分区信息 |

**代价写在明处**：现在「上周」与「上上周」落进同一个上下文（只差 0.005，阈值挡不住），
所以这两句之间会互相命中。这是照官方实现走的既定结果，不是待修的缺陷。
要修就是自研存储，得走 `alignment.md` 里那条三段式，等人判断。

## 过期与容量：靠上下文自己失效

官方实现不过期。但键里带着**日期**（`PromptComposition` 的时间精度是"到天"），
所以跨天之后 `contextHash` 变了，旧行查不到——逻辑上每天自动失效一次。

物理行不会删，Redis 里会一直留着。处理方式：

- 不给这个实例配持久化（重启即空，缓存本来就是可丢数据）。
- `maxmemory` + `maxmemory-policy allkeys-lru`（compose 里是 256MB）：满了按最近最少使用淘汰。

**为什么时间精度必须是"到天"**：带 `HH:mm` 的话 `contextHash` 每分钟变一次，
缓存活不过 60 秒。这是提示词与缓存键之间唯一的耦合，改 `PromptComposition` 的格式前先看这一条。

## 失败姿势：缓存现在是强依赖

这条变了，必须说清楚。原来（自己写存储时）缓存挂了不影响对话；现在是官方实现的行为：

| 出问题的环节 | 结果 |
| --- | --- |
| 启动时连不上 Redis | **启动失败**（索引在 `afterPropertiesSet` 里建，那一步就连接） |
| 运行中 Redis 挂掉 | **这一轮报错**（`adviseCall` 调 `get`/`set` 时没有 try/catch） |
| 缓存里没有候选 | 正常打模型 |

这两条不由我们再包一层去抹平——抹平就是自研，而"缓存不参与可用性"这条承诺本身
是跟着旧实现长出来的，现在改成"缓存与数据库同级"。要保住可用性只有一个办法：
`claw4j.cache.enabled=false`，整套不装。

## 装配与配置

- `claw4j.cache.enabled`（默认 true）+ `QwenModelCondition`：没有向量能力就不装。
- `claw4j.cache.similarity-threshold`：默认 0.93。
- `claw4j.cache.redis-uri`：默认 `redis://127.0.0.1:6379`。
- 镜像必须是 **Redis Stack**（`redis/redis-stack-server`）：普通 Redis 没有 RediSearch，
  向量索引建不出来。compose 里已经加好。

order 是显式传的：`DEFAULT_CHAT_MEMORY_PRECEDENCE_ORDER + 50`（记忆之后、工具循环与脱敏之前）。
官方默认值是 `-2147483448`，排在记忆之前——命中时那条用户消息还没进会话，聊天记录会少一轮。
