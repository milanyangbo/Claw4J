# 语义缓存：同一个问题第二遍不该再算一次

> 设计说明：为什么这么做、否决了什么。要看结论去 [README](../../README.md)，要看决策去 [ADR](../adr/)。

"上周华东成交额多少"这类问题每天被同一个人问好几遍，每次都要打模型、查库、再算一遍。
缓存一层做在 Advisor 链上，命中时**一次模型都不调**：

```
请求 ──► 记忆(写这条消息) ──► 脱敏 ──► 缓存(查/存) ──► 工具循环 ──► 模型
                                          │
                                          └─ 命中：直接返回"（同上次）"，工具与模型都不动
```

**命中要同时满足三条，少一条都可能把别人的答案或另一个问题的答案发出去：**

1. **同一个上下文**。上下文是两段拼的：
   - **权限范围**。这是安全边界不是优化：`guest` 读不到 `sales_order`、`admin` 读得到，
     同一个问题在两个角色下答案本来就不同。指纹取 `tables + actions` 排序后的哈希——
     **不取 `userId`**（按人分等于同角色的人互相命中不了，缓存白做），
     **也不取角色名**（角色改一次配置，缓存全失效，而改配置看起来跟缓存无关）。
   - **问题里的实体**（时间词与数字）。"上周"与"上上周"余弦 0.9950，比同义改写还高，
     阈值分不开它们，只能靠"这不是同一段时间"来分。理由见下一节。

     **"上"用 `上{2,}` 而不是把 `上上周`、`上上上周` 一个个列出来**：列 `上上周` 会让
     `上上上周` 从第 2 个字开始匹配成"上上周"，于是三周前与两周前落进同一个上下文——
     这一档的余弦比 0.9950 还高，直接给出另一个时间窗的答案。量词把这一类一次挡住，
     枚举只能挡住想得到的那几档。同理，token 内部的空白会被去掉：`近 7 天` 与 `近7天`
     是同一个时间窗，不去掉就是两个签名、永远命不中。

   **区域故意不进实体。**"上周华东"与"上周华南"当然也不是同一个问题，但区域名是一张
   越列越长的枚举（省、市、大区、门店）：今天加"华东华南"，明天就要加"东区""北区"——
   那正是这套上下文键要避免的形态。区域这一档靠阈值挡（0.8968 / 0.9057）。真要做到按区域分，
   正确做法是让工具返回里带上"这次查了哪个区域"，而不是继续在问题文本里猜。

   两段合起来就是框架 `SemanticCache` 接口里那个 `contextHash` 的位置。
2. **相似度过阈值**（默认 0.93）。这个数是实测的，理由见下一节。
3. **没过期**（默认 1 小时）。

## 一行缓存长什么样

表在 `claw4j_cache.semantic`（`V4` 建表，`V5` 加 `entities`）：

| 列 | 作用 |
| --- | --- |
| `fingerprint` | 权限指纹（`tables + actions` 排序后哈希） |
| `entities` | 实体签名（时间词 + 数字），与指纹一起构成上面那个"上下文" |
| `question_key` | 问题归一化后的 SHA-256，只用于去重：同一句话重问就覆盖旧行，不堆副本 |
| `embedding` | `vector(1024)`；检索用 `<=>`（余弦距离），相似度 = `1 - 距离` |
| `answer` / `expires_at` | **未脱敏**的回答与过期时刻——脱敏在出站那一层，命中与不命中走同一条路 |

唯一键是 `(fingerprint, entities, question_key)`。**不建 HNSW / IVFFlat**：在这个量级下精确
扫描既快又准，建索引等于多养一份要在写入时维护的结构（理由写在迁移文件末尾）。

## 阈值不是拍的：一张实测表

用 `text-embedding-v3`（dimensions=1024）算余弦。两组基准分别是
「上周华东成交额多少」与「上周华东区成交额多少」（后者多一个"区"字，就是真链路里用的那句）：

| 余弦（两组） | 问句 | 意思 |
| --- | --- | --- |
| 1.0000 | 同一句话 | — |
| 0.9987 | 上周华东成交额是多少 | 只多了个"是" |
| 0.9967 | 华东上周成交额多少 | 词序颠倒 |
| **0.9950 / 0.9956** | **上上周华东成交额多少** | **换时间，意思完全不同** |
| 0.9470 / 0.9501 | 上周华东销售额多少 | 同义（额 → 销售额） |
| **0.9372 / 0.9117** | **华东上周卖了多少** | **同义改写** |
| **0.9187 / 0.9154** | **上周华东订单量多少** | **换指标** |
| 0.8968 / 0.9057 | 上周华南成交额多少 | 换区域 |

只有一个数的前三行是当时只量了一组，不影响结论——结论只用带两个数的那五行，
它们恰好也是"最像"的那几类。

同一类"同义改写"在两组里差了 0.026，这个抖动幅度本身就是一个信号。这张表否掉三个直觉：

- **票面原定的 0.95 太高**：连 0.9470 的同义说法都会落空。
- **纯阈值救不了"换时间"**：0.995 比同义改写还高。任何单一阈值都无法同时做到
  "命中 0.9372"和"挡住 0.9956"——这不是调参能解决的，是语义相似度这件事本身的边界。
  所以"问题里的时间词与数字"必须**进上下文键**：`上周` 与 `上上周` 不是同一个上下文，
  压根不互相检索。这一段的取值见 `CacheAdvisor.entitySignature`。
- **"同义改写"与"换指标"的分数在第二组里是反序的**：同义改写 0.9117 反而**低于**同一组的
  换指标 0.9154。也就是说在两组数据上，没有任何一个阈值能同时做到"命中所有同义改写、
  挡住所有换指标"——这不是调参没调到，是这两类问法在向量空间里本来就没有先后。
  于是问题变成：往哪一边错？

**答案是往"漏"的那一边错。** 0.93 挡得住换区域（0.8968~0.9057）与换指标（0.9154~0.9187），
代价是漏掉措辞差得多的同义改写（0.9117）。另一组 0.9372 的同义改写刚好过线——
同一类问法在一组里进了、另一组里被挡在门外，这就是"阈值只能选方向"的具体样子。
漏只是没省到钱，误是给出另一个问题的答案，这两种错的代价不对等。

**这个结论要诚实地接受**：语义缓存对"数值/时间/指标实体只差一点"的问答本质上不可靠。
它真实的收益场景是"同一个人几分钟内几乎原样再问一遍"（1.0 与 0.99 那一档可靠），
不是"随便换个说法都能命中"。真出问题时的第一反应应该是调高阈值或关掉它，
而不是再往上叠启发式规则。

## 淘汰只有 TTL，没有 LRU / LFU

这三件事在这里不是一回事，混起来会得出"该加个 LRU"这种错的结论：

- **TTL 有**（1 小时，落成 `expires_at`），`SemanticCacheCleanup` 每小时真删过期行。
  过期判定写在 SQL 的 `where` 里而不是取出来之后过滤：一条过期的老问题不该参与
  "最相似"的竞争，否则它会把新问题挡在外面。
- **LRU / LFU 没有，也装不上。** 它们是"表满了淘汰谁"的策略，前提是"命中"有一个明确的键，
  可以计次、可以按时间排序。语义缓存压根没有键：命中是一次最近邻检索，每次检索都会碰到
  **所有**同上下文的行，"哪一条被访问过几次"没有可靠来源。何况容量从来不是这里的瓶颈——
  几十到几千行，全表精确扫描都在毫秒级（所以迁移里也没建 HNSW）。
- **真正会过期的是答案，不是行。** "上周成交额"的答案随日历翻页而变，而一行缓存自己不知道
  这件事。约束它的是 TTL 与"时间词进上下文键"，不是淘汰算法。

真到了需要限制容量的规模（几十万行以上），先加的是向量索引与按 `created_at` 的批量清理，
而不是 LRU——理由同上：LRU 依赖的访问计数在这张表里没有出处。

## 哪些一轮不缓存

判断依据是**这一轮实际调用过的工具**，不是问题文本。规则是"所有工具的动作名都必须等于 `read`"：

| 这一轮 | 缓存？ | 为什么 |
| --- | --- | --- |
| 一次工具都没调（纯问答） | 是 | 没有外部状态参与 |
| 调了 `querySales`（`read`） | 是 | `read` 是这个系统里唯一被声明为幂等的动作 |
| 调了 `draft_script` / `run_script` | 否 | 有副作用，复用那一轮的答案等于复用一次执行结果 |
| 调了没登记权限的工具 | 否 | 没人评估过它会碰到什么，保守方向是"不缓存" |

按这条规则，`recall_session` 也不缓存：它的动作名是 `recall_session` 而不是 `read`。
这个排除是刻意的——它读的历史每一轮都在变，复用它的回答等于复用一个已经变了的上下文。

"这一轮调过哪些工具"记在 `ToolCallLog`（ThreadLocal）里，写入点是 `MeteredToolCallback`——
那是所有工具的唯一入口，父 Agent 与子 Agent 都从那里过。放在别处必然有某条路径漏记。

**流式只读不写**：读是安全的，而且对 SSE 与飞书的收益更大（用户对首字延迟最敏感）。
写不做，因为流式下要拼出完整回答得靠累积每一块，而"每块是增量还是累计"因供应商而异——
拼错就是缓存了一条重复十遍的回答，而它下次会被原样发出去。同步路径已经能把缓存填上。

## 失败姿势：缓存不参与可用性

| 出问题的环节 | 结果 |
| --- | --- |
| 向量服务挂了 | 这一轮当作没命中（`reason=embedding-failed`），照常回答 |
| 缓存查询挂了 | 这一轮当作没命中（`reason=cache-failed`），照常回答——整条读路径裹在 try 里，包括诊断用的那两次查询 |
| 缓存写入失败 | 只影响省成本，这一轮的回答照常返回 |
| 这个上下文里没有候选 | 没命中；再查两次（先同权限不限实体、再全库），用来区分 `different-entities` / `different-permission` / `no-candidate` |

四条朝同一个方向：**缓存是优化，它没有资格让一轮对话失败**。`embedding-failed` 与
`cache-failed` 分开记，是因为它们的处置方式完全不同（一个等向量服务恢复，一个去看库），
混成一格的话，排查时第一眼就会看错方向。

最后一条只是**诊断**：那两次额外查询的结果绝不参与命中判定，否则就等于绕过了授权。

## 与票面原设计的三处偏离

| 票面 | 实际 | 理由 |
| --- | --- | --- |
| 引回 Redis Stack | pgvector（`claw4j_cache.semantic`） | 缓存要和授权、会话在同一套数据里做一致性判断；pgvector 已经在库里。ADR-0005 第二次修订 |
| 阈值 0.95 | 0.93 | 0.95 太高，连 0.9470 的同义说法都会落空；而同义改写与换指标在第二组里是**反序**的（0.9117 < 0.9154），没有任何阈值能两边都对，只能选"宁漏不误"那一侧 |
| TTL 24 小时 | 1 小时 | 问的是相对时间（上周/本周），答案随日历翻页而变；24 小时会在跨周一时给出上一周的数 |
| `misses` 的 reason 含"已过期" | 没有这一档：过期就落成 `no-candidate` | 过期判定写在 SQL 的 `where` 里，连诊断那两次查询也带着它，所以"从没写过"与"写过但过期了"在指标上分不开。要分开得再查一次不带过期条件的，而这一层只为把 miss 的原因说准——它不值得多一条查询 |

**Redis 仍然不引**。ADR-0005 里那段"引回 Redis Stack 要换镜像、客户端要 Jedis"的说明已标作废——
不标的话，下一个人会照它去装一遍，然后发现装了个没人用的东西。

## 框架自己有 `SemanticCacheAdvisor`，为什么还是自己写

Spring AI 2.0.2 带了这个 advisor，类在通用包
`org.springframework.ai.chat.cache.semantic`，但**物理上只打在
`spring-ai-redis-semantic-cache` 这一个 artifact 里**（连同 `DefaultSemanticCache`、
`spring-ai-redis-store`、jedis 7.4.1）。反编译之后的实情比文档写的更硬：

| 事实 | 后果 |
| --- | --- |
| `adviseCall` 只有"取问题 → 算 ctx → `cache.get` → 命中就返回 → 否则 `nextCall` → 非空响应就 `cache.set`" | 没有"该不该缓存"的钩子，写缓存只判响应非空 |
| `Builder` 只有 `cache` / `order` / `scheduler` | 网上传的 `timeToLive`、`similarityThreshold`、`isolateBySystemPrompt` 是 `pro.redisson` 第三方实现的，不是官方 API |
| `extractContextHash` 是 private，硬编码 SHA-256(系统提示词) | 隔离维度**不可干预**。我们全员共用一份系统提示词 → 整体换过去等于零隔离，`different-permission` 直接失效 |
| 接口里 `get(q, ctx)` / `set(q, r, ctx)` 是 **default 方法，默认实现直接忽略 ctx** | "隔离"不是框架替你做，是后端实现自己的事——它只给了一个字符串槽位 |
| 接口还有 `VectorStore getStore()` | 实现它就得再提供一个 `VectorStore`，而我们的表结构不是 `VectorStore` 的 schema |
| 命中后原样返回缓存响应，无标记、无指标 | 用户分不清"答得快"是因为缓存还是模型那天心情好；"命中率为什么低"也查不出来 |

所以这里的分工是"**占它的位置，不背它的实现**"：

- **上下文键**用的是框架的 `contextHash` 概念，只是取值换成"权限 + 实体"。
  这不是自创机制——槽位是框架留的，填什么是应用的事（它自己填系统提示词）。
- **相似度阈值与过期**在存储层判定，和 `DefaultSemanticCache` 的分工一致。
- **advisor 自己写**，因为框架把 `contextHash` 的来源写死在 private 方法里。

代价是两处"框架没有、我们加了"的东西，都在文档里点名，不是静默存在：
`sideEffectFree`（有副作用的一轮不缓存）与命中标记/指标（可观测）。
前者撤掉会产生功能错误（`run_script` 的"已执行成功"被复用），后者不改变行为正确性。

**退场条件**：哪天 `contextHash` 开放给调用方，这套就可以换成
`SemanticCacheAdvisor` + 一个 pgvector 的 `SemanticCache` 实现，只留"权限与实体"和"副作用判定"两个钩子。

## 纯问答也进缓存：知道，但不加判断

"你好，你能做什么"这类一问一答也会进表（`sideEffectFree` 对空集合返回 true——
没调工具就是没有外部状态参与）。它确实不是"查得到数的答案"，但**这一轮不额外加规则**：

官方的 `SemanticCacheAdvisor` 写缓存只判"响应非空"，同样没有"这轮调没调工具"的概念。
自己加一条，等于在一个框架明确留白的地方塞私有语义；
下次框架加了官方钩子，这条就成了要拆的旧代码。而它的收益只有"少存几行"。
真觉得碍事，调小 `claw4j.cache.time-to-live`（比如 10 分钟）比加判断直接。
