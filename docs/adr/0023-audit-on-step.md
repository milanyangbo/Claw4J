# 审计长在 step 上：一次工具调用一行，读法是视图，留存 90 天

---
status: accepted
date: 2026-11-02
---

出了事要查得清：**谁在什么时候、以什么角色、让哪个工具做了什么、谁批的、为什么被拒**。
这几样全部补在 `agent_step` 上（加六列），读的时候走视图 `claw4j_run.audit_trail`。
**不新建执行表**——另建一张的话，同一件事从那天起有两个答案，对不上时没人知道信哪个。

> 与 ADR-0016 的关系：那条 ADR 否决的是"每次工具循环内部的检索与自纠错都落一行"
> （事件溯源那套）。这里落的是**一次工具调用**（真跑了 / 被拒了 / 停在等审批），
> 且只带摘要与指纹、不带参数原文与产出原文。粒度变了一格，理由换了：
> 不是为了回放，是为了合规那一格答得出来。

## Context

在 P07 之前，这张表能回答"这件事做到第几步"，答不出三句话：

1. **这次调用是谁让做的**。`agent_run.owner` 是归属键（`userId@权限指纹`），
   它是拿来判"这是不是你的 run"的，不是拿来回答"谁"。而"以什么角色"这一格，
   收权之后第一个被问到的就是它。
2. **这次调用是哪次批准的**。审批表记着"谁批的、批的什么参数"，执行记录那边却没有编号，
   两边对不上——查一条越权时，只能按时间猜是哪一条。
3. **被拒的那次也算一次调用**。拒绝发生在工具执行之前，`MeteredToolCallback` 根本看不到它，
   于是"有人试过但被拦下来"这件事在库里完全没有痕迹，只有一条会被滚动窗口清掉的计算器。

顺带一件事：留存。会话有 TTL、缓存有 TTL，都各配了一个清理任务（这个坑踩过三次）；
审计如果一个数都不配，它就只会一直长。

## Considered Options

**另建一张 `audit_tool_call`** — 否决。它跑得起来，但那时"这件事调了两次还是三次"有两个答案：
step 说一套、审计说一套，而对不上的那天没有任何一方是权威。审计的价值全在"它就是执行记录"，
一旦复制，它就成了第二份需要有人对账的数据。

**从会话表里事后重建** — 否决。会话是被压缩的（`SessionCompactor` 会把超阈值的事件压成摘要），
压缩掉的第一批正是"调了哪个工具、参数大概是什么"这类结构化细节；而且会话按人分片，
回答不了"跨人、跨时间按结局查"。

**加列 + 视图（采纳）** — 六列（`actor / actor_role / outcome / args_digest / args_summary /
approval_id`）、一条唯一索引、一个只读视图。视图不复制任何真相：它把 step 的列、
run 的目标、审批那一侧的结论接在同一行上，于是"谁批的"不用再教人写三张表的 join。

## Decision

- **一行 = 一次工具调用**，`kind = 'tool_calls'`，`outcome` 只有三种：
  `executed`（跑过，成没成看 status）、`rejected`（被鉴权挡住）、`awaiting_approval`（停在等人点头）。
- **两个写口，与两个接缝一一对应**：鉴权 Advisor 写 `rejected` / `awaiting_approval`
  （工具没被执行，只有它知道），工具回调写 `executed`（"真的发生了"只有它知道）。
  同一件事只有一个类在写（`ToolCallAudit`），它才有资格说"审计与执行是同一份真相"。
- **只落摘要与指纹**：`sha256(工具名 + 规范化参数)` 与前 200 字符的脱敏摘要。
  不落参数原文，不落产出原文——审计不是业务数据的第二份副本。产出那一侧只有
  "工具抛出 XxxException"这句话（只记类型，不记 message）。
- **一条批准 ↔ 一条执行**，由唯一索引担保，谓词是 `outcome = 'executed'`：
  等审批那一行也带着同一个编号（"停在谁身上"要能查），而它不是一次执行。
- **留存 90 天**，作用于 run（step 级联）与审批（没有外键，单独删，按提出时间算）。
  过期不是一种状态，是时间：判定在 SQL 里用库的时钟比，`AuditRetention` 只负责删。

## Consequences

代价，写下来免得以后变成"意外"：

- **step 表会长得快**。一次工具调用一行，不带参数原文，但仍然是一行。90 天留存是对它的补偿，
  而不是"这张表本来就不大"。真要更省，就该回头问"是不是每次调用都必须留痕"——
  答案是合规场景下是的，所以这里不再优化。
- **兑现批准与执行工具之间那条线是进程内状态**（`ToolCallAudit#granted` 的那个 map）。
  两处拿不到同一份上下文（ToolContext 是每次执行现造的），所以只能这样连。
  代价：多副本部署时那一行的 `approval_id` 可能是空；兑现了但没执行会留下一条会被 TTL 清掉的槽。
  丢了只影响这一条线，那一行审计仍然在。
- **子 Agent 的工具调用暂时不落审计**：子链的工具上下文里没有 runId（与预算同一个原因），
  写不进任何一件事。那是 A10 的事，不是"忘了接"。
- **审计 ≠ 观测 ≠ 评测**：指标回答"今天花了多少、拒了几次"（滚动窗口，会归零）；
  审计回答"三个月前那次是谁批的"（90 天，按行查）；评测（A06）回答"答得好不好"，
  与这里一个字段都不共用。三者混起来的第一个症状是"审计里查不到上个月"，
  而那时通常已经有人拿它当过监控看板了。
- **`heartbeat` 的重估条件到齐了**：ADR-0021 说它要"预算（A04）与审计（P07）都落地之后"再谈。
  现在两半都在，它可以重估——但重估的结论是"它只是 `schedule_task` 的上层用法"，
  归下一张票，不在本条里。
