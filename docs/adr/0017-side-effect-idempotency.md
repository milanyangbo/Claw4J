# 副作用的幂等契约：意图先行，重跑等于查表

---
status: accepted
date: 2026-10-29
---

每次**有副作用的**工具调用，先落一行带唯一键的执行意图；执行完把返回值绑回去。
重跑时命中已完成的行，就返回旧结果、**不再执行**。崩溃留下的悬空行**不自动重试**，
一律变成一次待人确认的待办。

> 实现状态：本条是裁决，尚未落代码。它不依赖 A01 的全部，但必须早于 A01 第一版表结构。

## Context

ADR-0016 让 run 可以被续跑之后，续跑的起点是"上一个没走完的 step"。
问题是：**工具的副作用与 step 落库之间没有事务边界**。

序列是这样的：模型决定发邮件 → 工具执行、邮件真的发出去了 → 进程在这一瞬间崩了 →
重启后从 suspended 的 step 续跑 → 模型看到上一次没有结果 → 再发一次。
第二封邮件在任何人看来都合理：模型不知道前一封已经进了对方邮箱。

这类事故的形状与已有的 `InboundMessage.eventId` 去重不一样——那个管的是**通道重推同一个事件**
（飞书超时会送两次同样的 eventId），管不到"模型自己决定再试一次"。

失败方式还是不对称的：多查一次库毫无代价，多发一封邮件、多执行一次 `run_script`、
多外调一次不可回滚的 HTTP 接口，都要别人来收拾。

## Considered Options

**每个工具自己保证幂等（自报幂等键）**
否决。`examples/scripts/*` 里的脚本包与第三方 MCP server 都是别人写的实现，我们改不了它们的内部；
"保证幂等"也写不进验收——没法用测试证明一个工具做到了它声称的事。
这条思路里唯一正确的部分（工具自己才知道哪些参数构成"同一件事"），被下面键的设计吸收了。

**执行前多问一句人**
否决。等于把正确性转嫁给用户，而且只在审批打开时成立（多数工具按 ADR-0007 并不需要人审）。

**意图先行：`tool_effect` 表（采纳）**
执行前落一行带唯一键的意图，执行完把返回值绑回去；重放时命中就返回旧结果。

**给整个过程加事务（两阶段提交）**
否决。涉及的不是同一种资源：一次工具调用背后可能是 MCP 子进程（ADR-0014）、
一个 python 脚本（ADR-0002）、或者对方的 HTTP API。跨这些边界没有事务，只有补偿，
而通用补偿等于重写业务。

## Decision

新增 `tool_effect(run_id, step_seq, tool_name, idempotency_key, args_digest, status, result_ref, created_at)`，
唯一约束 `(run_id, idempotency_key)`。

- **键的形状**：`sha256(runId + stepSeq + toolName + 规范化参数 JSON，对象 key 递归排序)`。
  排序是必需的：不排则模型换个参数顺序就得到新键，等于绕过幂等。
- **键含 runId**：跨不同一件事，同参数要真的重做——"上周成交额"这次问和下次问是两个请求。
- **与审批指纹划清界限**（最容易混的一处）：审批指纹是 `sha256(toolName + 规范化参数)`，
  **不含 runId**，因为一次批准要覆盖"这类操作"，否则每个新任务都要重批。
  两个哈希形状相似、口径相反：**幂等键要区分每一次执行，审批指纹要跨执行复用**。
  混用的事故是双向的——用错键轻则重复执行，重则批一次长期通行。
- **状态只有三档**：`pending → done / failed`。执行前插 `pending`，执行完改 `done` 并记返回值。
  留着 `pending` 的行，意思是"可能没发出去，也可能发出去了但没记上"。
- **悬空行不自动重试**：副作用类动作（`run_script` / `draft_script` / `send_email`，
  以及 MCP 里被按工具覆盖成写动作的那些）转成 `needs_review`，把 run 停在 suspended 等人来点；
  **只读类动作**（`read` / `read_system` / `use_skill` / `recall_session`）允许自动重跑一次——
  多查一次没有损失。这一条是本 ADR 承认做不到的事：幂等表把"静默重复执行"变成
  "一次确定的待办"，消灭不了它。
- **只对有副作用的动作落行**，按 ADR-0007 已经在用的动作名判定。读动作一律不写 effect 行，
  否则表按调用次数线性膨胀且没人读。
- 开关 `claw4j.execution.idempotency=on|off`，默认开，排查时能关掉比对行为。

## Consequences

- **包在哪里已经有答案**：`MeteredToolCallback` 已经是每条工具调用的唯一入口，
  它的 javadoc 记录了为什么包在 `ToolCallback` 上而不是 `ToolCallingManager` 上
  （一次 `executeToolCalls` 可能包含多个调用，计在 manager 上数的是轮次不是工具）。
  同一个理由对幂等成立，所以新增的包装层沿用这个形状，不再论证一遍。
- **代价**：每次有副作用的调用多一次插与一次改；多一张表；需要一处挂载点。
  漏包一条路径就等于那条路径没有幂等——这个仓库出过两次"某条路径没被包上"的事故，
  所以对应的单测要这样写：**同一个 key 调第二次，被调工具的实现体必须没有被执行**
  （用计数断言，不用等待）。
- **`pending` 行是数据不是错误**。丢掉它等于承认"这一步不知道做没做完"，
  所以 `GET /api/runs/{id}`（ADR-0018）要把它列出来，而不是只在日志里出现。
- **明确不做**：通用补偿与回滚、跨进程的分布式事务、第三方工具的幂等改造
  （我们管不了，只能在文档上标注"这个 server 不保证幂等"）。

与另外两条的界线：ADR-0016 定"表里有什么"；本条定"工具怎么被包"；**结果怎么回到人**归 ADR-0018。
