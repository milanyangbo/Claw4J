# 通道选型：飞书长连接为真实 IM 通道，HTTP+SSE 为无账号演示通道

---
status: accepted
date: 2026-10-22
---

ADR-0008 定的通道顺序里没有真实 IM。真实 IM 通道的价值不在于"多接一个平台"，而在于它会逼出 HTTP 通道逼不出来的工程约束（事件推送的超时、重推、多实例投递语义），这些约束才是能讲的东西。选择标准是三条：**个人能否开通**、**本地能否免公网调试**、**有无官方 Java SDK**。

## 事实核查结论（2026-10）

| 平台 | 个人能否开通机器人 | 免公网调试 | 官方 Java SDK |
|---|---|---|---|
| **飞书** | ✅ 个人账号可直接创建企业自建应用，无需企业认证 | ✅ 长连接（WebSocket）模式，SDK 主动外连，无需公网 IP/域名/内网穿透 | ✅ `com.larksuite.oapi:oapi-sdk`，Central 上最新 2.8.7 |
| **企业微信** | ❌ 个人可注册"个人组建团队"，但**腾讯官方明确：个人注册无法登录网页管理后台**，而机器人必须通过在管理后台创建自建应用拿 AgentId/Secret | 部分（有长连接，但前提是能进后台） | ❌ 无官方 SDK，只有社区包（`weixin-java-cp`） |
| **钉钉** | ✅ 个人可建团队 | ✅ Stream 模式同样免公网 | ⚠️ 官方 SDK 未在 Maven Central 命中，需按官方文档确认坐标 |
| **Telegram** | ✅ BotFather 几分钟拿 token | ✅ 长轮询/getUpdates | ✅ `telegrambots` 6.9.7.1 |
| **微信个人号** | ❌ 无官方机器人 API，第三方走协议逆向 | — | ❌ 封号风险，不做 |

**企业微信这条路对没有公司的人走不通**，不是配置问题而是账号体系问题：个人团队拿不到管理后台，就没有自建应用，也就没有收发消息的凭据。它唯一能用的是"群机器人 webhook"，但那个只能往群里推消息，**收不到用户消息**，做不成双向对话。若后续拿到企业管理员权限，本条 ADR 的顺序需要重排。

## Considered Options

**Telegram 作为主通道**
否决。它最简单，但国内访问需要代理，面试现场演示有翻车风险；且它在国内企业场景里不是主流，讲不出业务价值。保留价值：作为"第二个 Channel 实现"证明 SPI 抽象有效，成本仅半天。

**企业微信作为主通道**
否决，理由见上。

**HTTP+SSE 作为唯一通道**
部分采纳，但降级为"演示通道"而非唯一。它不需要任何外部账号，是面试现场唯一能保证演示的通道，必须保留；但它逼不出事件推送的真实约束。

**飞书长连接 + HTTP+SSE 双通道（采纳）**
飞书满足全部三条标准，且它的两条硬约束反而成了设计素材（见下）。

## Consequences

- **交付顺序更新为**：HTTP+SSE（M1）→ 飞书长连接（M2）→ A2A（M3）→ Teammors WebSocket（最后，可不做）。Telegram 作为可选的第二 Channel 实现，用于证明 SPI 可替换。
- **3 秒超时重推是硬约束**：飞书长连接要求收到事件后 3 秒内处理完成且不抛异常，否则触发重推。而 Agent 跑一次 Text-to-SQL 可能十几秒。因此 `ChatChannel` 的入站路径必须做成**收到事件立刻 ACK → 交给异步编排 → 结果通过主动发消息接口回推**，而不是在事件线程里同步等 Agent。这条约束同时逼出**事件去重**（重推会导致同一条消息被处理两次），是真实的工程问题，正好落在 M2。
- **集群投递语义**：长连接模式的推送是集群模式、不支持广播，同一应用多个客户端时只有随机一个收到。本地演示保持单实例；多实例场景要说明这条限制，不能假装它能负载均衡。
- **模块调整**：`claw4j-channel` 拆为 `claw4j-channel-api`（放 `ChatChannel` SPI，不依赖任何平台 SDK）+ `claw4j-channel-http` + `claw4j-channel-feishu`。重依赖（`oapi-sdk`）只留在飞书实现里，`claw4j-app` 按需引入，不想接 IM 的人不会被拖累。ADR-0004 的五模块由此变为七模块。**〔已过时〕**此条已被 ADR-0010 推翻：三个通道模块当时都是零 Java 文件的空壳，拆分没有收益；最终形态是单一 `claw4j-channel` 模块内按包分层（`spi` / `http` / `feishu`），边界由 ArchUnit 包级规则守卫。加渠道不再新建模块。**依赖也不再走 optional + `-P` 开关**：`oapi-sdk` 作为普通依赖随 `claw4j-channel` 传递，`claw4j-app` 不必声明、构建不必带参数（2026-10-27，见 ADR-0010）。
- **凭据处理**：App ID / App Secret 走环境变量与 Spring 配置，不进 `SKILL.md`、不进仓库（延续 ADR-0002 的收口原则）。
- 1.x 的 Teammors 私有加密协议仍排最后：它的 ECDH/AES 与自建心跳讲不出通用价值，代码留在 `legacy/` 作对照。

## 实现记录（2026-10-26，M2 收尾落地）

Consequences 里"3 秒超时重推"那条展开的几件事，各自落在哪个类、凭什么说它成立：

| 约束 | 落点 | 证据 |
| --- | --- | --- |
| 收到事件立刻 ACK | `channel.feishu.sdk.FeishuLongConnectionChannel#onMessage` 只做"翻译 → 交给 `InboundDispatcher#accept`"；`accept` 只去重、认人、投任务，方法返回即 ACK | 有测试守着：`accept` 返回时 Agent 一次都没被调；Agent 卡住不放时 `accept` 照样立刻返回（若它等 Agent，这条用例会挂在超时上） |
| 异步编排、不拖住事件线程 | `InboundDispatcher` 注入的 `Executor`（装配里给它单独的 `feishuExecutor`） | 有测试守着：两条事件都进到 Agent 里、谁也没被串行挡住；池满时用户当场收到一句"稍后再试"，而不是干等 |
| 按 `eventId` 去重 | `InboundDispatcher` 内的 `SeenEventIds`：进程内 `ConcurrentHashMap`，TTL 10 分钟，**先记再跑** | 有测试守着：重推仍然 ACK、Agent 只跑一次、群里只有一条回答；过了窗口同一个 `eventId` 会重新处理，表不会只增不减 |
| 主动回推 | `channel.feishu.sdk.FeishuOpenApiReplySender`：`im().message().create`，`receive_id_type=chat_id`、`msg_type=text` | 有测试守着：Agent 抛异常时群里出现的是一条说清失败的消息；模型给空内容时也有占位，不静默丢弃 |
| 超长回答分段 | `channel.feishu.MessageSplitter`：按 4000 字符切块，代码块每段重放围栏（带语言标记）、表格每段重放表头 | 有测试守着：段序不变、每段不超上限、围栏成对、表格每段都有表头、原文一行不少 |
| 认人 | `FeishuChannelProperties#roleOf`（`roles.*.users` 里填 `open_id`）→ `FeishuPrincipalResolver` 拿角色名去共用的授权表 `claw4j.channel.http.roles` 取表与动作；认不出回"没有权限" | 有测试守着：未登记的 `open_id` 回"没有权限"；同一个人登记两个角色在启动时就失败；角色名在共用表里不存在时启动失败并点名 |

三条实现上的取舍，写在这里免得下次重新讨论：

- **去重表就在进程内，没有引入 Redis**：跨实例去重的前提是广播，而长连接是集群投递、不支持广播（见上"集群投递语义"）。单实例是既定形态，多实例去重在这个形态下没有意义；代价是重启后十分钟内的重推会被当成新事件——比"引入一个连不上就起不来的组件"便宜。
- **"没有任务可跑"的两条分支必须当场回一句**：认不出人、线程池满。前者不回，用户会以为机器人坏了（ADR-0007：不设兜底身份）；后者已经 ACK 过、飞书不会重推，不回就永远没人应。这两次发送是事件线程上唯一的网络往返，几毫秒，且不涉及模型。
- **事件回调里绝不抛异常**：抛出去平台会重推一条同样处理不了的消息。翻译失败、回推失败都收在回调内部记 ERROR；只有"连不上"在 `start()` 抛，让应用起不来（不带着一个收不到消息的通道跑）。

> **修订记录（2026-11-08，票 02 落地）：最后那句"连不上就起不来"收窄成"只有永久错才起不来"。**
> 可恢复的失败（握手超时、网络层失败、对端暂时不可用）不再抛：状态置 `DISCONNECTED`，
> 后台按 30 秒起、每次翻倍、封顶 10 分钟退避重连，**应用照常启动、其它通道照常工作**。
> 凭据错、应用未发布/未开通长连接仍然是启动失败。判据在 `FeishuConnectionFailures` 里，
> 每一格都照 lark-oapi 2.8.7 的字节码核过（`awaitReady` 超时抛 `ServerUnreachableException`；
> 取连接地址那步的 HTTP/业务错码抛 `ServerException`；其余非 0 业务码与本地凭据缺失抛 `ClientException`）。
>
> 改的理由不是"宽松一点"：原判据把**配置错**与**时序错**混成一类，于是一次对端重启在 K8s 上就是
> CrashLoopBackOff，连不依赖这条连接的 HTTP 通道也一起不可用。OpenClaw 的分法见
> `docs/channels/slack/transports.md:71`（可恢复的重试到通道停止，凭据类失败立刻失败）。
> 上面"去重表就在进程内"那条 bullet 会在票 04 落地时一并失效（改成落库），届时再补一条。
> 修订记录（2026-11-08，票 04 落地）：**"去重表就在进程内"那条失效了，改成落库**。入站现在是
> "先落库 → 再 ACK → 认领 → 执行 → 结算"，表在 `claw4j_channel.inbound_event`（`V7__channel.sql`，形状照 OpenClaw 的
> `channel_ingress_events`）。三条随之改变的事实：
> ① 重推窗口由 tombstone 的保留期给（默认 7 天），不再是 10 分钟的进程内表；
> ② **重启之后没跑完的那条有人接着跑**——这才是原来那句"代价是重推被当成新事件"真正压着的东西：
>    平台收到 ACK 就不会重投，而消息当时只在内存里，进程一退就永久消失；
> ③ 线程池满不再当场回一句"稍后再试"（上面第二行的后半句作废）：事件已经在库里，池满只是
>    "这一轮没开始"，那一条仍是 `pending`，下一轮扫描接着跑。
> **代价写清**：入站从此依赖库在——库不可用时 `accept` 会抛出去（宁可让平台重推，也不越过一条
> 没落库的消息）；每次入站多一次写入。表结构与四条判断（复合主键、tombstone、没有序号、
> 孤儿回收不涨 attempts）写在 `V7__channel.sql` 的注释里。
