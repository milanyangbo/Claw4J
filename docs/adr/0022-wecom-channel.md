# 企业微信通道：自建应用 + 手写回调加解密，不做被动回复

---
status: accepted
date: 2026-11-02
---

企业微信作为**第二个真实 IM 通道**接进来（P06）：入站是一个公网回调端点，出站是一次应用消息
`POST`；回调解出来的五个字段直接交给 `InboundDispatcher`，与飞书共用同一份编排。
**不引第三方 SDK，不改内核**——只在编排层加了一句可选的回执。

> 与 ADR-0009 的关系：那条 ADR 的结论是"企业微信这条路对**没有公司的人**走不通"
> （个人注册能建团队，但进不去网页管理后台，也就拿不到自建应用的 AgentId/Secret），
> 所以当时把它排在飞书后面。本条不是推翻它，而是补上它写的那个前提：
> **拿到管理员权限之后，接进来的形状是什么**。

## Context

飞书那条通道证明了 `InboundDispatcher` 抽得出来：去重、认人、异步、回推四件事与平台无关，
飞书只是在"怎么收"和"怎么发"上各有一次适配。企业微信要回答的是三个新问题：

1. **收**。企业微信没有长连接可选（自建应用走的是公网回调），回调要自己验签、自己解密。
   报文是 XML，密文是 AES-256-CBC，签名是四个字符串排序后的 SHA-1。
2. **回**。回调五秒内必须给响应，否则重推；而一次 Text-to-SQL 十几秒。
   协议允许"被动回复"，但安全模式下回一段文本也要现加密一段 XML。
3. **推**。结果要能回到人手里，并且要能被 A05 的目标表找到（在飞书问、企微收）。

## Considered Options

**引 `weixin-java-cp`（社区包）** — 否决。它把加解密、换 token、发消息都包了一层，
但我们要的只有"一个回调端点 + 一次 POST"。为它拖进一个第三方依赖，换来的是
"这个包什么时候跟进 Spring Boot 4"这类与本事无关的维护问题；而且它替我们做的判断
（比如重试策略、token 缓存）恰好是这里最需要说清楚的部分。

**做被动回复（回调响应里直接回一段加密 XML）** — 否决。它确实能省掉一次推送，
但代价是：加密要写第二遍（这次是加密方向）、响应体要按协议拼一段 XML、
而"五秒内"这个窗口从此同时管着"解出来"和"答出来"两件事。
更要紧的是它只在"答案恰好很快"时才可行——而我们的答案从来不快。
**选的是回空串（= 收到了，不回复）+ 主动推送。**

**给回执加在通道里（accept 之前自己发一句"收到"）** — 否决。看起来最省事，
但它排在去重之前：重推的那一条会再"收到"一次；也没过认人：被拒的人先被安抚一句、
紧接着又被告知没有权限。回执只能加在**去重与认人之后**，那是编排层的位置，
所以在那里加了一个可选的第五件事（`InboundDispatcher` 的 `receipt`）。

**跨实例去重用 Redis** — 否决，理由与 ADR-0009 完全相同：回调是平台单点投递，
单实例是既定形态；为了一个不存在的场景引一个连不上就起不来的组件不划算。

## Consequences

- **五秒窗口决定了形状**：控制器只做"验签 → 解密 → 交给编排 → 回空串"，
  返回时模型还没开始跑。答案走 `POST /cgi-bin/message/send`。
  代价是那十几秒里对话框没有动静，所以补了一句回执（`WecomChannel.RECEIPT_REPLY`）——
  企业微信的客户端没有"正在输入"，这一句只能自己发。
- **三样配置错一个就是静默失败**：`token` 错 → 签名永远对不上；
  `EncodingAESKey` 错 → 解密抛异常；`corp-id` 错 → 解出来的 receiveid 与它不等。
  三种表现都是"用户永远等不到回答"，所以前两样在构造时就校验，第三种在解密时校验并记 WARN。
- **`receiveid` 必须校验**：签名对、密钥对，内容却可以是别人家的。这条检查是唯一挡得住它的东西。
- **`@ConditionalOnMissingBean` 要写名字，不写类型**。飞书与企微的 `OutboundDelivery`
  是同一个类型，按类型判"缺不缺"的结果是**谁先装配谁赢**，另一个永远注册不上——
  而"在飞书问、企微收"恰恰需要两个实现同时在场。飞书那份（`feishuOutboundDelivery`）
  与本条一起改成了按名字判；同一个坑在 P03 的 `ApprovalCards` 上已经踩过一次。
- **这条件通道没有"连接"**：`start()` 只记一行日志，不做回调地址探活。
  与飞书"连不上就抛"的区别在于：飞书的连接是它自己发起的，连不上就是真的收不到消息；
  而回调地址通不通，从容器里探出来的结论经常是反的（反向代理、白名单）。
- **认证与授权仍然是两件事**：`roles.*.users` 里只填"谁是谁"（成员 UserID），
  表与动作去 `claw4j.channel.http.roles` 按角色名取；角色名对不上就在装配期失败。
  这一条与飞书那份逐字同构，是"授权表只有一份"的延续。
- **不做**：群机器人 webhook（只能推不能收）、通讯录同步（成员名单仍然手写在配置里）、
  被动回复与图文卡片、企业微信的"保密消息"（`safe=1`，要求成员点开才可见）。
