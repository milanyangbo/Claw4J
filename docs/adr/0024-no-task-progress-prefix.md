# 不往上下文里钉"任务进度"

---
status: accepted
date: 2026-11-05
---

ADR-0019 里 A08 的原话是"压缩可以丢细节，不能丢『还剩几步没做』和『上一次为什么失败』"。
这个 ADR 记录的是：**把它做成一条被钉住的系统事件之后，实测找不到它能生效的场景**，
以及为什么"改成按会话投放"也救不了它。

## Context

第一版把进度做成系统事件，入参是这一轮的 `runId`。评测跑下来：

```text
progressWritten: false   compacted: false
```

两件事叠在一起：

1. 评测的每条消息都不带 `runId`，`openRun` 每轮新开一件，`planOf(新 run)` 是空的；
2. 压缩根本没触发。历史全在，模型当然答得对——**测的是"记得上下文"，不是"压缩之后还记得"**。

于是有"改成按会话查"的想法：压缩丢的是会话历史，投放就该落在会话上。
方向听上去对，但代码没有支撑它：

`ChatClientAgentPort` 每轮收尾都调 `runs.finish(runId, RunStatus.DONE, answer)`。
**run 的寿命是一轮，不是一段对话。** 实测连问两句之后，该 `owner` 下
`status in ('running', 'suspended')` 的行数是 0
（`RunLifecycleTest#anAnsweredTurnLeavesNothingUnfinished`）。

所以"这个会话里最近没做完的那件事"，在普通多轮里根本不存在——按会话查也一样查不到。

三条路径逐一核对：

| 路径 | run 从哪来 | 进度有没有内容 | 有没有增量 |
| --- | --- | --- | --- |
| 普通多轮（消息不带 runId） | 每轮新开，答完即 `done` | 新 run 的 `plan` 为空；上一件已收尾 | 无 |
| 续跑（消息带回 runId、审批放行） | 同一个 run | 有 | 无：`promptText` 已经用 `recap` 把目标 + 计划 + 最近 5 步拼进提示词，每次从库里重新渲染，压缩影响不到它 |
| 另一件正在并发跑 | 别的线程 | 有 | 不该钉：那是别人的事被塞进这段对话 |

## Considered Options

**按 `runId` 传（第一版）** —— 否决。只有续跑路径有内容，而那条路径 `recap` 已经覆盖。

**按会话查最近未收尾的 run** —— 否决。前提是 run 跨轮存活，现在不是。
把它改成跨轮是个大变更（每轮要不要 `finish`、谁说一件事做完了），不该由一条进度前缀倒逼。

**只钉 `suspended` 的（当成"待办提醒"）** —— 否决。等审批时确实有一件事挂着，
但那时用户正在等批准，而 resume 时 `recap` 本来就会带上计划。收益很窄，
代价是一条新的系统事件类型和新的误钉风险。

**不做** —— 采纳。压缩丢的是"用户之前说过什么"，那是摘要的活；摘要压得不好应该改策略或阈值，
不是在旁边加一条永远无法验证的前缀。

## Decision

不往上下文里钉"任务进度"。A08 关闭，实现不合并。

留一条守门测试：`RunLifecycleTest#anAnsweredTurnLeavesNothingUnfinished`。
它钉的不是 A08，是"run 的寿命是一轮"这个前提。哪天前提变了（比如真的支持跨轮长任务），
这条会红——到那时 A08 的问题才有重新讨论的余地，而不是靠谁记性好。

## Consequences

1. **每条对话少两次读、一次写**：不再有 `latestUnfinished` 查询与 `appendMessage`。
2. **`spring.ai.session.allow-system-messages` 保持默认 `false`**。打开它没有用处，
   而一旦打开，别处往会话里写系统消息就不再被拦住——那是个更值得保留的闸门。
3. **"还剩几步"仍然只有一个出口**：续跑时的 `recap`，与 `update_plan` 的工具回执。
   不要在别处再拼一份，否则两处会各说各的。
4. **A09（失败回灌）、A10（子 run 预算）不受影响**。如果确实需要"跨轮接着做一件事"，
   那是 **run 的寿命**问题，要单独开票；不是上下文前缀的问题。
