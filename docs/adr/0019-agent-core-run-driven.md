# Agent 线任务拆分：12 张票（A01–A12）

---
status: accepted
date: 2026-10-29
---

把 agent 核心的能力增量按「能不能把一件事做完 ▸ 答得对不对 ▸ 能不能同时做很多件」三层拆成
**12 张票（A01–A12）**，每层的完成定义不是进度描述，是**验收闸门**。这条 ADR 记的是这条线的
任务清单与每张票的裁决；ADR-0016 / 0017 / 0018 已经裁过的边界不再重复。

## Context

现状可以被一句话概括：`ChatClientAgentPort` 一次 `prompt().call()` 就结束，`stream()` 也在同一处
结束。**系统里没有任何一个地方能表达"这件事还没做完"**。

三个直接后果，每条都能用一个动作验证：

1. **"继续"在系统里是一段新对话**。让它做一件一轮做不完的事（比如逐表对齐口径），只能靠用户
   再问一句；而这一句与上一句互不相识——不是同一件事的下一步。
2. **预算记的是轮，不是事**。`ToolCallBudget` 的两个常量（单工具 3 次、整轮 6 次）写在
   `toolCallingManager` 上，它的 javadoc 自己写着"一轮对话的工具调用预算"，跨请求无法累计。
3. **计划只活在上下文里**。`SessionCompactor` 每轮进模型前压缩；`recall_session` 能召回原文，
   但召不回"接下来做第几步"。

再叠加两个"没有办法判断好不好"的事实：

- **工具检索不做中文分词**。现在是 `RegexToolIndex`，按空白与标点切词。`ToolSearch.SYSTEM_SUFFIX`
  的注释里记着实测：query 写"回忆以前说过的话"命中 **0** 个工具，写成关键词才命中。
- **301 条用例证明的是装配成立**。数值确实从库里出来，但没有一条能回答"这版比上版好还是差"。

## Considered Options

**一次性做一个大内核改造**
否决。前 5 张（A01–A05）就能让"一件事"闭环，中间可以被打断、被验证；一次性做会把这一次发版
变成"一切都不确定"。

**按 OpenClaw 的能力清单逐条补**
否决（见 ADR-0021）：它的形态是单用户常驻助手，清单不是目标。

**按「做完一件事 ▸ 答得对 ▸ 同时做很多件」三层拆（采纳）**
每层的完成定义是验收闸门。

## Decision

编号规则：`A01–A12` 属 agent 线，`P01–P19` 属平台线（ADR-0020）。编号跨批次唯一，不复用。
每张票都写明**一句话裁决 / 判据 / 依赖**——判据是能照着执行的验收动作，不是形容词。

已经是终点的地方不重复列票：ADR-0016 裁的是边界（run/step 落什么），ADR-0017 裁的是副作用调用的幂等，
ADR-0018 裁的是投递目标与通知策略的形状。这三份里的结论在下面直接引用，不再新开一张票。

依赖图（实线是硬依赖，虚线是"挂得上"）：

```text
A01 ──► A02 ──► A03 ──► A08
  │       │
  │       ├────► A04 ──► A10
  │       │              ▲
  │       └────► A05     │
  │                      │
  └──► A06（评测）──► A07、A09、A10
                 A11 ──► A12
```

### M7a · 一件事能做完（A01–A05）

**A01 · run / step 成为系统里的第一等身份**

裁决：**一次"事"= 一个 run**。模型收到请求时在入口造 run，工具循环**内部**一次都不写库
（这条边界已由 ADR-0016 裁过，此处只记它落到哪张表：`run(id, principal, status, created_at, …)` +
`step(run_id, seq, kind, payload, created_at)`）。

判据：把进程杀掉再起来，能答出"这件事做到第几步"；同一件事的两次回答 `runId` 相同。
今天这两个问题的答案是"答不出"与"每次都是新的"。

**A02 · `resume(runId)`：让"继续"是同一件事的下一步**

裁决：被 resumed 的执行**不新建 run**，`seq` 接着涨。入口形状已在 ADR-0018 定过，这里记账单点：
用户再说一句、HTTP 的 `resume` 入口、以及 P02 审批通过后的服务端续跑，三条都走同一个方法。

判据：让它做一件一轮做不完的事（例如逐表对齐口径），中间断开，回来再问一句——
落的是同一个 `runId`、`seq` 连续，且回答内容是"下一步"，不是从头再来。这条的答案今天定是"新对话"。

依赖：A01。

**A03 · 计划外置：模型要记得"做到第几步"**

裁决：计划写进 run 的 step，不放在上下文里。`SessionCompactor` 每轮压缩之后，模型仍能从库里读到
"还剩什么没做"。今天 `recall_session` 召得回原文，召不回进度——差别就在这张表。

判据：压到超过阈值之后仍能答出未完项；把第 2 步标 `done` 再 `resume`，模型不会重做第 2 步。

依赖：A02。

**A04 · 预算从"一轮"提到"一次 run"**

裁决：预算按 run 累计，轮预算降级为默认值而不是上限。`ToolCallBudget` 那两个常量（单工具 3 次、
整轮 6 次）的 javadoc 自己写着"一轮对话"，跨请求无法累计，所以现在的预算**管不住一件跨轮的事**。

判据：一次 run 跨 3 轮共调 7 次工具 → 第 7 次被拒（今天是每轮重置，7 次全放行）；
超预算写结局并停下，而不是抛异常让上层猜。

依赖：A01。**这张票是 ADR-0021 里 `heartbeat` 的重估前提之一**，另一个前提是 P07。

**A05 · 结果投递与回收：run 绑 principal，不绑通道**

裁决：投递目标是 ADR-0018 的 `(runId, channelRef)` 一对多表；`GET /api/runs/{id}` 轮询；
通知策略 `done_only / silent / state_changes`，**定时任务默认 `silent`**。

判据：在飞书提问的人可以在企微收到结果（或轮询拿到同一条 run 的完整结果）；
定时任务跑完不打扰人，但能被查到。今天的形状是"谁问的就回给谁"，这两个场景都做不到。

依赖：A02。

### M8 · 答得对（A06–A10）

这一层的共同前提：**M7a 之后每一次执行都有 run/step 可回读**，所以"好不好"第一次能被测出来。

**A06 · 评测集：把"跑通"换成"跑得好"（M8 唯一的闸门）**

裁决：50~100 条带判分口径的用例进仓（`eval/`），跑**真模型**（ADR-0011 的口径：mock 只能证明装配成立），
产出可比较的报告。今天 301 条用例证明的是装配成立，没有一条能回答"这版比上版好还是差"。

评分看三件事：**答案是否命中要点 / 工具轨迹是否对 / 有没有越权或遗漏**。只判答案会把"蒙对了"也算通过。

判据：改一句工具描述，报告里的分数**能看到变化**——能观测才谈得上优化；
与 301 条装配用例分开跑、分开看。

依赖：A01（按 run 收工具轨迹）。**必须先于 A07–A10**：没有它，后四张票只能靠肉眼判"好像好了"。

**A07 · 工具检索要能看懂中文**

裁决：`RegexToolIndex` 按空白与标点切词，**对中文整句无效**——`ToolSearch.SYSTEM_SUFFIX` 的注释里
记着实测：query 写"回忆以前说过的话"命中 **0** 个工具，写成关键词才命中。换成一个对中文有解的索引
（二元切分或词典分词二选一，加必要的同义扩展）。

判据：中文整句 query 能命中它该命中的工具；工具从 20 个涨到 100 个，**答案不变差**——
这条正是 ADR-0021 里"领先 2（行为不随工具数量变化）"的验收动作。

依赖：A06。

**A08 · 长 run 的上下文工程**

裁决：压缩可以丢细节，**不能丢"还剩几步没做"和"上一次为什么失败"**。今天 `SessionCompactor`
每轮压缩，这两样都在进去之前就被压没了。

判据：构造一个必然超过压缩阈值的长任务，跑到最后模型仍答得出未完项与上次失败原因；
摘要里带结构化前缀（plan 状态 / 失败记录），而不是一段纯自然语言。

依赖：A03、A06。

**A09 · 失败可诊断，并给一次纠错机会**

裁决：工具失败要把**结构化的原因**回灌模型一次（工具名、错误类别、可修的那部分入参），
然后**只允许一次**重试。这与"自动重试到成功"是两件事——后者已被 ADR-0021 否决，
它的问题不是"重试"，是"不知道什么时候停"。

判据：故意让工具因为参数可修的原因失败 → 模型自救成功一次；连续失败 → 重试一次即停并转成待办，
不出现"一串看不出头的重复调用"。

依赖：A06。

**A10 · 子 Agent 要从父 run 扣预算**

裁决：委派出去的活有自己的 context 隔离（ADR-0012 已裁），但**预算没有自己的**——补上：
子 run 挂 `parent_run_id`，消耗计入父 run 的预算。

判据：一次委派的总消耗不超过明示上限；子 agent 拿不到父的完整历史（用越权用例验证）。

依赖：A04、A06。

### M9 · 同时做很多件（A11–A12）

**A11 · 同一 run 内的并行工具执行**

裁决：模型一轮给出多个**互不依赖**的调用时就并发执行——今天它们是一个接一个跑的。

判据："同时查三个区的销售额"的墙钟 ≈ 一次调用而不是三次；其中出错的那个不影响另外两个。

依赖：A04（预算计数要经得起并发，这条比"并发执行"本身更难写对）。

**A12 · 多 run 调度与配额**

裁决：系统级并发上限 + per-principal 配额 + 等待队列；**超限时明确回"要等多久"**，不要沉默排队。

判据：打满并发之后第 N+1 个请求立刻得到排队位置与预计时长；一个用户的配额不能被自己吃满到
让别人排不到。

依赖：A11、P07（配额的执行对象要有审计可查）。

## Consequences

1. **M7a 的五张与 M7b 的七张是同一个批次的两半**，不是两个优先级。平台线挂不上的理由
   （P04/P05 需要 A02 的 `resume`、P06 需要 A05 的投递目标）写在 ADR-0020 里，这里只记结论：
   **P 不能先于 A01/A02 完成**，理由不是重要程度，是挂不上。
2. **A06 是 M8 唯一的硬闸门**。它之前的所有"改好了"都是自述，之后才有比较。这条决定了
   A07–A10 的顺序不可调换，也决定了 M8 的第一件事写不出漂亮的 demo。
3. **A04 落地之后，ADR-0021 里 `heartbeat` 的重估条件才成立**（另一半是 P07）。这是"待重开"条目
   被引用的第一次，说明那份清单不是墓碑。
4. **代价是每次模型调用多一层状态读写**，以及一份必须长期维护的契约：`step` 的形状一旦对外，
   它就和数据库一样难改。所以 ADR-0016 把"工具循环内部不落 step"写成硬边界，正是为了让
   `step` 的数量级可控——一次 run 里每次工具调用的入参都落一行，这张表就会大到失去作为审计投影的价值
   （ADR-0020 的 P07 把审计定义为 step 的只读投影，那里同理）。
5. **审计 ≠ 评测 ≠ 观测，三件事各自占一个位置**：谁让谁做了什么（P07，合规）／回答好不好
   （A06，质量）／系统现在怎么样（P14，Ops）。任何一次合并都会让其中一件做不深。
6. **每张票的判据都是今天能答出答案的反题**。这句话是这份清单唯一的质量标准：如果一条判据
   现在就已经成立，那它对应的那张票不该存在。
