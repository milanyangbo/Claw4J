# Skill Generator 走五步链路，未人审的脚本不注册

---
status: accepted
date: 2026-10-24
---

让 Agent 能自己产出一个新的 Script Package。1.x 的 `SkillGeneratorSkill` 让模型写出 Python 落盘执行，
并允许脚本自行 `pip install --break-system-packages`，那条链路把宿主机 shell 交给了模型。
新架构里执行位置收口了（ADR-0002），但"能不能产出新能力"这件事本身是本项目"开放扩展"定位
唯一能自证的部分，不能因为原实现危险就整体砍掉。

链路固定为五步：**生成 → 静态检查 → 隔离沙箱自测 → 审计留痕 → 人审通过才注册**。
未人审的脚本拿不到被调用的资格。

## Considered Options

**保留生成能力，只做参数白名单**
否决。白名单挡不住脚本自身的副作用（自动装包、读写任意路径），而白名单本身会成为长期维护负担。

**允许自测通过后自动注册**
否决。"模型写的脚本"和"人认可的能力"是两件事，把第二件省掉，
等于把"这个系统的能力边界是什么"交给一次模型输出的随机性决定。人审必须是人。

**只做静态检查，不执行自测**
否决。静态检查认写法不认意图，一份"看着没问题"的脚本跑不起来是常态；
没有自测，模型只能提交一份自己都没验证过的东西，而人审那一步要替它验证——
那不是人审，那是替模型调试。

**把沙箱做成容器**
否决（判据沿用 ADR-0003 第 ① 类那条）：**CI 的 runner 上没有 Docker 守护进程**，
依赖容器的沙箱在 CI 上就是一串红灯，而跑不起来的沙箱等于没有测试。
代价是网络隔离这一项给不了，见下。

## Consequences

### 五步的顺序就是安全边界的顺序

- **静态检查在落盘之前**：危险代码不该先被写下来再被删掉——那样磁盘上出现过它，而没人会记录。
- **自测在沙箱里，不在暂存区里**：跑的是未审核代码，不能让它改自己待审的那份内容。
  实现上是把候选目录复制成一份临时目录再跑，跑完即删。
- **审计分三步各记一条**，而不是最后补一条：最后补的那条写不出"被挡下的是谁提交的"。
- **人审是最后一步**，代码只读人写下的签字，没有"自动通过"的分支。

### 静态检查是唯一一道机器关，也是最便宜的一环

它是纯函数（不读文件、不看时间、不取随机数），认写法不认意图。
因此"它挡住了什么"可以被一张表钉死：危险清单逐条一个用例，正常脚本另有一组用例
（只测"危险被挡下"的话，一条全拒的实现也会绿）。
它挡的是明着写的那部分——1.x 那次事故就是明着写的。

### 人审比对的不是"有没有签字"，是"审的是哪一版"

审批标记里除了 `status=approved` 与签名人，还要签**脚本摘要**。
同名包被重新生成后摘要变了，旧签字自动作废：否则"审过一次"会变成一张长期通行证，
而人看到的是"我审过"、系统跑的却是另一份内容。

审批目录默认在暂存区**旁边**而不是里面，自测那份副本够不到它——
这是"未审核代码不能给自己签字"的物理保证
（沙箱锁得住入口、参数、工作目录，锁不住脚本体内去写一个绝对路径）。

**摘要比对挡住的只有"还没注册"的那一段**（2026-10-24 修订）。签字生效时若把执行目录
直接指向候选目录，那么"已注册"这个状态会反过来成为一道口子：清单里已经有这个名字，
下次发布时它被跳过（重名注册是失败的），而候选目录里的脚本已经被同名重提整份覆盖——
跑的会是一份没人签过字的脚本，人看到的"我审过"指向的却是另一版。
修法是**上线快照**：签字生效时把候选目录整份复制到发布目录，清单与执行都指向那份副本。
候选目录是模型还能重写的地方，副本不是；新版重新签过字会重新复制一次，
所以快照不是把闸门焊死。code-review（基线 `552414f`）抓到的是这个形状——
它不出现在"有没有签字"这条判据上，只出现在"签字生效之后、文件被改了"这条路径上。

### 第 ② 类沙箱与第 ① 类是两套代码

判据是跑的东西不同：① 跑人审过的包，② 跑模型刚写出来的脚本。
"还没人看过"是这两者之间唯一重要的区别，它决定了默认姿态是"先别信"。
② 给的三样：临时目录（跑完即删）、只有 `PATH`、5 秒上限（比 ① 更紧）。

**给不了的三样**，不拿去当承诺：
- **网络隔离**：纯 Java 起的子进程没有可移植的网络限制手段（`unshare` / `sandbox-exec`
  都是要再起一条命令，而那正是 ADR-0002 禁止的事）。规格里如实写成 `NOT_ISOLATED`
  并写明原因，真正的隔离由部署层的容器网络策略给；联网的脚本在静态检查那一关就被挡了。
- **内存与 CPU 上限**：同上，纯 Java 对子进程没有可移植的限制手段。
- **脚本体内读绝对路径**：进程沙箱锁得住入口与参数，锁不住脚本自己的行为。

### 权限：`draft_script` 与 `run_script` 是两个动作

提交一份草稿不等于能跑脚本。把两个动作合成一个，等于让"能提议的人"顺手拿到了执行权。
生成器登记不到任何业务表，它只写暂存区。

### 装配上的两个约束

- **没有脚本层就没有生成器**（`@ConditionalOnBean(ScriptPackageRegistry.class)`）：
  人审之后的注册目标就是脚本层的清单，没有它，"人签了字"会变成一个没有任何效果、
  却看起来成功的动作——那比"这一层不存在"更难发现。
- **执行留痕要挂在 `ExecutionListeners` 这个容器上**，而不是注入一个 listener：
  脚本层先装配，那会儿还没有审计，按类型注入会得到 null 或容器里唯一那个别的实例，
  而"没接上"的表现是静默的——从此没有任何执行记录。
