# 平台能力一律挂在 run 上，不另开旁路（P01–P19）

---
status: accepted
date: 2026-10-29
---

> **被 0027 部分取代（2026-11-06）**：run 已判定为"一轮的句柄"，不落任何表。
> 本文里"持久 run / step 落库 / 按 runId 续跑 / 审计长在 step 上 / 投递登记表"的部分
> 已被 [ADR-0027](0027-run-is-a-handle-not-an-entity.md) 取代，代码里那两张表也已经删了。
> 正文保留当时的推理——它记录的是"为什么当初这么想"，不是现状。

审批、定时、通道、审计、凭据这些平台能力，**共用 ADR-0016 的 run / step 与 ADR-0018 的投递目标，
各自不许再开一条"自己跑一次 Agent"的路径**。下面 P01–P19 是平台线的全部任务清单，也是平台线唯一的编号源。

## Context

平台要补的东西看起来彼此无关：审批是新的一列权限，定时是一张调度表，企微是一个新通道，
审计是一份留痕。但它们在代码里会撞到同一处——**都要触发一次模型调用**，或者**都要拿到一次模型调用的结果**。

现在的 `AgentPort` 只有"你问、我答、答完结束"这一种形状。于是每一个平台能力落地时都会面对同一个诱惑：
自己拼一个 ChatClient，自己跑一遍工具循环，自己处理异常。这条路**每一个单独看都走得通**，
但加在一起的结果是：

1. **三套预算**。定时任务自己记一次耗时，审批通过后续跑的那一段没人记账，HTTP 入口记的是第三套。
   "这件事一共花了多少"永远答不准。
2. **三条绕过权限模型的路径**。权限之所以能"卡在模型之前"（ADR-0007），是因为所有调用都从同一条
   advisor 链进。谁自己拼 ChatClient，谁就可能漏掉 `AuthorizationAdvisor`。
3. **三套幂等**。ADR-0017 的意图表里查不到旁路发起的那次调用，所以"发邮件"会被重放。
4. **两套执行真相**。审计如果按自己的表记，就会与 execution 侧的 step 对不上，而对不上时没人知道信哪个。

所以这不是一条"架构洁癖"，是一条**成本控制**：一条共用路径的代价是 A01/A02 那两张票，
十九张旁路的总代价是十九套异常处理和四个答不准的问题。

## Considered Options

**各自旁路（每个平台能力自己拼一条执行路径）**
否决。就是上面那四条。再补一条最实际的：它把"分配任务、暂停、预算"这三个概念重新实现若干遍，
而这三件事恰恰是最难写对的。

**引入工作流引擎（Temporal / Camunda / Quarkus 的一个 durable executor）**
否决：

1. ADR-0009 定的是单实例形态。工作流引擎要它自己的 store 与 worker 部署形态，
   为了一张调度表引入一整套运行时，这不是取舍，是换系统。
2. 它的调度顺序同样不受"权限必须在模型之前"这条约束。
3. 定时真正需要的那件事（到点干活 + 多实例不重复）用一行 SQL 就能拿到：
   `@Scheduled(30s)` + `select … for update skip locked`。引引擎换来的只是熟悉感，正确性一点没变。

**挂在 run 上（采纳）**
平台能力的接入方式被压缩成三种动词，全部复用同一条路径：

| 平台要做的事 | 在 run 上的形状 |
| --- | --- |
| 到点干活 | 创建一个 run（`resume` 的兄弟入口），此后与普通提问无差别 |
| 批了才执行 | 把 step 标 `awaiting`、run 标 `suspended`；批准后 `resume(runId)` |
| 答完要找到人 | 按 ADR-0018 的投递目标表推，不在返回值里硬编码"谁问的就回给谁" |

## Decision

任务清单按"能不能交付"分三批，不是按重要程度。**M7b 的七张是一个闭环**：少任何一张，
"批了才执行、执行完能找到人"这条线就不成立。

### M7b · 企业能用（P01–P07，依赖 M7a 的 A01/A02）

**P01 · `ToolPermission` 加第三个分量**

加 `Approval{NONE, REQUIRED}` 并建 `approval_request` 表。全仓只有 3 处构造点（两个工厂 +
`McpEndpoints`），调用点一处都不用改。**默认 `NONE`**，审批只加在真正有副作用的动作上
（`run_script` / `mail_send` / `draft_script`）。

判据：20 个工具的默认放行面一个都不变；标了 `REQUIRED` 的那个动作在无批准记录时被拦。

**P02 · 挂起 run 等审批（不挂线程）**

鉴权通过后，检查是否存在**同参数**的有效批准；没有就 step 标 `awaiting`、run 标 `suspended`，
请求直接返回。批准后由**服务端** `resume(runId)`。

这里推翻的是我先前"不做挂起等审批"的结论。当时的理由（Spring AI 工具调用是同步的，
`ChatClientAgentPort:80` 确实是 `.blockLast()`，挂起占线程）观察正确但结论错了：有了 run 之后，
"停在这一步"是**库里的一个状态**，不是挂着的线程。而"批准后让用户再说一句"这个替代方案，
在 IM 与定时任务里根本走不通——没人会去补那句话，也没定时可补。

核心是**参数指纹**：`sha256(toolName + 按 key 递归排序后的规范化 JSON)`。不排序则模型把参数换个
顺序就是一次"新"请求，审批被绕过。这一条要求做变异验证。注意它与 ADR-0017 的幂等键**形状相似、
口径相反**：幂等键含 `runId` 与 `stepSeq`（要区分每一次执行），审批指纹不含（要跨执行复用，
否则每个新任务都要重批）。混用的事故是双向的。

判据：grant 一次用完即废 + 10 分钟过期；拒绝也落一行并把理由回灌模型。

**P03 · 谁来批**

HTTP 接口 + 飞书交互卡片（走现有长连接）。审批人名单独立于业务角色（`claw4j.approval.approvers`），
**提问人不能批自己的请求**。

**P04 · 定时调度（不引 Quartz / Redis）**

调度表 + `@Scheduled(30s)` 扫描 + `select … for update skip locked` 保证多实例不重复；
失败 3 次自动停用。到点 = **创建一个 run**，其余全部复用。

判据：多实例起两个进程，同一时刻只有一个执行；已经定好的时间点不会因为重启而丢失。

**P05 · `schedule_task` 工具（一次授权，多次执行）**

创建时校验，执行时**重新鉴权**，跑的是**任务主人的 Principal** 而不是系统账号——用系统账号等于给了
一个万能身份；用角色快照则角色被收回后任务还能继续跑。

判据：把创建者的角色删掉，下一次到点必须失败而不是照跑。

**P06 · 企业微信通道**

回调解密 + 去重，复用现有 `InboundDispatcher`。投递走 ADR-0018 的目标表，不退回到"谁问回给谁"。

**P07 · 审计（step 的只读投影，不新建执行表）**

step 已经是执行真相（谁、第几步、调了什么、产出什么）。审计补的是 `actor`（谁发起、谁批的）、
`decision`、参数摘要、留存策略。另建一张表 = 两套真相，对不上时没人知道信哪个。

判据：任一步能答"这次调用是哪次批准的"，批准记录与执行记录一一对应。

### M8 · 能用得久（P08–P16）

**P08 · 凭据句柄**

OpenClaw 的七条企业属性里我们明确差的一条：**凭据有主**。现在 MCP 的 env 与模型 key 都是明文配置，
脚本只给 PATH（那一条是对的）。改成 secret handle：配置项里只写句柄名，出口前替换成真值，
模型在任何路径上看到的都是句柄。

判据：在模型的入参与工具返回值里搜不到任何真 key；日志与审计记录里也只有句柄。

**P09 · 审批策略升级（allow / deny / ask + tools profile）**

现在的权限是纯**数据轴**（表 × 动作），表达不了"这个部署只做消息、不许跑 shell"——不给 `run_script`
会把"读消息"一起卡住。补一条**能力轴**：`minimal / messaging / coding / full` 四档 profile +
按工具的 allow / deny 分组。这对应 OpenClaw 的 `tools.profile` 与 `tools.exec.mode`。

判据：切到 `messaging` 档，`run_script` 与 `draft_script` 不在工具清单里，其余不受影响。

**P10 · 知识库检索（必须独立的表）**

向量 + 关键词混合，结果带出处。**不能复用语义缓存那张表**：V4 的 `vector(1024)` 存的是问答对，
命中直接返回历史回答；文档块进同一张表，最坏情况是把一段文档当成"有人问过"的答案吐出来。
另外这里推翻我先前"一张表三个使用面"的说法——工具检索要 precision（20~100 个候选里 top-5 必须对），
文档检索要 recall（一段话里找依据）。共享 embedding 供应商与 pgvector 实例即可，
**表与阈值必须分开**，否则两边参数互相拉扯，各自都不好用。

判据（写在票里的前置限制）：Postgres 默认分词器对中文**失效**——`to_tsvector('simple', 中文)`
切不出词。这条票开工前要先定 pg_bigm、应用侧抽词、还是外部检索，否则"混合检索"名不副实。

> **2026-11-09 修订：混合检索撤回，只做向量。**
>
> 换成框架的 `VectorStore`（`PgVectorStore`）之后，关键词那一路没有对应物——
> Spring AI 只有相似度检索，混合检索是 OpenClaw 自己的实现（SQLite FTS + BLOB 向量）。
> 所以上一段那个前置限制（中文分词走哪条路）**随通道一起作废**，`bigrams` 列、
> `tsv` 生成列、GIN 索引与 RRF 融合全部删除。
>
> 代价正面记：`SKU-2024` 这类"字面精确、语义无关"的查询会退化。补回来只能是再写一条
> 全文路径——那就是这次删掉的东西。表也不再是我们设计的两张（`document` / `chunk`），
> 而是框架建的 `vector_store`，只留一张照 OpenClaw `memory_index_sources` 的文件账
> （`claw4j_rag.source`）用来跳过没变的文件。细节见 `P10` 票面的「方案变更」一节。

> **2026-11-09 晚，第三次修订：混合检索与重排加回来，但落在框架的接口上。**
>
> 上一段撤回的依据是"官方没有全文检索，补回来就得自己造一套"。这条依据只在
> "自己造 API"这个前提下成立。框架的 RAG 模块其实留了三个槽位，且都只有一个空壳或单路实现：
>
> | 槽位 | 官方 | 我们填 |
> | --- | --- | --- |
> | `DocumentRetriever` | 只有 `VectorStoreDocumentRetriever` | `KeywordDocumentRetriever`（全文那一路） |
> | `DocumentJoiner` | `ConcatenationDocumentJoiner` 按 score 排，两路分数不可比 | `ReciprocalRankFusionJoiner`（只看排名） |
> | `DocumentPostProcessor` | **零实现** | `RerankingDocumentPostProcessor`（专用 reranker：通义 `qwen3-rerank`） |
>
> 编排本身也用官方的 `RetrievalAugmentationAdvisor`（2026-11-09 用户裁决：官方有的能力就用，
> 冲突改我们这边）。它有三处默认行为必须改：默认模板要求"只按上下文回答"（会压住人格与工具）、
> `allowEmptyContext` 默认 false（闲聊全部回"无法回答"）、`before()` 没有 try/catch
> （检索抛异常即整轮失败）。前两处传自定义 `promptTemplate` 与 `allowEmptyContext(true)` 解决，
> 第三处接受——"库挂了"不该伪装成"文档没写"。原来那个 `searchDocs` 工具随之删除：
> advisor 每轮已检索，留工具就是每轮两次。
>
> 所以这次新增的是一份"官方接口的实现"，不是一份自有 API——与上一节删掉的
> `RankFusion` / 自有检索接口不是一回事。
>
> 全文那一路在 Postgres 上的形态，照 OpenClaw 的 FTS5 trigram 走：**子串匹配**
> （`content ilike '%q%'` + GIN trgm 索引），不是分词、也不是 `similarity()` 打分。
> 实测 `similarity('退货政策', 一段确实含这四个字的长文本)` 返回 **0**，分母是块长；
> `word_similarity` 依赖词边界，中文没有空格。所以那一路只产顺序，不产分数——
> RRF 正好只要顺序。
>
> **rerank：对齐到端点，不对齐到用法**（2026-11-09 更正）。OpenClaw **有** rerank：
> `extensions/rerank/` 是随包插件（默认启用），`docs/providers/rerank.md` 把任何 `/rerank`
> 端点接成 Decision model；`docs/plugins/knowledge/memory-provider.md:175` 推荐
> `gte-reranker-modernbert-base` 当**召回闸门**的判定模型。它是一对一判定（这段资料值不值得
> 进上下文），我们是列表重排（10 条候选排序 + 截断），端点形状一样、用法不同。
> 官方 2.0.2 仍然没有 rerank 类型（BOM 逐个 jar 扫描，连 `RerankModel` 接口都不存在），
> 所以直连通义的 `qwen3-rerank`（OpenAI 兼容端点，复用现有 `QWEN_API_KEY`）。
> 落在 `DocumentPostProcessor`；这是本项目唯一一处"官方没有、直接调 HTTP"的能力，
> 退场条件是框架出 rerank 模块。实测三段候选的分数是 0.657 / 0.588 / 0.281——
> 真正讲政策的那段排在第一，分差够截断。
>
> 细节、实测数据、语料与判据见 `docs/design/knowledge-retrieval.md` 与 `P10a` / `P10b` 票面
> （2026-11-09 拆票：混合检索一张、重排一张，后者能单独关掉、单独回退）。
>
> 编号口径照旧：**不属于新能力，就不给新号**。这两张是 P10 的同一次变更拆出来的，记作
> `P10a` / `P10b`；P17–P19 已经被 M9 占着，往下续号会撞上沙箱加固那三张。
>
> **2026-11-09 再追加一次修订：分块改成句子级语义断点，另立 ADR-0028。**
>
> 分块原来只是一件事——`TokenTextSplitter(800)`。用户要求"除了按 token，也要按语义方式切割；
> 基于句子语义差异，转折词或话题跃迁触发；先看有没有开源实现，不要自己想"。于是它有了独立裁决：
> **算法照 LangChain `SemanticChunker`**（句子 → `buffer_size=1` 的句子组 → 余弦距离 →
> 第 95 百分位断点 → `min_chunk_size` 合小块），只换中文断句正则、并叠加一条"句首转折词断块"
> 的用户规则；**字数只在块超 `chunk-size` 时出现一次**。切块身份落在一张 KV 表
> `claw4j_rag.index_meta`（照 OpenClaw 的 `memory_index_meta`，不是给文件行加列），
> 身份变了触发全量重建。
> 论证、代价与退场条件都在 **ADR-0028**，执行票是 `P10c`。这一段只留指针，不在这里重复。

**P11 · 反向 MCP server（把自己暴露出去）**

`spring-ai-starter-mcp-server` 本地已有 2.0.2 可直接用。补齐的是 OpenClaw `mcp serve` 那种反向用法：
让 Claude Code / Codex 把我们的能力当 MCP 工具用。

**P12 / P13 · 钉钉 / Slack 通道**

扩展点已经就绪，成本线性。这是企业落地的第一道门，但排在 M8 而不是 M7b——通道越多，
答错传得越广，所以要等 M8 的评测与自检先在。

**P14 · 可观测与 OTel 导出**

现在只有 Micrometer 的 `claw4j.tool.calls{tool,outcome}`，以及独立的运维端口。补 trace 导出
（一条 run 能连到它的每个 step 与每次工具调用）。注意审计 ≠ 评测 ≠ 观测：审计是"谁让谁做了什么"
（合规、落库可查），评测是"这个回答好不好"（质量、跑真值集，见 A06），观测是"现在系统怎么样"
（Ops、可聚合）。三件事合并会让每一件都做不深。

**P15 · 多 agent 配置（tools profile + 提示词分层，合并票）**

这两个原本是两张票，合并是因为它们其实是同一件事：分开会长出两套"人设"配置。要的是
角色 / 部门口径 / 技能 / 时间上下文 / 工具策略可组合、per-agent 可覆盖。

判据：同一份代码两次部署只改配置，一个变销售助手、一个变运维助手。

**P16 · 插件版本契约**

OpenClaw 有 ClawHub 与版本兼容校验；我们插件机制是 Boot 自动配置，既无分发也无版本口径。
这是 README「还没做的」里的第一条真限制。要做的是**契约**（plugin 声明它依赖的 core 版本区间），
**不做市场**。

### M9 · 规模（P17–P19）

**P17 · 脚本沙箱加固（真正的隔离边界）**

现在 `SandboxPolicy` 只有四条约束：PATH-only env、30s、非 root、限 cwd。脚本与宿主**同 OS 用户、
同网络、同文件系统**——这是七条企业属性里我们唯一明确 ✗ 的一条：**有约束，无隔离**。
加容器级限额（network=none、只读根 FS、内存/CPU 限额、临时 workdir）。

**P18 · `doctor` 自检**

照 OpenClaw `doctor` 的形状：检查 key 有效性、迁移是否最新、外部 server 是否连得上、
目录是否存在。

**P19 · WebSocket 传输**

HTTP+SSE 之外的第二条传输。对应 OpenClaw Gateway 协议的一小部分，但**不做它的控制面**。

## Consequences

1. **M7b 是闭环，不是清单**。P01→P02→P03 + P01→P07 是硬依赖；P04/P05 挂在 A02 的 `resume` 上；
   P06 挂在 A05 的投递目标上。所以 **M7a 的五张必须先于 M7b 全部完成**——理由不是重要，是挂不上。
2. **对每个平台能力都多了一道约束**：它不许直接碰 ChatClient。这是这份 ADR 唯一真正的限制，
   也是它唯一的收益。
3. **`resume(runId)` 会成为系统里最热的一个入口**。审批、定时、故障恢复、CI 回调全部走它，
   它的错误处理与幂等要按 ADR-0017 的标准写，而不是按"内部方法"写。
4. **审计落在 step 的投影上，意味着 step 表的留存策略决定了审计能查多久**。
   这两个需求必须一起提，不能一个留 7 天一个要求查半年。
5. **明确不做的事写在 ADR-0021**，不在这里重复。
