# 评审：按什么顺序查，什么不该报

给评审的那一方（人或 agent）。`code-review` 会开两条互不相干的轴——**规范**（这个仓库怎么写代码）
与**规格**（这是不是忠实地实现了发起它的那张票），各出一份报告、不合并、不重排：
一条改动可以完美符合规范却做错了事，也可以精确做对了事却破坏约定，合成一个结论就会互相盖掉。

## 一、先认领规格，再动眼

规格在 `.scratch/<effort>/spec.md`（一轮工作的目标）与 `.scratch/<effort>/issues/NN-*.md`（一张票），
约定见 `issue-tracker.md`。

**提交信息里没有指向票的 trailer 时，不要凭提交标题猜。** 按改动内容去票目录里找，
找不到就问；猜错的代价是整份规格报告都在审一件没发生过的事。用户当场给的指令也算规格，
但要在报告里写明出处是"哪一句原话"，不能当票去引。

## 二、文档承诺与代码一致——这个仓库的第一大类缺陷

判据一句话：**每一句带数字、带"只有 / 唯一 / 必填 / 没有…的版本 / 验了…"的断言，都要去代码里数一遍。**
近两轮评审挑出的十处里，七处是这一类，且都不是打字错误，是写着写着就比代码走得远了：

- javadoc 说"这几条 SQL 都真跑过、`entities varchar(64)` 与十六进制正好卡满"，实际只断言了
  `embedding` 的维度，签名还是五个字符的串——**假绿**，比假红贵。
- 设计文档说"上下文必填，签名上没有不带上下文的版本"，而接口上就有两条少传的。
- 用例的 javadoc 说"只留两条"，方法已经五条。
- 代码注释说"断言的是容器里那个 bean"，下一行是 `new AgentAutoConfiguration()`。

查法不是通读：把断言里的名词挑出来，用 Grep 落到具体那一行。落不到就记一条。

## 三、测试：去 `testing.md`，别在这里重抄

四条判据、组织界限、好坏测试的形状全在那份里。评审只多记两条：

- 上限（每模块 ≤10 文件、每文件 ≤20 方法）由 `verify.sh` 计数拦着，评审不必再数。
- 上面第二类"假绿"要**变异**才验得出来：把注释里点名的每一处各改坏一次，红不了的那处就是没验。

## 四、回查 `guardrails.md`

列在那张表里的偏差不是缺陷，评审该查的是"补偿手段够不够"。反过来，**文档说一套、代码做一套**
仍然要报——记账的是偏差本身，不是自述与实现的分歧。

## 不该报的

- **没有 CI、没有 pre-commit hook**：有意为之，入口只有 `./scripts/verify.sh`。别再提第二遍。
- 工具已经管的：编译器、ArchUnit 边界、JaCoCo 覆盖率、文件数与方法数。
- 已有更深的用例覆盖到的浅层断言。

## 报告纪律

- 每条给**文件:行**（或方法名）+ 依据原文（截短可以，转述不行）+ 建议改法。
- 分清**硬违规**（引得出文件里的原句）与**判断题**（基线坏味道、风格一致性）；判断题就标成判断。
- 依据必须是自己读到的。从注释或文档转述来的结论，先去找原文——上一轮子代理报的十条里三条不成立，
  三种典型：注释就写在下方的取舍被当缺陷、用户的当场指令被当规格蔓延、机制已由一条 order 断言守着
  却被报成"没测"。**复核别人的结论也是评审的活。**
- 判断"这是缺陷"之前先验一次（单跑那个测试类、写一行断言跑一遍），判据见 `pitfalls.md` 十四。
