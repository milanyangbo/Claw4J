# 代码注释怎么写

一句话：注释是写给下一个读这个文件的人，不是写给读者做说服工作的。

结构照 Google Java Style（2025-04-26 版）第 7 章与 4.8.6；语言按 `humanizer-zh` 的判据过一遍。

## 一、硬格式（Google Java Style，必须遵守）

- **7.1.1 一般形式**：多行用 `/** ... */`；只有整块（含注释标记）能放进一行、且不带块标签时，才用单行。
- **7.1.2 段落**：段与段之间、块标签组之前，留一行只有对齐 `*` 的空行；除第一段外，每段正文前紧接 `<p>`，其后不加空格。
- **7.1.3 块标签**：按 `@param`、`@return`、`@throws`、`@deprecated` 的顺序出现；这四种标签**不许空描述**；一行放不下时，续行从 `@` 起再缩进 4 个空格。
- **7.2 摘要片段**：每个 Javadoc 以一句摘要开头。它是名词短语或动词短语，不是完整句子——不以「本方法返回……」开头，也不写成祈使句。首字母大写、句末带标点。
- **7.3 用在哪**：public 类及其 public / protected 成员必须有；不言自明的 getter 可省；覆写方法可省。
- **4.8.6 实现注释**：与所在代码同缩进；多行 `/* */` 的后续行 `*` 对齐；不用星号画框。TODO 写成 `// TODO: 出处 - 说明`，出处指到票或缺陷，不指人。

## 二、本项目追加（Google 不管、但我们踩过的）

1. **Javadoc 里禁 Markdown**。`**加粗**`、`##`、`- 列表`、反引号在 Javadoc 里不渲染，只会原样显示。用 `<b>`、`<p>`、`<ul><li>`、`{@code 代码}`、`{@link 类型}`。
2. **一段一意，正文不超过 4 行**。类注释正文不超过 40 行。超了说明这些话该在 ADR 或设计文档里，代码里留一句指针（「取舍见 docs/adr/00xx」）。
3. **不用第一人称**。「我们」「我」一律去掉。也不写「不藏」「说白了」「说实话」这类口气，不用感叹号。
4. **不复述代码**。行内注释只写三样：为什么这么做、为什么不是另一种写法、边界在哪。`i++ // 自增` 这种删掉。
5. **不写变更史**。「原来是 X，后来改成 Y」不进注释，API 兼容说明除外。
6. **引用外部系统必须可核对**。写「与 OpenClaw 对齐」要带 `文件:行` 或配置项名；核不到出处，就删掉这个声称，只写代码本身在做什么。
7. **术语**：中文说明加英文原文，原文不译（session、turn、approval、chunk、rerank、compaction……）。同一概念全仓库只用一个词，对照根级 `GLOSSARY.md`。

## 三、humanizer-zh 在注释里的六个落点

| 毛病 | 注释里的样子 | 改法 |
| --- | --- | --- |
| 铺垫代替陈述 | 「这不仅是一层缓存，更是……」 | 直接说这层缓存做什么 |
| 强凑三段式 | 「快、稳、可维护」 | 只说有依据的那一条 |
| 意义拔高 | 「至关重要」「彰显了设计的严谨」 | 删掉，事实留着 |
| 粗体当装饰 | 每段开头 `<p><b>小标题</b>：` | 段首短句即可，粗体只在真需要跳读时用 |
| 层叠的「的」 | 「这是一个十亿参数的开源小模型的微调的完整方案」 | 拆成两句 |
| 套话收尾 | 「综上，该设计具备良好的扩展性」 | 删掉 |

判据不是词表。一个词命中不代表要改；没有问题的句子原样留着，别为了改而改。

## 四、改前 / 改后

**类注释**

```java
// 改前：整段是加粗小标题 + 辩论，Markdown 不会渲染
/**
 * 两路融合：**加权求和**，矢量分 0.7 + 全文分 0.3。
 * <p><b>权重是与 OpenClaw 对齐的固定值</b>……**不做成配置**——多一个旋钮，
 * 只会让"结果为什么变了"多一个可能的答案。
 */
```

```java
// 改后：摘要一句，其余按事实分段，粗体只留一处
/**
 * 把向量与全文两路命中按 0.7 / 0.3 加权合并成一个列表。
 *
 * <p>权重是固定值，与 OpenClaw 的 {@code hybrid.vectorWeight} / {@code textWeight} 一致
 * （{@code src/agents/memory-search.ts:165}）。不做成配置：它那边对应的配置项已经撤掉。
 *
 * <p>全文那路的分是命中次数，先按本次查询的最大值归一（{@code hits / maxHits}）再乘 0.3，
 * 两路才都在 0~1。融合分写回 {@link Document#getScore()}，因为下游官方
 * {@code ConcatenationDocumentJoiner} 按这个分排序。
 *
 * <p>不截断：截断只发生在 {@link TopKDocumentPostProcessor}。代价是只被全文命中的块最多
 * 0.3 分，排序上会输给余弦高于 0.43 的向量命中。
 */
```

**方法注释**

```java
// 改前：摘要里塞了契约，正文在解释为什么不那样写
/**
 * 两路融合。**顺序是契约**：第 0 路向量（分是余弦），第 1 路全文（分是命中次数）。
 * <p>用显式的两参数版本而不是靠 {@code Map} 猜路别：猜错一次就是静默地把余弦当命中次数用。
 * @param vectorHits  向量那一路的命中，分是余弦相似度
 */
```

```java
// 改后：摘要说做什么，契约进正文，标签补齐
/**
 * 按 {@code vectorHits}、{@code keywordHits} 的顺序融合两路命中。
 *
 * <p>参数顺序就是路别。{@link DocumentJoiner#join} 的 {@code Map} 签名不带路别信息，
 * 传反了会把余弦当命中次数用，而且不报错。
 *
 * @param vectorHits 向量命中，分是余弦（0~1）
 * @param keywordHits 全文命中，分是命中次数
 * @return 融合后的列表，按融合分降序
 */
```

**行内注释**

## 五、改完怎么算完成

- 只动注释行，代码、字符串、注解、缩进都不动。
- `./scripts/verify.sh` 全绿。
- Javadoc 里搜不到 `**`、行首 `- `、反引号。
- 每一处「与 X 对齐」都能点到 `文件:行` 或配置项名。
- 对齐上发现疑点，不在这里改代码，记进 `docs/reviews/` 的清单。
