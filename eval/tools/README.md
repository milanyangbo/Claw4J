# 工具检索评测（票 09 / 票 12）

回答一个问题：**同一句人话，索引的前 k 里有没有那个工具。**
不回答"模型拿到候选后选不选对"——那是 BFCL 那一层，要真模型与多轮，另一张票。

## 两条路，分工不同

| | 谁算 | 怎么跑 | 用来干什么 |
| --- | --- | --- | --- |
| **权威口径** | `ir_measures`（TREC 标准实现） | `./eval/tools/run.sh` | 对外说数、跟公开结果对齐、钉基线 |
| 快速反馈 | 票 09 的 `ToolRetrievalEval` | `./mvnw -o -Peval -pl claw4j-eval -am test -Dtest=ToolRetrievalSnapshotTest` | 改索引时先看一眼，不装 Python |

两条路**分母不同**，所以 `R@1` 会有差：第三方只算 qrels 里那 36 题（有 gold 的），自研算全部
38 题（`no-search` 那两题按"零候选 = 命中"计入，其中一题通过）。实测 `regex` 自研 0.079 /
第三方 0.056，差的就是那一题——不是算错。`R@5` 自研 0.342 / 第三方 0.333。

2026-11-26 之前这条写着"自研 0.150 / 第三方 0.111"：那个 0.150 是**自研实现有 bug 时的数**。
见下面「自研指标修过的那个 bug」。

## 跑（权威口径）

```bash
./eval/tools/run.sh                        # 导出 + 算分，全部 5 档
./eval/tools/run.sh --configs hybrid-0.0   # 只跑一档
./eval/tools/run.sh --from-report          # 不重跑导出，只按当前门槛重算
./eval/tools/run.sh --cross-check          # 加做两套指标的一致性校验
./eval/tools/run.sh --update-baseline      # 确认改好了，把分数钉成新基线
```

- 只有一条环境变量：`QWEN_API_KEY`（hybrid 三档要真 embedding）。**没有 judge、不花钱**。
- 退出码：`0` 全过；`1` 有回归；`2` 环境没搭起来（缺 key / 缺依赖 / **缺基线**）。
- 产物在 `eval/tools/reports/`，**不入库**；`baseline.json` 入库——一个是产物，一个是标准。

## 产物

| 文件 | 谁写 | 内容 |
| --- | --- | --- |
| `reports/qrels.txt` | Java `ToolRetrievalExportTest` | `<qid> 0 <tool> 1`，36 行（每题一个 gold） |
| `reports/<config>.run` | 同上 | TREC run：`qid Q0 docno rank score runid`，rank 就是检索给的顺序 |
| `reports/no-search.jsonl` | 同上 | `{"qid":…, "returned":n, "tools":[…]}`，两行 |
| `reports/score.json` | `run_ir.py` | 机器读的分数 |
| `reports/report.md` | `run_ir.py` | 人读的报告 + 判定 |
| `baseline.json` | `run_ir.py --update-baseline` | 上次被接受的版本 |

**`no-search` 为什么不进 qrels**：TREC 表达不了"期望零候选"。qrels 里没有相关文档的 qid 会被
跳过或记 0，而这两题的判据是"给了候选才算错"。所以它们单独一份、单独判。

## 列

| 列 | 意思 |
| --- | --- |
| `R@k` | 前 k 名里有 gold 工具的比例。**每题只标一个 gold**，所以与"命中任一"等价 |
| `RR` | 第一个 gold 名次的倒数均值（= MRR）；没命中记 0 |
| `nDCG@10` | 与 ToolRet（ACL 2025）同口径，方便跟公开数字对话 |

`no-search` 那两道按**零候选率**单独报：给了候选就是噪声，明细（哪几题、给了谁）每轮都打印。

**加多 gold 的题之前注意**：`ir_measures` 的 `R@k` 是"覆盖比例"，票 09 的自研是"命中任一"。
现在每题一个 gold 所以等价；一加多 gold，两边就会分道扬镳，到时要选一个口径并改另一边的注释。

## 门槛：两层，不是 RAG 侧的三层

- **回归门**：每档 `R@5` 不低于 `baseline.json` 减 `TOLERANCE`（0.05，一格题的量级）。
- **零候选率也是回归门**：基线记当前值，掉下去才失败。**不是"必须 1.0"**——当前 `regex`
  对「谢谢」就会给候选（`tools-chitchat-thanks`），拿 1.0 当门槛等于假装它已经修好。

没有第三层「分档（差/良/好）」：RAG 侧有那一层是因为 judge 会漂、需要相对判断；这边全是确定性
指标，分档只会把当前噪声固化成标准。

## 一致性自检

`--cross-check` 用票 09 的公式重算 `R@5` / `RR`，与 `ir_measures` 逐档比，差 > 1e-9 就打印
两边数字并退出 1。两套实现之间对不上时，第一个问题是"信谁"——这条把它变成当场可见的报错。

## 2026-11-26 的基线（19 个工具、38 条题，36 条进指标）

```
配置                  R@1      R@3      R@5       RR  nDCG@10
hybrid-0.0        0.333    0.556    0.722    0.480    0.540
hybrid-0.5        0.167    0.444    0.611    0.331    0.400
hybrid-1.0        0.056    0.278    0.333    0.165    0.208
lucene            0.139    0.250    0.361    0.218    0.253
regex             0.056    0.278    0.333    0.165    0.208
no-search 零候选率 0.500（1/2；给了候选：tools-chitchat-thanks）
```

**这一版题库换过（票 13），旧数字（20 题那版）已作废，不要跨版本比。** 换了两处：

1. `zh-en` 从 5 题加到 20 题，并且移走了 3 道"gold 的描述其实是中文"的题（`systemStatus` /
   `recall_session` / `intent`，归 `business`）、删掉 1 道死题（`MemoryView` 不在目录里）。
2. `business` 里 4 道指向 `mail_*` / `github_*` 的题**在评测上下文里也是死题**（那些工具随 MCP
   装配，评测没接 MCP），换成指向现有工具的四种问法。

**分档看这一张**（`zh-en` 是全部 20 题的那一档，第三方口径）：

```
配置          zh-en R@1  zh-en R@5  zh-en RR      business R@5
hybrid-0.0       0.200      0.600     0.352          0.917
hybrid-0.5       0.100      0.500     0.212          0.833
hybrid-1.0       0.000      0.100     0.033          0.750
lucene           0.000      0.200     0.070          0.750
regex            0.000      0.100     0.033          0.750
```

`zh-en` 这一档终于能说话了：**关键字那一路几乎全空**（R@5 0.100，等于 20 题里中 2 题），纯向量
0.600。旧题库里这一档是 0.60 对 0.20，看着"差三倍"；换成 20 道真正的"中文问英文描述"之后是
**0.60 对 0.10**，差别比旧数字大得多——因为旧的那 5 道里有 3 道在测中文问中文。

分档表的算法：按 `gold.yaml` 的分类把 qrels 与 run 各切一份，再喂 `ir_measures.calc_aggregate`
（`run_ir.py` 只出总表，分档是手算的，命令见票 13 的收票记录）。

**向量档的 `R@1` / `R@3` 会漂，`R@5` 不会**：同一份代码连跑三次，`hybrid-0.0` 的 `R@1` 是
0.333 / 0.389 / 0.389、`R@3` 是 0.556 / 0.500 / 0.444，而 **`R@5` 三次都是 0.667**（那还是旧题库）。

根因是**近分并列**，不是 embedding 不稳（同一句连调三次，1024 维逐位相同，已验）：
`intent` / `list_schedules` / `Task` / `recall_session` 这一簇工具的描述在向量空间里几乎同一个点，
而框架的 `VectorToolIndex` 用 `ORDER BY embedding <=> ?` 取 top-k，**没有 tie-breaker**——
PostgreSQL 对等值行不做顺序保证。所以两次跑的差异只发生在这一簇内部：相邻名次互换，
`R@5` 的集合不变，`MRR` / `nDCG` 在第 2 位小数上抖（实测 0.488→0.481、0.532→0.527）。

判定只盯 `R@5` 就是这个原因。`R@1` / `R@3` / `RR` / `nDCG@10` 是观测项，
**不要拿它们做前后对比的判据**——那个精度这次测量达不到。要修只有一条路：自己实现向量检索、
在 `ORDER BY` 后面加 `, tool_name`，为一个第 2 位小数的抖动改掉框架实现，不划算。

三条读法：

1. **`hybrid-1.0` 与 `regex` 逐格相同**——权重 1 真的等于纯关键字，那张"对照"是真对照。
2. **纯向量最好**：`R@5` 0.722，是关键字那一路的两倍多；`nDCG@10` 0.540 vs 0.208。
3. **默认 0.5 被关键字那一路拖回中间**：0.611。降权还是换描述，都得先有这张表。

**样本仍小**（38 条、19 个工具），所以这不是"结论"，是基线：往后每改一次检索跑同一份题对比。

## 自研指标修过的那个 bug（2026-11-26）

`ToolRetrievalEval` 原来把"一个候选都没给"直接当命中（`noCandidate || within(k)`），**不看这题
该不该有候选**。于是最坏的失效拿满分：`regex` 下 20 道 `zh-en` 里有 3 道返回空，自研记成
R@1 0.150，而第三方口径同一批是 0.000。

错的方向特别坏：它奖励"查不到任何东西"，并且只在坏的时候生效——好配置上看不出来。现在
`matched` 先看 `goldEmpty`，用例是 `ToolGoldTest#emptyResultIsNotAHit`（断言空手时 R@1 = 0）。

## 中文化（票 11）的三次测量

`zh-description` **只喂向量那一路**（`index=vector|hybrid`），关键字那一路读原文。三次测量都在
同一份题上，变量一次只改一个：

| 哪一版 | 题目 | 关键字那一路 | 向量那一侧 |
| --- | --- | --- | --- |
| 早：两翼都读中文 | 20 题 | `regex` R@1 0.15 → **0.10** | `zh-en` 0.60 → 0.80 |
| 中：只喂向量 | 20 题 | 0.15 → 0.15（不再降） | `zh-en` 逐格相同（**没复现**） |
| 晚：只喂向量 | **38 题** | 0.056 → 0.056（不受影响，符合设计） | `zh-en` **0.200 → 0.250~0.400** |

### 晚这一次的数（加厚题库之后，各跑三遍）

```
hybrid-0.0  zh-en       R@1              R@5              RR
关（三次）          0.200 0.200 0.200   0.600 0.600 0.600  0.352 0.341 0.348
开（三次）          0.350 0.250 0.400   0.750 0.800 0.750  0.495 0.444 0.520
```

- **收益现在测得到**：`R@5` 从 0.600 到 0.75~0.80（3~4 格），远在 0.05 的容差之外。`R@1` 同向但更抖。
- **收益只落在英文描述的工具上**：同一轮里 `base`（Read/Grep/Glob/Bash/WebFetch，描述全英文）
  的 `R@1` 从 0.000 到 0.250；`business`（中文描述）纹丝不动（0.750 / 0.917）。
- **杂音来自翻译本身**：开的那一侧三次跑出三个不同的 `R@1`——因为**翻译不落表**，每个进程重新译
  一次，译文措辞不同、embedding 跟着不同。关的那一侧是逐位可复现的。
- 所以"上一次说没收益"的结论**只对 20 题那版题库成立**：那 5 道 `zh-en` 里有 3 道在测中文问中文，
  中文化对它们本来就不可能有效果。

**判定**：`index=vector|hybrid` 时建议打开；默认仍关，因为默认 `index=regex`，而它在那条路上
一次都不生效（关键字翼读原文，模型看到的清单也是原文）。要让它可复现，得把译文落表（票 11 的
V9 缺口）——现在每跑一次评测就重新译一遍，这也是 `R@1` 观测不稳的来源。
