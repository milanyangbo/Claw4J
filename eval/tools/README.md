# 工具评测（两把尺子，量两件不同的事）

两个目录，各有各的脚本、依赖、基线与报告。

| 目录 | 被测对象 | 候选从哪来 | 入口 | 花不花钱 |
| --- | --- | --- | --- | --- |
| `retrieval/` | **我们的检索层**（`ToolIndex`，Java） | 我们自己的 58 个工具 | `./eval/tools/retrieval/run.sh` | 不花（只算 embedding） |
| `bfcl/` | **模型 + 我们的提示词**（DeepSeek） | BFCL 题库自带的 1 个函数 | `./eval/tools/bfcl/run.sh` | 花（真模型） |

`retrieval/` 是产品指标：一句话进来，前 5 个候选里有没有那个工具。
`bfcl/` **不是产品指标**，它是一个**提示词实验台**：同一批题、同一个模型、同一套判据，
只改 system 里的那几行，看 `irrelevance` 与 `simple_python` 怎么动。验出来的提示词
回灌到 `ToolSearch.SYSTEM_SUFFIX`（见票 30）。

## 为什么删了 `live/`

票 28 曾经建过第三个目录，做的是「我们的检索给候选 + 我们的提示词 + 模型决策」。
它拿 BFCL 的题和 BFCL 的判据，套在一套 BFCL 不认识的工具上——**定位错了，不是实现错了**：

- 题目：`irrelevance_103` 问「纽约现在几点」，BFCL 给它配的函数是 `weather_forecast.get`；
- 判据：`eval_runner.py:290` 的 `success = not contain_func_call`，只看有没有解出调用；
- 我们把候选换成自己的 58 个工具之后，`world_clock` 就在里面，调它**是对的**，判据判它错。

同一道题、同一个模型，换掉 tools 之后正确答案就反了，判据没有跟着变。那个数（`bfcl` 81.25%）
因此没有产品意义，留着只会被当成指标用。2026-11-27 整个目录删除，票 30 记着原因。

要把「我们的候选 + 我们的模型」这件事量准，缺的不是一个目录，是**一份我们自己的标注**
（240 句里哪些我们真能做、该调哪个工具）。那是另一张票，没做之前不建目录。

## 为什么要分开

- **依赖不同**：检索层只要 `ir-measures`；选择层要整套 `bfcl-eval`（含 torch、faiss），
  而且**必须 Python 3.10–3.12**（它把 numpy 锁在 1.26.4，3.13 装不上）。
  挤在一个 venv 里，两边都被对方的最严约束卡住。
- **成本与频率不同**：检索层零成本、改索引就能跑；选择层要真模型、要钱。合在一起，
  "顺手跑一下"就变成了"顺手花一块钱"。
- **口径不同**：检索层的分数是集合运算（确定性）；选择层的分数来自模型的决策（会漂、
  要容差）。两种数放在同一个报告里，读的人分不清哪个能当判据。

## 共用的东西

- 都不进 CI：`retrieval/` 要 Testcontainers 起库、要 embedding key；`bfcl/` 要真模型。
  两边都是手动跑，与 `-Peval` 同一条规矩。
- 都是 `baseline.json` 入库、产物（`reports/`、`result/`、`score/`）不入库——一个是标准，
  一个是产物。
- 都遵守同一条退出码口径：`0` 达标、`1` 有不达标或回归项、`2` 环境没搭起来
  （缺 key / 缺依赖 / 缺基线）。
- 都判两根门（票 19）：**绝对门**回答「够不够好」（与基线无关的合格水位），**回归门**回答
  「有没有变差」。只判回归门等于拿上次自己的分数当合格线，那是自证清白。各自的线写在
  子目录 README 的「门槛」一节，改动要连依据一起写。
