# 工具评测（三把尺子，各量一段）

三个目录，各有各的脚本、依赖、基线与报告。**它们不是"同一件事的三个阶段"**——
2026-11-27 之后才齐，之前那版只有前两段：

| 目录 | 被测对象 | 候选从哪来 | 入口 | 花不花钱 |
| --- | --- | --- | --- | --- |
| `retrieval/` | **我们的检索层**（`ToolIndex`，Java） | 我们自己的 58 个工具 | `./eval/tools/retrieval/run.sh` | 不花（只算 embedding） |
| `bfcl/` | **模型本身**（DeepSeek） | BFCL 题库自带的 1 个函数 | `./eval/tools/bfcl/run.sh` | 花（真模型） |
| `live/` | **检索 + 决策串起来**（票 28） | 我们的检索给的 top5 | `./eval/tools/live/run.sh` | 花（真模型） |

区别在第三列：`bfcl/` 的候选是 BFCL 每题自带的那一个（240 道 irrelevance 每题只给 1 个函数），
跟我们没有任何数据流连接；`live/` 的候选才是**线上真正会发生的那 5 个**。同一个模型、
同一句提示词约束，候选从"1 个不相干的函数"换成"5 个有点关系的工具"，误调率从 10.4% 涨到 23.3%
（`live/README.md` 有表）。**所以乱调主要不是模型不听话，是候选给得太客气。**

产物也各自独立：`retrieval/` 走"Java 导出 TREC 格式 → Python 用 `ir_measures` 算分"，
`bfcl/` 是 BFCL 自己的 handler 直连、用它的 `decode_ast` 判对错，`live/` 是我们自己发请求、
只判"调没调"（不判参数）。第一段经过我们的代码，后两段不经过。

细节各自在目录里的 `README.md`：`retrieval/README.md`、`bfcl/README.md`、`live/README.md`。

## 为什么要分开

- **依赖不同**：检索层只要 `ir-measures`；选择层要整套 `bfcl-eval`（含 torch、faiss），
  而且**必须 Python 3.10–3.12**（它把 numpy 锁在 1.26.4，3.13 装不上）。
  挤在一个 venv 里，两边都被对方的最严约束卡住。
- **成本与频率不同**：检索层零成本、改索引就能跑；选择层要真模型、要钱。合在一起，
  "顺手跑一下"就变成了"顺手花一块钱"。
- **口径不同**：检索层的分数是集合运算（确定性）；选择层的分数来自模型的决策（会漂、
  要容差）。两种数放在同一个报告里，读的人分不清哪个能当判据。

## 共用的东西

- 都不进 CI：`retrieval/` 要 Testcontainers 起库、要 embedding key；`bfcl/` 要真模型。
  两边都是手动跑，与 `-Peval` 同一条规矩。
- 都是 `baseline.json` 入库、产物（`reports/`、`result/`、`score/`）不入库——一个是标准，
  一个是产物。
- 都遵守同一条退出码口径：`0` 达标、`1` 有不达标或回归项、`2` 环境没搭起来
  （缺 key / 缺依赖 / 缺基线）。
- 都判两根门（票 19）：**绝对门**回答「够不够好」（与基线无关的合格水位），**回归门**回答
  「有没有变差」。只判回归门等于拿上次自己的分数当合格线，那是自证清白。各自的线写在
  子目录 README 的「门槛」一节，改动要连依据一起写。
- **检索层达标，选择层不达标**：`retrieval/` 的 `R@5` **0.852**（线 0.80；88 题 / 58 个工具），
  退出码 `0`；`bfcl/` 的 `simple_python` **95.25%** 达标、`irrelevance` **76.25%**（线 90%）
  不达标，退出码 `1`。后者是模型与 system prompt 的结果，改我们的代码动不了它，见票 23。
  （`irrelevance` 换个调用形态能到 89.58%，但那不是生产形态，见票 24。）
- **真实链路：危险的那一类过了，宽松的那一类没过**。`live/` 的 `production`（一次都没改
  外部世界）**100%**，而 `bfcl` 口径只有 **76.67%**（线 90%），退码 `1`。两个数差这么远，
  本身就说明"调了"与"改坏了"必须分开报，见票 28。
