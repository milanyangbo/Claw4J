# 工具评测（两层）

同一件事的两个阶段，分开两个目录，各有各的脚本、依赖、基线与报告：

| 目录 | 测什么 | 入口 | 花不花钱 |
| --- | --- | --- | --- |
| `retrieval/` | 一句话进来，**前 k 个候选里有没有那个工具** | `./eval/tools/retrieval/run.sh` | 不花（只算 embedding） |
| `bfcl/` | 候选给了之后，**它选对没有、参数填对没有、不该调时老实没有** | `./eval/tools/bfcl/run.sh` | 花（真模型） |

两层的细节各自在目录里的 `README.md`：`retrieval/README.md`、`bfcl/README.md`。

## 为什么要分开

- **依赖不同**：检索层只要 `ir-measures`；选择层要整套 `bfcl-eval`（含 torch、faiss），
  而且**必须 Python 3.10–3.12**（它把 numpy 锁在 1.26.4，3.13 装不上）。
  挤在一个 venv 里，两边都被对方的最严约束卡住。
- **成本与频率不同**：检索层零成本、改索引就能跑；选择层要真模型、要钱。合在一起，
  "顺手跑一下"就变成了"顺手花一块钱"。
- **口径不同**：检索层的分数是集合运算（确定性）；选择层的分数来自模型的决策（会漂、
  要容差）。两种数放在同一个报告里，读的人分不清哪个能当判据。

## 都过了才算端到端能选对工具

只过检索层：候选里有那个工具，但模型可能挑错。
只过选择层：模型挑得对，但它拿到的候选是别的（真实链路上根本没这个机会）。

## 共用的东西

- 都不进 CI：`retrieval/` 要 Testcontainers 起库、要 embedding key；`bfcl/` 要真模型。
  两边都是手动跑，与 `-Peval` 同一条规矩。
- 都是 `baseline.json` 入库、产物（`reports/`、`result/`、`score/`）不入库——一个是标准，
  一个是产物。
- 都遵守同一条退出码口径：`0` 达标、`1` 有不达标或回归项、`2` 环境没搭起来
  （缺 key / 缺依赖 / 缺基线）。
- 都判两根门（票 19）：**绝对门**回答「够不够好」（与基线无关的合格水位），**回归门**回答
  「有没有变差」。只判回归门等于拿上次自己的分数当合格线，那是自证清白。各自的线写在
  子目录 README 的「门槛」一节，改动要连依据一起写。
- **检索层已达标，选择层差一档**：`retrieval/` 的 `R@5` 0.800（线 0.80）、零候选率 1.000
  （线 0.90），退出码 `0`；`bfcl/` 的 `simple_python` 95.50% 达标，`irrelevance` 77.08%
  （线 90%）未达标，退出码 `1`。后者是模型的决策能力，不归我们的代码管，见票 20。
