# 工具检索评测（票 09 / 票 12 / 票 18）

回答一个问题：**同一句人话，索引的前 k 里有没有那个工具。**
不回答"模型拿到候选后选不选对"——那一层在 `eval/tools/bfcl/`（票 17，用 BFCL 的题库与判据，
要真模型、要花钱），见那份 README。

2026-11-26（票 22）撤掉 `no-search` 之后两边都是 50 题，下面这段对比只作为历史记录留着：

票 18 换题库后实测 `regex`：

| | R@1 | R@5 |
| --- | --- | --- |

这 3 题没定位过，是两套实现之间尚未解释的差（`--cross-check` 校验的是 `run_ir.py` 内部两套

记在缺口里，见票 18。

## 跑（权威口径）

```bash
./eval/tools/retrieval/run.sh                        # 导出 + 算分，全部 5 档
./eval/tools/retrieval/run.sh --configs hybrid-0.0   # 只跑一档
./eval/tools/retrieval/run.sh --from-report          # 不重跑导出，只按当前门槛重算
./eval/tools/retrieval/run.sh --cross-check          # 加做两套指标的一致性校验
./eval/tools/retrieval/run.sh --update-baseline      # 确认改好了，把分数钉成新基线
```

- 只有一条环境变量：`QWEN_API_KEY`（hybrid 三档要真 embedding）。**没有 judge、不花钱**。
- 退出码：`0` 达标（绝对门与回归门都过）；`1` 有不达标或回归项；`2` 环境没搭起来
  （缺 key / 缺依赖 / **缺基线**）。
- 产物在 `eval/tools/retrieval/reports/`，**不入库**；`baseline.json` 入库——一个是产物，一个是标准。

## 产物

| 文件 | 谁写 | 内容 |

| `reports/<config>.run` | 同上 | TREC run：`qid Q0 docno rank score runid`，rank 就是检索给的顺序 |

| `reports/score.json` | `run_ir.py` | 机器读的分数 |
| `reports/report.md` | `run_ir.py` | 人读的报告：测了什么 / 指标怎么读 / 每档配置是什么 / 按分类 / 怎么算达标 / 已知噪声 |
| `baseline.json` | `run_ir.py --update-baseline` | 上次被接受的版本 |

**为什么没有 `no-search` 这一档**（票 22 起）：原来有 10 道"期望零候选"的寒暄题，闸在检索层的
一个中文词表上（删空即返回零候选）。撤掉的理由是那条判据量的是"这一轮该不该检索"——意图判定，
不是检索；而且词表是照着那 10 道题写的，1.000 只证明它覆盖了自己那份题。这项能力现在由
`eval/tools/bfcl/` 的 `irrelevance` 档判（240 题，判模型该不该调），不在检索层重复一个更弱的版本。

## 报告怎么读

`reports/report.md` 是给人看的，自带四节：**测了什么**、**五个指标各是什么意思**（含算例）、
**每档配置是什么**（`hybrid-0.5` 的 0.5 是关键字那一路的权重）、**怎么算达标**（门槛与退出码）。
下面这张表是同一件事的压缩版，报告里那份才是完整的。

## 列

| 列 | 意思 |
| --- | --- |
| `R@k` | 前 k 名里有 gold 工具的比例。**每题只标一个 gold**，所以与"命中任一"等价 |
| `RR` | 第一个 gold 名次的倒数均值（= MRR）；没命中记 0 |
| `nDCG@10` | 与 ToolRet（ACL 2025）同口径，方便跟公开数字对话 |

**加多 gold 的题之前注意**：`ir_measures` 的 `R@k` 是"覆盖比例"，票 09 的自研是"命中任一"。
现在每题一个 gold 所以等价；一加多 gold，两边就会分道扬镳，到时要选一个口径并改另一边的注释。

## 门槛：两根，管两件不同的事

| 门 | 回答什么 | 现在的线 |
| --- | --- | --- |
| **绝对门** | 够不够好 | `R@5 ≥ 0.80`（判生产默认那一档） |
| **回归门** | 有没有变差 | 不低于 `baseline.json` 减 `TOLERANCE`（0.05 ≈ 两道半题，分母 50） |

**这两件事必须分开**。只用回归门等于拿「上次自己的分数」当合格线——上一次那版从没被判过合格，
那是自证清白。所以票 19 补了绝对门，报告顶部因此有一张 `| 指标 | 当前 | 合格线 | 口径 | 结论 |` 表。

绝对门这个数**不是行业公开数字**：工具检索没有公认榜单。它的依据是用户可感知的错误频率——
`R@5` 0.80 = 五题漏一题（24 个工具随机取 5 个的命中率是 0.208，0.80 是它的近 4 倍）。
要改，改 `run_ir.py` 的 `GATE_R5` 并写清新依据。

**质量线判的是生产实际在用的那一档**（`run_ir.py` 的 `GATE_PRIMARY`，与 `application.yml` 的
`index` 同一个值，现在是 `hybrid-0.5`）。给没人用的对照档设门没有意义：红了也没人去修。
`lucene` / `hybrid-1.0` / `hybrid-0.0` 只在总表里作对照，不参与判定
（`hybrid-1.0` 与 `lucene` 逐格相同，两个都在表里只是为了让"融合层没写错"这条自检看得见）。

票 19 刚加线时三项全红（0.640 / 0.500），票 20 做到 0.800 / 1.000，票 21 换翼后到
**0.880**，退出码 `0`。票 22 撤掉零候选率那一条后，绝对门只剩 `R@5` 一项。

不设第三层「分档（差／良／好）」：RAG 侧有那一层是因为 judge 会漂、需要相对判断；这边全是确定性
指标，分档只会把当前噪声固化成标准。`R@1` / `RR` / `nDCG@10` 同理列作诊断项（`—`）：前五里有对的
工具，模型还能自己挑，排得靠后不构成功能缺失。

## 一致性自检

`--cross-check` 用票 09 的公式重算 `R@5` / `RR`，与 `ir_measures` 逐档比，差 > 1e-9 就打印
两边数字并退出 1。两套实现之间对不上时，第一个问题是"信谁"——这条把它变成当场可见的报错。

**分档看这一张**（第三方口径）：

```
分类                lucene  hybrid-1.0  hybrid-0.5  hybrid-0.0
base               0.800       0.800       0.900       0.500
business           0.700       0.700       0.800       0.850
zh-en              0.850       0.850       0.950       0.900
```

同一张表的 `R@1`（位置更敏感，噪声也更大）：

```

base               0.700       0.700       0.400       0.100
business           0.300       0.300       0.550       0.600
zh-en              0.400       0.400       0.550       0.300
```

**两路各有一块谁也替不了的强项，这就是 0.5 权重最好的原因**：

- `base`（文件/命令类）：Lucene 翼 0.800，纯向量只有 0.500。中文 query 与中文译文有
  **字面**重合（「编译」↔「编译」），TF-IDF 抓得比语义稳。
- `business`（自有工具，中文描述）：纯向量 0.850 最高，Lucene 翼 0.700，各一半是 0.800。这些工具的"动作"说法
  与描述字面不像（「还有什么事挂着没人管」↔「列出未关闭的 issue」），得靠语义。
- `zh-en`（中文问英文描述）：Lucene 翼 0.850、各一半 0.950，是译文的功劳（译前 Lucene 只有 0.200）。

`base` 这一档顺带回答了上一版的疑问：`把 pom.xml 打开我看看`、`代码里哪些地方还留着 TODO`、
`把项目编译一下` 当年"两种配置下都没有返回"。现在它们是 Lucene 翼的第一名。
**不是题坏，是那一路读的文本语言不对。**

分档表现在由 `run_ir.py` 自己出（票 15）：分类来自 `reports/categories.txt`（Java 导出），
按分类把 qrels 与 run 各切一份再喂 `ir_measures.calc_aggregate`——仍然只有 `ir_measures` 一家
在算分，切片只决定"哪些题进这一档"。

**向量档的 `R@1` / `R@3` 会漂，`R@5` 不会**：同一份代码连跑三次，`hybrid-0.0` 的 `R@1` 是
0.333 / 0.389 / 0.389、`R@3` 是 0.556 / 0.500 / 0.444，而 **`R@5` 三次都是 0.667**（那还是旧题库）。

根因是**近分并列**，不是 embedding 不稳（同一句连调三次，1024 维逐位相同，已验）：
`intent` / `list_schedules` / `Task` / `recall_session` 这一簇工具的描述在向量空间里几乎同一个点，
而框架的 `VectorToolIndex` 用 `ORDER BY embedding <=> ?` 取 top-k，**没有 tie-breaker**——
PostgreSQL 对等值行不做顺序保证。所以两次跑的差异只发生在这一簇内部：相邻名次互换，
`R@5` 的集合不变，`MRR` / `nDCG` 在第 2 位小数上抖（实测 0.488→0.481、0.532→0.527）。

判定只盯 `R@5` 就是这个原因。`R@1` / `R@3` / `RR` / `nDCG@10` 是观测项，
**不要拿它们做前后对比的判据**——那个精度这次测量达不到。要修只有一条路：自己实现向量检索、
在 `ORDER BY` 后面加 `, tool_name`，为一个第 2 位小数的抖动改掉框架实现，不划算。

### 两次导出差在哪（2026-11-26 实测，同一份代码连跑两次）

`lucene` 的 50 道题里有 **37 道**两次候选顺序不同；`R@5` 0.780 / 0.800 各一次。差的是尾部与并列：

```
tools-glob-md   第一次 [Glob, Grep, Read]      第二次 [Glob, Read, Grep]
tools-read-pom  第一次 [Read, WebFetch, BashOutput]  第二次 [Read, WebFetch, Task]
```

两个来源，都不是"这次改动弄坏了什么"：

1. **每轮重新翻译**：评测每次起新容器，`claw4j_tool.tool_description` 是空的，译文要重算一遍，
   措辞不同 → 向量与 Lucene 的输入文本不同。票 16 落了表，但那只在同一个库里有效。
2. **近分并列**：`ORDER BY embedding <=> ?` 没有 tie-breaker，PostgreSQL 对等值行不保证顺序。

所以这张表能比的是 **`R@5` 的 0.05 量级**（一道题 2 个点），不是逐格。`hybrid-0.5` 两次都是
0.880，这也是判定只认它的原因之一。

### 零候选率那一列量错了对象（本批修掉）

`no-search.jsonl` 原来固定取 `regex` 那一档的结果——因为当初它是默认档，而闲聊拦截当时长在
`ChineseToolIndex` 里，只对它生效。后来默认换成 `hybrid`、拦截随 `regex` 一起删掉，这一列才
露出来：**它从没量过生产**。改成按 `hybrid-0.5`（生产档）量之后，第一版结果是 **0.000**——
十道寒暄题每题都拿到 5 个候选。

修法不是把那句话塞回某一档索引，而是独立成层：`ChitchatToolIndex` 包在所有索引外面，
整句只由寒暄词拼成（或空 query）就返回零候选，与选哪一档无关。修完回到 **1.000**，
`R@5` 不动（闲聊题不进 qrels，拦截只可能减少候选、不可能改动得分题的名次）。

> **票 22（同日）把这一层整个撤了。** 它量的是"这一轮该不该检索"——意图判定，不是检索；
> 而那份中文词表是照着这 10 道题写的，1.000 只证明它覆盖了自己那份题。这项能力归
> `eval/tools/bfcl/` 的 `irrelevance` 档（240 题、判模型该不该调）。这一节留着，当作
> "为什么加过、为什么又撤掉"的记录——两次判断的依据都写在这里，不用靠回忆。

三条读法（票 21 之后）：

1. **`hybrid-1.0` 与 `lucene` 逐格相同**——权重 1 真的等于纯关键字，那张"对照"是真对照。
2. **`hybrid-0.5` 最好**：`R@5` 0.880，比纯向量（0.800）和纯 Lucene（0.780）都高。
3. **关键字那一路不再是拖累**：换成 Lucene 翼之前，加它只会把分数往下拉（0.620 < 0.800）；
   现在是往上抬（0.880 > 0.780）。差别不在权重，在那一路读什么文本、用什么排序。

**样本仍小**（50 条、24 个工具），所以这不是"结论"，是基线：往后每改一次检索跑同一份题对比。

## 自研指标修过的那个 bug（2026-11-26）

`ToolRetrievalEval` 原来把"一个候选都没给"直接当命中（`noCandidate || within(k)`），**不看这题
该不该有候选**。于是最坏的失效拿满分：`regex` 下 20 道 `zh-en` 里有 3 道返回空，自研记成
R@1 0.150，而第三方口径同一批是 0.000。

错的方向特别坏：它奖励"查不到任何东西"，并且只在坏的时候生效——好配置上看不出来。现在
`matched` 先看 `goldEmpty`，用例是 `ToolGoldTest#emptyResultIsNotAHit`（断言空手时 R@1 = 0）。

## 中文化（票 11）的三次测量

> **票 21 推翻了这一节的适用范围，读之前先看这一段。**
> 那时"关键字那一路"是 `ChineseToolIndex` 的**中文二元组**：描述一变长，二元组碰撞变多，
> 所以喂译文反而掉分（0.15 → 0.10）。换成 `LuceneToolIndex` 之后结论**相反**——
> 喂译文让 `lucene` 从 0.380 涨到 0.820，base 档从 0.000 到 0.900。现在**两翼都吃译文**。
> 下面三次测量是历史记录，它回答的是"二元组那一翼为什么不吃译文"，
> **不是**"关键字检索不能吃译文"。这个区别当时没看清，才让 `lucene` 白读了半年的英文。

`zh-description` 现在是**两翼都喂**（票 21 起）。下面是票 21 之前"只喂向量"那三次测量的原始记录：

| 哪一版 | 题目 | 关键字那一路 | 向量那一侧 |
| --- | --- | --- | --- |
| 早：两翼都读中文 | 20 题 | `regex` R@1 0.15 → **0.10** | `zh-en` 0.60 → 0.80 |
| 中：只喂向量 | 20 题 | 0.15 → 0.15（不再降） | `zh-en` 逐格相同（**没复现**） |
| 晚：只喂向量 | **38 题** | 0.056 → 0.056（不受影响，符合设计） | `zh-en` **0.200 → 0.250~0.400** |

### 晚这一次的数（加厚题库之后，各跑三遍）

```
hybrid-0.0  zh-en       R@1              R@5              RR
关（三次）          0.200 0.200 0.200   0.600 0.600 0.600  0.352 0.341 0.348
开（三次）          0.350 0.250 0.400   0.750 0.800 0.750  0.495 0.444 0.520
```

- **收益现在测得到**：`R@5` 从 0.600 到 0.75~0.80（3~4 格），远在 0.05 的容差之外。`R@1` 同向但更抖。
- **收益只落在英文描述的工具上**：同一轮里 `base`（Read/Grep/Glob/Bash/WebFetch，描述全英文）
  的 `R@1` 从 0.000 到 0.250；`business`（中文描述）纹丝不动（0.750 / 0.917）。
- **杂音来自翻译本身**：开的那一侧三次跑出三个不同的 `R@1`——因为每个进程重新译一次，译文措辞不同、
  embedding 跟着不同。关的那一侧是逐位可复现的。票 16 把译文落了表，**同一份库**重启不再重译；
  但这条评测每次起新容器（Testcontainers），所以跨 run 仍会重译——上面的数就是那样测出来的。
- 这组 A/B 是在**19 个工具**那一版上测的；票 14 加进 5 个 MCP 工具后基数变了，但两侧同基数，
  结论不受影响（要更准就重跑一遍，`--configs hybrid-0.0`）。
- 所以"上一次说没收益"的结论**只对 20 题那版题库成立**：那 5 道 `zh-en` 里有 3 道在测中文问中文，
  中文化对它们本来就不可能有效果。

**判定**：`index=lucene|vector|hybrid` 时都该打开（票 21 起 `application.yml` 默认 `enabled: true`）；
`index=regex` 那一档不包译文，开着只是白花翻译调用。要让它逐位可复现，得把译文落表——票 16 已落表，
但本评测每次起新容器（Testcontainers），跨 run 仍会重译，这也是 `R@1` 观测不稳的来源。
