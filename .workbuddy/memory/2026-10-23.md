# 2026-10-23 Claw4J 重建

## 模块分层复盘（ADR-0010）

用户质疑通道拆成三个模块是否过度。核对后确认是过度拆分，已合并。

**事实**：`claw4j-channel-api` / `-http` / `-feishu` 三个模块**零 Java 文件**，只有 pom.xml；
且 ADR-0004 原本写的是五模块（`claw4j-channel`），拆三模块是后来写 ADR-0009 时偏离的。
用户判断成立。

**合并后的边界怎么守**（这是合并能成立的前提）：
- 飞书 SDK 改 `<optional>true</optional>`，不传递给下游；要飞书走 `-Pchannel-feishu`
- 边界改由**包级 ArchUnit 规则**守：SPI 平台中立 / 飞书 SDK 只在 feishu 包 / agent 与 channel 互不依赖
- 包级规则比模块隔离**粒度更细**（模块拦不住"spi 包里混进一个平台 import"）
- 规则有效性用违规探针反向验证过：故意在 spi 包 import com.lark.oapi，两条规则各拦一次

**顺带修掉一个更严重的问题**：agent 与 channel 之间此前**没有任何依赖边**，
"入站消息怎么交给 Agent"根本没定义，M1 写 HTTP 通道时会临时拍脑袋。
解法：端口放 domain（不是调用方模块）——
- `domain.port` 新增 `InboundMessage` / `OutboundMessage` / `AgentPort`
- 依赖方向变成 `channel → domain ← agent`，接线只在 app，两边零耦合
- domain 承诺零框架，流式只能用 `Consumer<OutboundMessage>` 不能用 Flux
- agent 提供 `ChatClientAgentPort` 实现并注册 bean

**拆模块判据**（写进 ADR-0010，避免以后重复讨论）：独立发布周期 / 独立持久化或团队 /
两个以上互不相干的变化原因且都超千行。当前全仓 Java 不到 400 行，五模块已偏多。
M2 引入 Skill 引擎与 MCP client 后若 agent 膨胀，再按判据评估拆 `claw4j-skills`。

**遗留**：`claw4j-agent` 尚未依赖 `claw4j-tools`（装配线没接），M1 补，方向不变。

## 按 API key 有无自动装配 ChatModel（ADR-0006 修订）

用户提供 DeepSeek key，问能否"有 key 才注入对应 ChatModel bean"。答案是可以，已实现，
并借此去掉了 Maven profile `real-model`（换模型不用重新构建）。

**关键事实**：`DeepSeekChatAutoConfiguration` 的条件是
`@ConditionalOnProperty(name="spring.ai.model.chat", havingValue="deepseek", matchIfMissing=true)`，
**与 api key 无关**。classpath 有 starter 时缺 key 照样激活并抛 "API key must be set"。
→ 所以依赖改用纯包 `spring-ai-deepseek`（不带 starter），厂商自动配置不参与竞争。

**必须用自定义 `SpringBootCondition` 而非 `@ConditionalOnProperty`**：
后者只能判断"等于某值"，判断不了"字符串非空"；空串也算属性存在，条件照样通过。

**踩到的坑（很重要）**：`DeepSeekChatModel` 默认 options 的 model 是 null，
请求不带 model 时 DeepSeek **返回空内容且不报错** —— 表现为"调用成功但回答永远为空"。
必须显式 `DeepSeekChatOptions.builder().model(...)`。这个坑只有真调一次才会发现。

**另一个坑**：Spring Boot 默认不读 `.env`（那是 docker compose 的约定）。
解法 `spring.config.import: optional:file:.env[.properties]`，已验证生效。

三态：`claw4j.model.mock` 留空=自动 / true=强制 mock / false=强制真实（无 key 则启动失败）。

## M0-04 HTTP+SSE 通道端到端

通道包 `io.github.claw4j.channel.http` 四个类各管一件事：
- `HttpChatController` 只管传输（读头/认人/转发），不碰 AgentPort
- `HttpPrincipalResolver` 头 → Principal（`X-Claw4j-User` 必填、`-Role` 默认 read-only、
  `-Session` 缺省回落用户标识）；缺头或未登记角色即拒绝（401），不做"找不到就给默认权限"
- `HttpChatChannel` 同步直调；**流式提交到业务线程池后立刻返回 `CompletableFuture<Void>`**
  ——因为 `AgentPort.stream()` 是阻塞的（domain 不用 Reactor），十几秒会吃满 Tomcat 线程，
  飞书还会触发 3 秒重推。这个形状先在 HTTP 跑通，M2 换长连接只需把 emitter 换成主动推送
- `HttpChannelAutoConfiguration` 走 `AutoConfiguration.imports`（app 不扫描该包），
  `HttpChatChannel` 用 `initMethod/destroyMethod` 触发 SPI 的 start/stop

端点 `POST /api/chat`（同步）、`POST /api/chat/stream`（SSE，事件名 chunk/done）。
本机 curl 已跑通：同步 `{"sessionKey":"http:ethan","text":"[mock] 上周华东区成交额多少"}`。

**三个坑（已写进 ADR-0007）**：
1. `BaseAdvisorChain` 给流式取的是 `getStreamAdvisors()`，只认 `StreamAdvisor`——
   只写 `CallAdvisor` 的 Advisor 在 `.stream()` 上**既不报错也不生效**。三层拦：
   ArchUnit 规则（Advisor 必须同时可赋值给两个接口）+ `AdvisorBothPathsTest`（反面用例钉住行为）
   + `AdvisorNotSkippedOverHttpTest`（HTTP 全链路证明生效）
2. **匿名 `BaseAdvisor` 的 `getClass().getSimpleName()` 是空串** → 不覆写 `getName()`
   会让观测上下文抛 `advisorName cannot be null or empty`，且**只有流式路径抛**
3. `Prompt.augmentUserMessage(String)` 是**替换**用户消息不是追加（名字误导），
   要追加必须走 `Function` 版本 `augmentUserMessage(u -> u.mutate().text(...).build())`

**配套改动**：`MockChatModel.stream()` 改成每 8 字符切一块——只返回一块的 mock 测不出
"流式被降级成一次性响应"；`AgentAutoConfiguration` 现在把容器里所有 `Advisor` bean
按 order 挂链（`ObjectProvider<Advisor>.orderedStream()`），否则测试挂的 Advisor 进不去。

SSE 断言要点：分块边界会落在标记中间（`[mock] [` + `ADVISOR]`），
必须先拼接所有 `data:` 行再 `contains`，直接查原始报文会误判。

## 模型路由与主备降级（RoutingChatModel）

用户问"DeepSeek 与千问怎么切换"，选了**现在做薄版**。ADR-0006 原写"具名 ChatClient.Builder 分流"，
落地时改成 **ChatModel 层主备**：Advisor 链只有一份，分流 ChatClient 等于把链复制两份，
鉴权脱敏要各配一次；真正要"换一家"的时刻是模型调用失败那一刻，那是 ChatModel 的职责。

结构：`ModelConfiguration` 按各家 key 装具名 bean（`deepSeekChatModel` / `qwenChatModel`），
`RoutingModelConfiguration`（after Model、before Mock）排成主备并暴露 `@Primary` 的 `RoutingChatModel`；
一家都没装时 `MockModelConfiguration` 兜底。`claw4j.model.primary` 从死键变成真开关。

**降级规则**：同步任何异常都换下一家（全挂抛 `ModelRoutingException`，每次失败挂 suppressed）；
流式**只在首块之前**降级（吐过再换会把同一句发两遍）。

**最大的坑（只有跑真实链路才会暴露）**：各家 `ChatOptions` 互不兼容，厂商 ChatModel 直接把
`prompt.getOptions()` 强转成自己那一型 → 通义为主、DeepSeek 为备时，降级当场 `ClassCastException`，
救命路径必崩。修法：交给某家之前先 `own.mutate()` 以本家默认参数为底、搬厂商无关参数（温度/topP/maxTokens…）、
**model 一律用本家的**（否则等于让 DeepSeek 跑 qwen-plus）。已加两条测试钉住。

**通义适配代价**：无官方适配器 → `spring-ai-openai` 走 `/compatible-mode/v1`，带进
`openai-java-core` + `okhttp`；`maxRetries(0)`（避免 SDK 重试与降级叠加）、
`checkJacksonVersionCompatibility(false)`（Boot 4 是 Jackson 3，版本校验会启动失败）。

**验证方式（可复用）**：起假 OpenAI 兼容端点（python，返回固定内容 + SSE 流），
把两家 base-url 指过去跑同步/流式；再把主的 base-url 指到没人听的端口验降级。
注意两点：假服务要处理 **chunked 请求体**（DeepSeek SDK 用 chunked，OpenAI SDK 用 Content-Length）；
**沙箱会拦 JVM 的回环连接**（curl/python 可以，Java 报 ClosedChannelException），冒烟需放开沙箱。

## 流式取消为什么不能用 CompletableFuture.runAsync（用户提问）

`HttpChatChannel.stream` 手写 `AtomicReference<Thread>` + `whenComplete` 中断，用户问为何不一行
`runAsync(..., streamExecutor)`。实测结论（JDK 21）：

- `CompletableFuture.cancel(true)` 的 mayInterruptIfRunning **完全无效**（文档明说）→ 实测工作线程未被中断
- `ExecutorService.submit()` 返回的 FutureTask `cancel(true)` **真中断** → 实测被中断
- 池满时 `runAsync` **同步抛** `RejectedExecutionException`（`asyncRunStage` 无 try/catch），
  与手写版等价 → 这点不构成差异，不要拿它当理由

所以唯一差异是取消：控制器 `emitter.onTimeout/onError/onCompletion` 都调 `agent.cancel(true)`，
换 runAsync 会让客户端断开后模型继续把流烧完。且 runAsync 把任务包进内部 `AsyncRun`，
拿不到线程引用，想自己补都补不上。`HttpChatChannelTest:137` 正好钉住这条（换成 runAsync 会红）。

手写版的安全不变式已写进 javadoc：CF 一次性状态保证任务完成后 cancel 返回 false 且不触发
whenComplete，不会污染归还后的池线程；窄窗口下的残留中断位由 `workQueue.take()` 抛出时顺带清除。

**通用教训**：需要"取消必须传播"时，别用 `CompletableFuture.runAsync`，
要么手写线程引用，要么用 `submit()` 拿 FutureTask 再桥接成 CF。

## M1-03 鉴权 Advisor（已 resolved，提交 e7ee1e1 / 9025e11）

**最大的坑：票面与 ADR-0007 把 order 方向写反了。** 循环内部是 order **更大**的一侧：
`ToolCallingAdvisor.DEFAULT_ORDER = HIGHEST_PRECEDENCE + 300`，链按 order 升序排，
它每轮递归的是 `copy(this)` **之后**的那段（类注释明说 +200 的 memory advisor 落在外面）。
写反不是慢一点，是**整条鉴权失效且很隐蔽**：排在循环外时 `chain.nextCall()` 拿到的是
工具循环跑完后的最终响应，里面已经没有工具调用了 → 永远放行。变异检验改 order 为 -100：7 红 6。

**判定发生在模型返回之后、工具执行之前**（票面写的"不调 chain.next()"是错的——
不调就看不到模型这轮要调什么）。不通过就把这一轮**连工具调用一起换掉**，
只换正文保留 `toolCalls` 的话工具照跑（变异：7 红 5）。

**流式不能用 BaseAdvisor 默认实现**：它只在 `onFinishReason()` 那一块调 `after()`，
而工具调用是分块发的，带 finish reason 的收尾块里通常已经没有工具调用。
解法：自己 `handle((chunk, sink) -> ...)`，看到越权当场发拒绝 + `sink.complete()` 掐断上游。

**权限登记跟着工具走**：domain 加 `ToolPermission(动作, 表清单)` + `ToolPermissionRegistry` 接口，
tools 模块声明 `querySales → read + sales_order`，agent 只认接口，**没登记一律拒绝**。
动作名用粗粒度动词（read / sendMail）而不是工具名，免得角色配置变成工具清单。

**顺带修正语义**：`Principal.readOnly` 原来动作集为空 = 只读身份连查数都不行（默认角色废掉）。
现在拿 `read` 动作；通道默认角色同步，另加 `guest`（只 `region` 表）做"换角色头"演示。

Principal 走 **Advisor 上下文**传给链（`.advisors(spec -> spec.param(KEY, principal))`），
不走 ThreadLocal：上下文跟着每轮请求与 Reactor 订阅走，掉了的失败姿势是放行。

测试 97 个全绿（+16）。app 层 `AuthorizationOverHttpTest` 用两轮假模型替掉 mock
（mock 是回声，永远不会要求调工具，鉴权根本不触发）——按"提示词里有没有 ToolResponseMessage"
分轮而不是用计数器，避免共用容器串状态。

## M1-04 出站 PII 脱敏（已 resolved，提交 6545bde）

**摆位与鉴权相反**：脱敏 Advisor 的 order **小于** `ToolCallingAdvisor.DEFAULT_ORDER`
（排在工具循环外面，整通对话只跑一次）。放进去会把**工具结果**一起打码，
而模型要靠原始值判断"这个号码是哪一单的"。两张票一内一外，各自有理由，不是随手写的。

**流式必须扣住尾巴**：分块边界会正好落在手机号中间（8 字一块时 11 位号码必然被切开），
逐块各自脱敏两块都匹配不上 → 整个号码漏出去，而且漏不漏取决于模型那批吐了多少字。
`PiiRedactor.safePrefix()` 砍掉末尾连续的数字/X 段（PII 模式只由这些字符组成）再吐出，
剩下的攒着，收尾时全部吐出。配套性质测试：任意位置切一刀，结果与整体脱敏必须完全一致。

**正则两侧要定界**（`(?<!\d)` / `(?!\d)`）：不然 18 位数字会被当手机号切一段打码。
金额、订单号这类"不是号码的数字"必须原样放过——打错地方比不打更糟，看着像真数据。

**日志断言踩坑**：Boot 的 `OutputCaptureExtension` + `CapturedOutput` **实测抓到空串**
（日志系统若在替换 stdout 之前就初始化，appender 持有的是原流）。
改成往 logger 挂 Logback `ListAppender` + 显式设 DEBUG level。
断言要分两半：`不含原始值`（单独看恒真）+ `含掩码后的值`（证明日志真打了）。

## M1-05 Text-to-SQL 闭环（提交 cb39bb9，已关票）

**只读约束落两层，理由是可写 CTE**：`with x as (delete ... returning *) select * from x`
是一条语句且以 with 开头，任何"首关键字放行"的字符串规则都会放过它。
第一层 `SalesSqlGuard`（纯字符串，去注释与字面量后再判）；
第二层是**只读事务**而不是只读库用户——`TransactionTemplate.setReadOnly(true)`
经 Spring → `Connection.setReadOnly(true)` → PG 驱动事务级只读，与配只读用户等价且可在 Testcontainers 里证明。
**变异检验删掉了我自己多加的 `set transaction read only`**：去掉它 5 条测试照样绿，说明驱动已做，
那段是"测不出作用"的代码，不留。

**只读断言被现实纠正**：delete/drop 的实际失败原因是"包一层子查询后连解析都过不去"
（PG 子查询不能是 DML；带数据修改的 WITH 必须在最外层），不是 read-only。
所以断言改成"抛异常 + 数据没变"，另用 `select ... for update`（能穿过包装）证明只读事务本身。

**自纠错**：工具返回数据库 root cause 原文（Spring 把 PG 原话包进 BadSqlGrammarException）
+ 改写提示，而不是抛异常。固定 schema 与区域字典值（east/south/north）写进工具描述——
`where region_code='华东'` 不报错只返回 0 行，而"0 行"是自纠错唯一发现不了的错误。

**重试上限用框架自带的但必须显式传**：`DefaultToolCallingManager.Builder` 默认 40/150，
`THROW` 时 ToolCallingAdvisor 接住后直接给客户端、不再回头问模型。
收紧到 3/6。**`spring.ai.tools.limits.*` 到不了这条链**——ChatClient 是我们自己建的，
必须用五参 `ChatClient.builder(model, obs, null, null, toolCallingAdvisorBuilder)` 传 manager；
退回单参就静默变 40/150（有单测钉着）。

**装配静默失效坑（值得记）**：`@ConditionalOnBean(JdbcClient.class)` 在
`ToolsAutoConfiguration` 里永远为假——自动配置按类名排序，`io.github.claw4j.*`
排在 `org.springframework.*` 前面，条件在 Boot 注册 JdbcClient 之前求值。
失效姿势是"工具静默消失，模型开始编答案"。修法 `@AutoConfiguration(afterName="...JdbcClientAutoConfiguration")`。

**新增接缝** `ReadOnlySqlExecutor`：Agent 侧循环测试（自纠错/上限）不需要 Docker；
02 的 `SalesDataRepository.sumAmount` 变成数字契约锚点，端到端断言写死的 128400.00。

ADR-0005 的 `spring-ai-starter-session-jdbc` 同样不存在。可用的是

## M1-06 会话记忆（已 closed）

**上一轮"06 坐标不存在"的结论是错的**：只在 `org.springframework.ai` 下翻 2.0.2 BOM。
`spring-ai-session` 是 spring-ai-community 的独立项目，groupId 是 **`org.springaicommunity`**，
根 pom 里 import 的 `spring-ai-session-bom:0.10.0` 一直在管它。
真坐标 `org.springaicommunity:spring-ai-starter-session-jdbc:0.10.0`（依赖 spring-ai 2.0.1，被 BOM 提到 2.0.2）。
**教训：查不到坐标时先看根 pom 里 import 了哪些 BOM，别只在最眼熟的那个 groupId 下找。**

**坑（值得记）**
- 官方 `JdbcSessionRepositoryAutoConfiguration` 拿主 `DataSource`，会话表落 public，
  与 ADR-0005"同库不同 schema"冲突 → 自己声明 `SessionRepository`（它带 @ConditionalOnMissingBean，会退让，
  自动配置按类名排序 `io.github.*` 先于 `org.springaicommunity.*`）。
- spring-ai-session 的 SQL 表名不带前缀，落点由连接 search_path 决定 → 会话池 URL 加 `currentSchema`。
  **会话池不能注册成 bean**：两个 DataSource 会让 `@ConditionalOnSingleCandidate(DataSource)` 不成立，
  JdbcClient 与事务管理器整套不装配（与 05 那个坑同一个病根）。
- Flyway 建表必须写全限定名（Flyway 连的是默认 search_path），运行时查询不带前缀（靠连接池 currentSchema）。
- 官方 schema initializer 在 bean 创建时就连库探测驱动 → 没库时应用起不来，必须 `initialize-schema=never`。
- 降级要认两类异常：`DataAccessException` **和** `TransactionException`
  （`CannotCreateTransactionException` 继承后者，不是前者——只认前者时"连不上库"恰恰漏在外面）。

**设计决策**
- 会话 id 只由 userId 派生，不掺 chatId（换通道不失忆）；代价是同一个人的多话题会混，M1 接受。
- 记忆 Advisor order 全链最小（HIGHEST_PRECEDENCE）→ 收尾最后 → 会话表里存的是脱敏后的文本；
  脱敏 order 相应从 `DEFAULT_CHAT_MEMORY_PRECEDENCE_ORDER - 100` 提到 `DEFAULT_CHAT_MEMORY_PRECEDENCE_ORDER`。
- 记忆失败降级（打 WARN）而不是 500：鉴权是安全边界，不能因为记不住就说不出"没权限"。
  三个 Advisor 失败姿势不同：鉴权/脱敏只能拒绝，记忆只能降级。

**可证伪判据的做法**：`ScriptedChatModel` 脚本从"写死响应"升级成**函数**（新增 `thenAnswer(Function<String,String>)`）。
第二轮只有看见上一轮才答得出华南的数，否则反问——无记忆的实现落在反问那一支，断言立刻红。
变异检验：不传会话 id 全红；拿 chatId 当主键只有"换通道不失忆"红；记忆 order 大于脱敏 2 条红；Advisor 不挂链 6 条红。

**顺带修**：`SalesDataRepositoryTest` 断言迁移记录总数 2 → 加 V3 就红，改成钉"V2 只执行过一次"（要防的是种子重放，总数与之无关）。
