# M9：规模（P17–P19）

## 这份 spec 是什么

`docs/adr/0020-platform-capabilities-ride-on-run.md` §M9 的落地。ADR 里那一段只给了三张票各一段
定义，没有票面；这份 spec 负责把三张排开、写清现在开到哪、以及判据沿用哪一套。

开票状态：`P17` 拆成 `P17a` / `P17b` / `P17c`，`P18` 拆成 `P18a` / `P18b`，`P19` 用户 2026-11-18
裁决**暂时不需要**。拆票编号沿用 `P10a` / `P10b` / `P10c` 的口径，不新起 P 号。

## 三张票

| 编号 | 一件事 | 状态 |
| --- | --- | --- |
| **P17** | 脚本沙箱加固（真正的隔离边界）：从"四条约束"到"容器级限额" | 拆成 `P17a` / `P17b` / `P17c`；`P17a` resolved（2026-11-18），另两张 `ready-for-agent` |
| **P18** | `doctor` 自检 | 拆成 `P18a` / `P18b`，均 `ready-for-agent` |
| **P19** | WebSocket 传输 | **暂不需要**（2026-11-18 用户裁决），未拆票 |

P17 的三张：

| 票 | 一件事 | Blocked by |
| --- | --- | --- |
| `P17a-sandbox-mode-and-docker-backend` | `tools.sandbox.*` 的键；命令真的跑进容器 | 无。**已 resolved** |
| `P17b-container-limits` | 断网、只读根、内存与 pid 上限、非 root；两条路径共用一份容器规格 | P17a |
| `P17c-workspace-and-lifecycle` | 工作目录进出、容器复用、退出清理 | P17a（可与 b 并行） |

P18 的两张，按"要不要出去"切——这两类的测试策略完全不同：

| 票 | 一件事 | Blocked by |
| --- | --- | --- |
| `P18a-doctor-local-checks` | 命令入口 + 报告格式 + 迁移版本 / 目录存在 / 凭据句柄能否解析 / 配了不生效的键 | 无 |
| `P18b-doctor-online-checks` | `--online`：模型 key 真的能用、外部 MCP 连得上（默认不跑） | P18a |

## P18 与 P19 的原文

ADR-0020：

**P18 · `doctor` 自检**：照 OpenClaw `doctor` 的形状——检查 key 有效性、迁移是否最新、
外部 server 是否连得上、目录是否存在。

**P19 · WebSocket 传输**：HTTP+SSE 之外的第二条传输。对应 OpenClaw Gateway 协议的一小部分，
但**不做它的控制面**。ADR-0018 还留了一句给这张票：WebSocket 与 SSE 的**重连**当时明确不做，
"M9 的 P19 再重审"。

P18 的四项已经全部落进 a / b 两张。**P19 不做**（2026-11-18 裁决），ADR-0018 留的那条"重连再重审"
随之搁置——它没有对象了，因为第二条传输本身不做。定义留在 ADR 里不动，将来要捡回来重新开票。

**P18 不是第二个 `actuator/health`。** 项目已经有 `/actuator/health`（9090，只绑 127.0.0.1）。
两者回答的不是同一个问题：health 是运行期被探针反复问"现在活着吗"，聚合成一个 UP/DOWN；
doctor 是人跑一次"这套配置能不能用"，逐项、带修复动作、不启 web。最实的差别是**一次报全**——
启动是 fail-fast，只报第一个错，修完再起又是下一个。

## 为什么 P17 排在前面

P17 与 P18 互不依赖，但 P17 有两个外部理由：

1. **它是 ADR-0021 里企业属性唯一明确 ✗ 的一条**：`SandboxPolicy` 锁住入口、参数、工作目录、
   环境、时长五样，但脚本与宿主**同 OS 用户、同网络、同文件系统**——有约束，无隔离。
2. **权限那批票里有一张硬等它**：`permission-alignment` 的票 06（`sandbox.tools` / `exec.host` /
   `elevated`）的 `Blocked by` 已经改指向 `P17a`–`P17c`。ADR-0030 裁决六写的顺序是硬的：
   先容器化，之后 `tools.sandbox.tools`，再之后 `elevated`——`elevated` 的语义是"我在沙箱里，
   这一次要跑到沙箱外"，没有沙箱就没有这句话。

P18 与权限无关，先做后做都不影响那一批。

## 与权限那批票的关系

只有一条：**票 06 等 P17 全部落地**。

反过来不成立——P17 不碰工具可见性、不碰审批。它管"在哪跑"，那批票管"准不准跑"。
两条路径（脚本包的 `ProcessRunnerFactory`、exec 的 `ExecBackend`）本来就是为换执行位置留的接缝，
P17 只是把实现换掉，调用方一行不动。

## 共同的判据（与仓库一致，不另立）

- **默认零变化**：`mode` 默认 `off`，不配这一整段时行为与今天逐字节一致。
- **不许静默降级**：配了 `backend=docker` 而探测失败，启动即失败并点名，不悄悄回落宿主。
  跟 `SandboxPolicy` 选白名单而不是黑名单同一个理由——静默的失效没人会发现。
- **配置里不许出现"配了不生效"的键**：`backend=ssh` 接受取值但启动报未实现，而不是忽略它。
  这正是权限那批票一直在删的东西。
- **门禁照旧**：`./scripts/verify.sh` 全绿（`clean verify` + 删除词闸 + 覆盖率 + 14/26 上限）。
- **真隔离的用例不进默认门禁**：`verify.sh` 要求跳过数为 0，`pom.xml` 那段注释也写明了为什么不用
  `assume`（`assume` 出来的是 skipped，而跳过的绿和通过的绿在报表里长得一样）。CI 上没有 docker
  守护进程，所以 argv 拼装与失败语义用假后端做单测进回归，真容器用例打 `@Tag("docker")`，
  按 `real-cli` / `real-mcp` 那套机制排除，需要时用 profile 放开。

## 边界与不做

- **`openshell` 后端不做**（ADR-0021 已明确），`ssh` 后端 P17a 只留取值不留实现。
- **`host=node` 仍是占位**：我们没有多宿主，配进来只落到本机。这一条归权限那批的票 06。
- **P18 只检查、不自动修**：ADR 写的是"检查"，加修复是扩范围，真要做另开一张。
- **P19 不做**（2026-11-18 裁决）：WebSocket 是第二条传输，`elevated` 不依赖它、通道也不依赖它，
  现在没有需要它的场景。ADR-0020 里的定义保留，随时可以重新开票。
- **容器预热池、磁盘配额不做**：前者是冷启动优化，后者在多数 storage driver 上静默无效。

## 缺口

- **P19 没有对象**：ADR-0018 留的"WebSocket 与 SSE 重连，M9 的 P19 再重审"随之一并搁置。
  真要接入长连接客户端时再回来看这两条——那时需求会告诉我们重连到底要不要做。
