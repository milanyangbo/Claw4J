# M2 收尾：先修三处缺陷，再落飞书长连接通道

## Problem Statement

从外面看，这个项目现在能演示的是"在 HTTP 上问一句成交额、拿到库里算出来的数"。但 ADR-0008 给
M2 的验收判据是"模型能自己选技能、委派子 Agent、跑通 MCP，**且能在飞书里发消息问答**"。
前三件都做了（8 张票全部 resolved），最后一件一行代码都没有：`claw4j-channel` 下只有
`spi` 与 `http` 两个包，飞书的依赖、版本、profile 都摆好了，但没有实现类。
所以 M2 是"票都关了、里程碑没关"。

而在接第二个通道**之前**，还有三处缺陷必须先修，因为它们的后果会被"通道进来的是陌生人"放大：

1. **子 Agent 的白名单在示例写法下静默失效。** `examples/subagents/sql-reviewer.md` 用 YAML 列表写
   `tools:`，而 front matter 用的是社区包 `MarkdownParser`——它是逐行的 `key: value` 解析器，
   `- querySales` 这种没有冒号的行被整行丢掉，于是 `tools` 的值是空串，`names()` 返回空名单，
   而 `selectTools()` 把**空名单当成"继承全部可用工具"**。结果是：示例里那个只该看一条 SQL 的
   复核员，实际拿到了整套工具（含发邮件与跑脚本）。ADR-0012 的"委派不提权"在这份定义上不成立，
   并且失败是静默的——不报错、不警告，只是权限变宽了。
2. **行数上限会让合法 SQL 变成语法错误。** `SalesSqlGuard.withRowLimit` 把原句直接拼进
   `select * from ( ... ) as claw4j_limited limit N`，中间不加换行。模型很常写以行注释结尾的 SQL
   （`-- 只看华东`），拼完之后注释把 `) as claw4j_limited limit N` 整段吃进注释里，
   合法的查询被数据库报成语法错误，而自纠错拿到的是一条**与被问的问题无关**的报错——
   ADR-0005 说"自纠错的前提是工具把数据库的原话返回给模型"，这里返回的原话是错的。
3. **路由的降级是一刀切的。** `RoutingChatModel.call` 捕获所有 `RuntimeException` 就换下一家。
   于是"参数构造错了""鉴权 401""响应解析失败"这些**换一家也不会好**的失败，会变成
   "每家都失败一遍再把几个异常捆在一起抛"，把一次确定的错误拖成 N 次网络往返；
   ADR-0006 里"主模型失败才退到备"的语义实际是"任何异常都退"。

## Solution

两段，顺序固定，不能并行：

**第一段：三处缺陷各修一处，各配一条会红的测试。** 它们都是"配置/边界写错却不报错"的类型，
所以修法的一致判据是——**把静默变显式**：白名单写不清楚就启动失败，语句拼不成就别拼，
降级只发生在"换一家可能好"的失败上。

**第二段：落飞书长连接通道，把 M2 关掉。** 形态定死为：SDK 主动外连（不要公网回调端点）、
收到事件 3 秒内 ACK、Agent 在独立线程上跑、结果用主动发消息接口回推、重推按 `eventId` 去重。
这几条不是实现偏好，是 ADR-0009 从飞书的硬约束里推出来的，也正是"四项做深"里
唯一还没演示过的那一项：**入站不等 Agent**。

用户（业务同学）看到的效果：在飞书里 @ 机器人问"上周华东区成交额多少"，几秒后群里出现一条
带数字与口径的回答；同一条消息被飞书重推两次，群里也只出现一条回答。

## User Stories

### 飞书问答

1. 作为业务同学，我希望在飞书群里 @ 机器人问一句自然语言，就能拿到库里的数，这样我不用学 SQL、也不用登后台。
2. 作为业务同学，我希望回答里带上统计口径（哪些表、排除了什么状态、时间窗怎么算），这样我能判断这个数对不对。
3. 作为业务同学，我希望机器人认出我是谁，这样我看到的数据和我有权限看的数据一致。
4. 作为没有登记过的飞书用户，我希望被明确告知"没有权限"，而不是收到一个看起来像"查不到"的空回答，这样我知道该去找谁开通。
5. 作为只读角色的同事，我希望问同一句话时拿到明确的"没有权限：不允许访问表 xxx"，这样我知道是权限问题而不是数据问题，也不是机器人坏了。
6. 作为业务同学，我希望第二轮只说"那华南呢"也能接上，不用把问题复述一遍，这样问话像跟人说话。
7. 作为业务同学，我希望同一句话被飞书重推两次时群里只有一条回答，这样不会被重复消息刷屏。
8. 作为业务同学，我希望机器人回得慢的时候也不出现"处理中"卡死或报错，这样我知道它还在跑。
9. 作为业务同学，我希望回答太长时仍然能读完（不因平台单条消息长度上限被截断），这样长口径说明不会丢。
10. 作为运维，我希望飞书事件在 3 秒内被确认，这样不会因为超时触发无限重推。
11. 作为运维，我希望机器人重复收到同一条事件时只执行一次，这样模型调用与数据库查询不会被浪费。
12. 作为运维，我希望飞书凭据缺失时这个通道干脆不装配、其它通道照常工作，这样只跑 HTTP 的部署不被拖累。
13. 作为运维，我希望凭据配了但连不上时启动直接失败，而不是带着一个"看起来在跑其实收不到消息"的通道，这样故障在启动时暴露而不是在演示时暴露。
14. 作为运维，我希望在日志里看得到"收到事件 → 已 ACK → 开始处理 → 已回推"这条链路，这样出问题能定位到是哪一段慢。
15. 作为运维，我希望这件事只支持单实例（不做假装的负载均衡），这样多实例部署时我不会误以为消息会被广播。

### 子 Agent 白名单

16. 作为写 Subagent 定义的人，我希望 `tools:` 写成 YAML 列表或逗号分隔都能被正确识别，这样我照抄示例不会出问题。
17. 作为写 Subagent 定义的人，我希望把 `tools:` 写成空的时候系统直接报错并告诉我"这是配置错误"，而不是悄悄给它全部工具，这样我的失误不会变成权限放大。
18. 作为安全评审者，我希望示例定义里的复核员拿不到发邮件与跑脚本的权限，这样"委派不提权"是可验证的而不是靠人读文档。
19. 作为写 Subagent 定义的人，我希望白名单里点了一个不存在的工具时在首次委派就失败并点名缺哪个，这样配置错误不会拖到线上。

### 只读执行

20. 作为业务同学，我希望模型写了带行注释的合法 SQL 时也能查到数，不要把语法错误当成"我写错了"。
21. 作为安全评审者，我希望行数上限那道包装仍然是"包一层子查询"（不往原句尾部拼 limit），这样模型自带的 order by / limit 不会被改坏。
22. 作为评审者，我希望所有被行上限包装过的语句都仍然只能读，这样包装这一步不会成为绕过只读约束的口子。

### 主备降级

23. 作为运维，我希望主模型超时、连接失败、429、5xx 时降级到备，这样一次抖动不至于让用户看不到回答。
24. 作为运维，我希望主模型返回 401（key 失效）或参数错误时**不要**降级，而是直接报出来并说清是哪一家的什么错，这样我不会在两个供应商之间来回撞墙。
25. 作为评审者，我希望"哪些失败算可重试"写在代码里只有一处、且被一条表驱动测试钉住，这样以后加供应商不用重新讨论一遍。

### 文档

26. 作为第一次读仓库的人，我希望 ADR 与代码现状一致（不再有"装配线还没接"这种早已过时的句子），这样我不用反复核对。
27. 作为第一次跑起来的人，我希望仓库里没有"引了但没人用"的占位（Redis 的依赖、配置、容器已一并摘除），这样我不会把它误读成"记忆存在 Redis 里"，也不会以为语义缓存已经在了。

## Implementation Decisions

### 三处缺陷

- **白名单解析不再借用社区 `MarkdownParser` 的两个键。** 依据：它是逐行 `key: value`，列表项没有
  冒号会被整行丢弃，且无法区分"没写"与"写了但读不出"。改为在本项目内解析 front matter 的
  `tools` / `disallowedTools` 两个键，同时接受 `a, b` 与 `- a` 两种写法（示例文件用的就是后者）。
- **"没写 tools"与"写了但一个名字都没解析出来"必须分开。** 前者是 ADR-0012 定义的"继承全部工具"
  （合法路径，且仍会减掉委派工具自己）；后者是配置错误，按定义错误失败并说清"`tools:` 这节
  解析不出工具名，是把列表写成了别的形状吗"。这条是缺陷①真正的修复点——不是"多支持一种写法"，
  而是**不让一个空结果被当成许可**。
- **行上限的修法：包成子查询之前，先保证原句末尾有换行**（而不是去猜注释、也不是去掉注释）。
  理由：执行的是原句，去掉注释会改变模型写的文本条件（ADR-0005 已定"执行原句"）；
  补换行既不改语义，也不需要认识 SQL 方言。断言要落在"包装后的语句在真库上能跑通"上，而不是
  落在字符串形状上。
- **降级改为按"是否可重试"分类**：连接失败/超时/429/5xx 降级；401/403/400/422 与本地构造错误不降级。
  判据统一写成一处判断（例如对一个异常分类函数的三态回答），路由只消费它，不自己识别异常类型。
  流式那条保持现有语义（首块之前才降级）不变，只把分类换上。

### 飞书通道

- **不新增模块，代码落在 `claw4j-channel` 的 `channel.feishu` 包**（ADR-0010）。依赖已在
  `claw4j-channel/pom.xml` 里以 `<optional>true</optional>` 声明、版本在父 pom 统一管理，本票只加代码。
- **拆成两层，就是为了能在默认构建里测**：
  - 纯 Java 的一层（下面统称"入站调度"）：接一条已经解析好的入站事件，负责"去重 → 立刻 ACK →
    交给 executor 跑 Agent → 用回推接口发结果"。不认识飞书 SDK 的任何类型。
  - SDK 绑定的一层：长连接客户端回调进来 → 把 SDK 的事件对象转成入站事件 → 交给入站调度；
    回推接口的实现调用飞书的消息 API。
  两层之间只有两个包内接口（入站事件、回推发送），不往 `channel.spi` 与 `domain` 加任何东西。
- **ACK 的语义是"事件线程立刻返回"**，不是"Agent 跑完了返回"。Agent 调用一律在独立的 executor 上，
  失败只影响那一条消息的回推，不能反过来阻塞事件线程。
- **去重按 `InboundMessage.eventId()`，进程内带 TTL 的缓存**。依据 ADR-0009：长连接是集群投递、
  不支持广播，单实例演示是既定形态，所以不引 Redis（Redis 的用途留给 M3 的语义缓存，见 Out of Scope）。
  重推命中时**照常 ACK 但不执行**——不 ACK 会触发下一轮重推。
- **认人**：飞书 `open_id` → `Principal`，映射写在配置里（角色 → 用户标识，与 HTTP 的角色表同一个口径），
  未登记的用户回一句"没有权限"并记 WARN。绝不"认不出就放行"，也不"认不出就静默丢弃"。
- **出站用一次性回答，不用流式**：飞书的普通消息没有 SSE，逐块更新要额外调消息更新接口并处理
  限频。本票合成一条消息发送（`AgentPort.reply`），流式增量更新列入 Out of Scope。
  超过平台单条长度上限时按段落切成多条顺序发送，切分不得把代码块或表格拦腰截断。
- **装配条件**：飞书 SDK 不在 classpath 时整个包退让（条件装配），凭据缺失时也不装配。
  理由：ADR-0010 的分层是为"只跑 HTTP 的部署"服务的，不能让它在启动时因为
  "飞书配置不完整"而失败；而凭据**配了但连不上**属于另一件事——那种必须启动失败（`ChatChannel.start`
  的既有约定：带着半死的通道跑比起不来更难排查）。
- **`-Pchannel-feishu`〔已推翻，2026-10-27〕**：原计划在 `claw4j-app` 里按 profile 把 `oapi-sdk` 声明成
  compile 依赖，channel 里保持 optional。实际交付改成**普通依赖随 channel 传递**：`-P` 只在 `mvn` 时存在，
  `java -jar` 根本没有它，漏了的现象是通道安静地不装配——又一个"要记住一个参数才生效"的机关。
  代价是只用 HTTP 的部署也带上约 28MB；`@ConditionalOnClass` 保留，依赖被误删时仍然是退让。
- **真实链路〔已推翻〕**：原计划打 `feishu-live` tag、父 pom 默认排除、`-Pfeishu-live` 才跑。
  实际交付不引入任何开关：这套开关只服务一条能被"带真凭据起一次应用"直接证伪的用例，而那次手验本身
  已经证明收发两侧都成立（群里那条"没有权限"就是 `im().message().create` 发出去的真实消息）。
  代价照实记在 guardrails：真链路之后没有自动化守着，SDK 升级或飞书改协议会静默失效。

### 记忆的边界（只记录，不改代码）

这节是为了回答"短记忆 Redis / 长记忆数据库 / 会话压缩"那套流行说法与本项目的关系。结论：**别按那套说法
再加一层存储，`spring-ai-session` 的形态与它不是一回事。**

- **本项目只用社区 `spring-ai-session`，不叠加官方 `ChatMemory`。** 两套机制都会把同一段历史拼进提示词、
  写进存储：同时开的结果是消息进两遍、存两份，压缩与清理各管一半。官方 2.0.2 BOM 里确实有
  `spring-ai-starter-model-chat-memory-repository-redis`（"短记忆放 Redis"那条路的现成实现），
  但它是 `ChatMemory` 家族的一员，与 session 的事件流不共享状态——**那是换机制，不是加缓存**。
  当前 pom 里连 Redis 客户端都没有，这是刻意的（ADR-0005 修订记录），别当成缺依赖去补。
- **`spring-ai-session` 0.10.0 的能力边界**（jar 里逐个类看过，不是猜的）：
  - 会话与事件流：`SessionRepository` 有 InMemory 与 JDBC 两个实现，JDBC 带 H2/MySQL/Postgres 三方言。
    **没有 Redis 实现**——想用 Redis 也没有可换的 bean。
  - 窗口化：`SessionMemoryAdvisor`（`eventFilter` / `messageFilter` / 事件 id 生成器 / `scheduler`）。
  - 压缩：trigger 三件（`TokenCountTrigger` / `TurnCountTrigger` / `CompositeCompactionTrigger`）×
    strategy 四件（`TokenCountCompactionStrategy` / `TurnWindowCompactionStrategy` /
    `SlidingWindowCompactionStrategy` / `RecursiveSummarizationCompactionStrategy`）。
  - 跨会话召回：`CrossSessionRecallTools`（构造时绑定 `userId`，关键词检索 + `pageSize` 分页）。
    这是"长记忆"的钩子，但**是关键词匹配，不是向量语义**。
  - 会话内检索：`SessionEventTools`；TTL：`CreateSessionRequest` 的 ttl + `deleteExpiredSessions`。
- **压缩的开关在 `SessionMemoryAdvisor.Builder` 上**（`compactionTrigger` / `compactionStrategy` 两个参数），
  **不是 yml 配置项**。本项目的 `SessionMemoryConfiguration` 一个都没设，所以压缩从未执行过——
  `FaultTolerantSessionService.compact` 那条穿透方法确实走不到。
- **`CrossSessionRecallTools` 没有注册成工具**，所以"去年那批单子怎么定的"这类跨会话回忆现在做不到。
  真要做语义召回得接 pgvector（ADR-0005 已定载体），不是把 Redis 塞进来。

### 文档债（同票处理，两行的事）

- 删掉 ADR-0010 末尾"`claw4j-capability` 尚未被 `claw4j-agent` 依赖（装配线还没接）"——早已接上。
- **会话记忆这条线已经通了，本票不碰它**（写在这里是为了别被当成缺口重做一遍）：`spring-ai-session-jdbc`
  0.10.0 已接线——`SessionMemoryConfiguration` 自建会话连接池指向 `claw4j_session` schema、
  `FaultTolerantSessionService` 包降级、`SessionMemoryAdvisor` 由 `defaultAdvisors` 收走，
  `ChatClientAgentPort` 每轮塞 `SESSION_ID` / `USER_ID`，`V3__session_schema.sql` 建表，
  `SessionMemoryTest` 11 条钉着。**Redis 在这条链上一行都不参与**（ADR-0005 明确否决过"Redis 兼做会话存储"）。
- `application.yml` 的 `spring.data.redis`、`claw4j-app/pom.xml` 的 `spring-boot-starter-data-redis`、
  compose 的 `redis` 服务**已于 2026-10-26 全部摘除**（决策与理由见 ADR-0005 修订记录）：它们当时是
  "引了、配了、代码零引用"，而记忆走 Postgres，留着只会让人反复误读成"记忆存 Redis"。
  M3 引回时的两个坑（镜像要 Redis Stack、客户端要 Jedis）记在同一处，本票不需要再处理。
- 去掉 `CLAW4J_REDIS_IMAGE`（`.env` / `.env.example`）与 README、`application-local.yml(.example)` 里
  "拉起 Postgres 与 Redis"的说法——这些是本票顺手清掉的残留，不留给下一个人去对账。

## Testing Decisions

**什么叫好测试（沿用 `docs/agents/testing.md`）**：只断言外部可观察的行为，不断言内部实现。
本次几条关键的"外部行为"分别是：群里出现几条消息、Agent 被调用了几次、ACK 什么时候返回、
数据库里那条 SQL 跑不跑得通、异常从哪一家抛出来。

**接缝（只有一个新的）**：入站调度那一层 + 一个回推发送接口。测试给一个假的发送实现
（记下发了什么）与一个可控的 executor，于是可以断言：

- 一条事件进来 → ACK 在 Agent 开始之前就已经返回；
- 同一条 `eventId` 第二次进来 → 仍然 ACK，但 Agent 只被调用一次；
- Agent 抛异常 → 群里出现的是一条说清楚的失败消息，而不是什么都没有。

SDK 绑定那一层**不写单测**：它的全部内容就是"把 SDK 对象翻译成入站事件、把文本发出去"，
两者都只有在真凭据下才有意义。它只能靠带凭据起一次应用手验，这个缺口在 guardrails 里
如实记账（照"两类沙箱都没有网络隔离"那几行的写法）。

**模块与文件配额**：缺陷①②③的测试分别加进已有文件（`SalesQueryTest`、`ModelRoutingTest`、
`SubagentDelegationTest`），**不新增文件**。飞书那部分在 `claw4j-channel` 内新增**一个**测试文件
（该模块当前 2 个文件，上限 10），方法数控制在 20 以内。

**先例**：`HttpChatChannelTest` 是"注入假 `AgentPort`、断言通道交出了什么"的现成写法，
飞书那一层照抄它的形状即可；`RealCliMcpEndToEndTest` 是 live tag 的先例。

**变异自检**（每条修复都要能被一句话打红）：把"空名单即继承"那行改回原来的写法、
把补换行那行删掉、把异常分类改回 `RuntimeException`、把 ACK 改成"处理完再返回"——
对应测试各自必须变红。

## Out of Scope

- **M3 的四项**：A2A 端点、可观测（token 计量 + Micrometer）、评估器进 CI、语义缓存。一项都不在本票。
- **会话记忆的深化**：① 压缩（给 `SessionMemoryAdvisor.Builder` 配上成对的
  `TokenCountTrigger` + `RecursiveSummarizationCompactionStrategy`——现在两个都没设，长对话会全量进提示词）；
  ② 跨会话长期记忆（两条路：先接 `CrossSessionRecallTools` 做关键词召回，再上 pgvector 做语义召回，
  载体 ADR-0005 已定）；③ 会话 TTL 从默认值改成显式策略。三项都不在 M2 验收判据里，
  **也与 Redis 无关**；放 M3 的理由很具体：压缩按 token 触发，而 token 计量正是 M3 可观测那一项，
  分开做要返工一次。
- **多实例去重**：不引 Redis 做事件去重，也不假装长连接能广播（ADR-0009 已把这条定性为限制而非缺陷）。
- **飞书富文本能力**：卡片消息、按钮回调、群聊 @ 成员解析、消息更新（editing an existing message）。
- **Telegram 作为第二通道**（ADR-0009 列为可选，不阻塞任何验收判据）。
- **ADR-0001 留下的工具检索评估**（`spring-ai-tool-search-advisor`）：与飞书无关，另立一票。
- 三处缺陷之外的其他代码问题。

## Further Notes

- **前置条件**：飞书自建应用（App ID / App Secret）+ 机器人被拉进一个群。ADR-0009 的事实核查
  结论是个人账号可开通、无需企业认证。没有凭据时本票仍可交付到"假事件源下 ACK/去重/回推成立"，
  真实链路只能靠带凭据起一次应用手验——交付时要说清这一档，不把"没跑过真链路"说成"跑通了"。
- **凭据落地方式**：`FEISHU_APP_ID` / `FEISHU_APP_SECRET` 走环境变量（与模型 key 同一姿势，
  统一进 `.env`），不进 `SKILL.md`、不进仓库（ADR-0002 的收口原则）。
- **为什么先修缺陷再上通道**：三处缺陷里有两处是"边界比写在纸面上的宽"。通道进来的是真人之后，
  "宽"的后果从"演示时模型多调了一个工具"变成"某个真实用户拿到了不该看的数据"。
  这个顺序不是排期偏好，是风险排序。
- 通道加完，ADR-0009 里"3 秒内 ACK → 异步编排 → 主动回推"这条就从"设计"变成"可运行、可演示"，
  M2 的验收判据同时补齐；之后 M3 的第一项（可观测）才有意义——没有第二通道，
  token 计量只能对着 curl 讲。
