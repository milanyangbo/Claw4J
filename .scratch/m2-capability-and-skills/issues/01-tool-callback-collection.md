# 01: 工具装配改成收集所有 ToolCallback —— 三层能力的共同入口

**What to build:** 今天能力层只导出一个工具来源，而且它的注册条件按"整个 provider 缺失"来判。再加第二个来源（MCP、Script Package、Skills）时，第二个 provider 会让位，工具**静默消失**——失效姿势是"模型手上没有这个工具，于是它开始编答案"，从聊天界面上完全看不出来（这条坑已经写在提供工具的那个自动配置的类注释上）。这张票先把装配改成收集容器内所有 `ToolCallback` / `ToolCallbackProvider`，让"加一种能力"变成往容器里多放一个回调。

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

**Demo:** 起应用，两个不同来源的工具（现有的 `querySales` 加本票新增的一个最小假工具）同时出现在模型可见的工具清单里，两个都调得到；把其中一个来源的注册去掉，有一条断言立刻红。

- [ ] 装配改为收集容器内所有 `ToolCallback` / `ToolCallbackProvider`，不再按"单个 provider 缺失"判条件
- [ ] 一条断言钉住"容器里到底有哪些工具"（含现有的 `querySales`）—— 少一个工具必须红，不能靠人发现模型变笨了
- [ ] 两个来源同时存在时都在清单里；去掉第一个来源的注册 → 对应断言红（变异检验）
- [ ] 只有一个来源时行为与今天一致：M1 的 177 个测试仍全绿
- [ ] 工具权限的登记规则不变：漏登记一律按拒绝（GLOSSARY 的"工具权限"）
- [ ] 调用预算（每工具 3 / 整轮 6）在多来源下仍生效 —— M1 那条"换了 builder 会静默退回 40/150"的断言仍然绿

**注意:** 这是 prefactor，不是能力。它本身不交付任何用户可见的新能力，交付的是"后面三张票能各自加一种能力而不互相踩"。做完它之前不要开始 02 / 03 / 04。

**不要做:** 不要在这张票里引 MCP 或脚本依赖，也不要决定 Skill 目录长什么样。
