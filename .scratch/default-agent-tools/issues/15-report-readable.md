# 票 15：报告要能自己读懂——指标、档位、达标线，加上按分类

**Status:** resolved

> 依赖票 12（`run_ir.py` 与门槛）、票 13（题库与分档实测）。

## 由来

用户原话：**"report.md 本身也写得太简单，我也看不懂，什么很多指标不明白什么意思，R@5、
hybrid-0.0（后面的 0.0 什么意思），怎么样算达标等等"**。

现在的 `report.md` 只有：时间、判定、一行零候选率、一张总表。它假设读者已经知道
`R@5` 是什么、`hybrid-0.5` 的 0.5 是什么、门槛在哪。写这份报告的是我，读的人不是——
这就是缺陷，不是"文档可以再补补"。

票 13 里还有一件事悬着：**分档表要手算**（临时脚本切 qrels/run 再喂 `ir_measures`）。
"这一档掉到 0.1"这种判断只能靠手算，等于每次都得有我在。

## 裁决

无需 ADR：只改评测产物与它的生成脚本，不动线上行为。

## 报告要回答的四件事

1. **这次测的是什么**：多少题、多少工具、检索几次、有没有调模型（一句"不调、零成本"）。
2. **每个指标是什么意思**：`R@1` / `R@3` / `R@5` / `RR` / `nDCG@10` 各一句大白话 +
   一个"读它的时候注意什么"。用具体例子算给读者看（例如"5 题里 2 题在前 5 名 → R@5 = 0.4"）。
3. **每档配置是什么**：`hybrid-0.5` 后面那个数是**关键字那一路的权重**（0 = 纯向量，
   1 = 纯关键字 = `regex`）。这一条用户明确问到了，必须写进报告而不只是写在 `application.yml` 里。
4. **怎么算达标**：回归门（`R@5` 不低于基线 − 0.05）、零候选率的门、没有基线的档怎么显示、
   退出码 0/1/2 各意味着什么。

外加一张**按分类**的表：`base` / `business` / `zh-en` / `no-search` 各一行，每档一句"它坏了说明什么"。

## 数据从哪来

分类信息现在只在 Java 手里（`ToolGold.category()`）。两条路：

- 让 Java 导出时多写一份 `reports/categories.txt`（`qid<TAB>category`），`run_ir.py` 按它分组；
- 或者 Python 装 `pyyaml` 直接读 `gold.yaml`。

选**前者**：多一个依赖只为读一份自己刚写的文件不划算，而且 Python 会多掌握一份"分类有哪些"的
真相——两份真相就会漂。Java 那边加一条断言：**categories 必须覆盖题库里每一条**，漏一条当场红。

分档指标仍交给 `ir_measures`（把 qrels / run 各切一份再 `calc_aggregate`），不另写公式：
两个实现已经够多了。

## TDD 用例清单

| 判什么行为 | 用例 | 先红的样子 |
| --- | --- | --- |
| categories 覆盖题库每一条 | ✅ `ToolRetrievalExportTest#categoriesCoverEveryQuestion` | 只写有 gold 的题时，`no-search` 那两条缺失，断言红 |
| 分类只允许题库里的四个 | ✅ 同上（值域断言） | 打错一个字（`zh_en`）时红，否则那一档在报告里静默消失 |
| 报告里有每档配置的说明与判定规则 | ⏳ `./eval/tools/run.sh --from-report` 后 `grep -c 'hybrid-0.5' reports/report.md` ≥ 2、`grep -c '^## 怎么算达标'` = 1（脚本级，不进 Java 门禁） | 只改表不改说明时，`hybrid-0.5` 的 0.5 又变成没人解释的数 |
| 报告里有按分类的两张表 | ⏳ 同上，`grep -c '^## 按分类'` = 2（R@5 与 R@1） | 生成器只吐总表时红 |

后两条是脚本行为，验法是 shell 断言；写进票面是为了记住它们必须被验，与票 12 的第四条同一种处理。
**没做成自动脚本**：要自动化得再引一个 shell 测试入口，而这两条改一次就不用再动（与票 12 的
第四条同一个理由）。手验命令就是上面那两条 `grep`。

复核：2026-11-26 `./eval/tools/run.sh`（导出 5 条全绿，退出 0）+
`./eval/tools/run.sh --from-report`（退出 0），`report.md` 含四节 + 两张分档表。

## 落地时与票面不同的两处（据实改）

1. **多导出一个 `catalogue.txt`**（一行一个工具名，19 行）。报告里那句"工具目录 N 个"要有出处；
   顺带排障时能一眼看出"某个工具到底装上了没"（票 13 那两批死题就是这类问题）。
2. **分档用的是 `R@5` 与 `R@1` 两张表**，不是一张。`zh-en` 那一档关键字 `R@1` 是 0.000、
   纯向量 0.200，`R@1` 的区分度比 `R@5` 更明显；只放 `R@5` 会看不出"第一名全错"这件事。

## 缺口（本票不做）

- **不出图**：报告是给终端与 diff 看的，一张 PNG 不能进 git diff。
- **不做历史趋势**：`baseline.json` 只记"上一次被接受的"，要曲线得先决定存哪（另一张票）。
- **不解释 `nDCG` 的公式推导**：只给"越靠前加分越多"和"和 ToolRet 同口径"两句，
  真要看公式的读者该去读 `ir_measures` 的文档。
