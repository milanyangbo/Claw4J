# 票 05：基础工具藏在检索后面，而检索要"猜中词"才给

**Status:** resolved

> 修法不在这张票：露出策略（常驻 / 阈值 / namespace）在票 06，索引用 `hybrid` 在票 07。
> 本票留着当证据——那两组受控实验的数字是 06 的由来。

## 由来

用户在 2026-11-25 看 `README-capability-tests.md` 时连着指出两处：C5 写"先用工具检索找到
WebFetch"，B2 写"用 Glob 找…""用 Read 读…""用 Grep 搜…"。他的问题不是措辞不好看：

> 我随便找了几个，这样的问法是不是都有问题啊，就是把 tool 的名称明确写着提问里面了

**都有问题。** 但把题目改成人话之后，能不能验过取决于一个我们没写进任何文档的条件。

## 实测（2026-11-26 00:3x–01:0x，`claw4j_accept_1125`，ops 人设，jar 含票 04）

受控：同一句话重复 N 次，每次换用户（不同会话），只看"有没有拿到真实文件列表"。

| 问法 | 次数 | 结果 |
| --- | --- | --- |
| `examples 目录下有哪些 .md 文件？`（**没有绝对路径**） | 5 | **0/5** |
| `<绝对路径>/examples 目录下有哪些 .md 文件？` | 3 | 3/3 |
| `列出 <绝对路径>/examples 下的 markdown 文件`（全中文） | 3 | 3/3 |
| `list all .md files under <绝对路径>/examples`（全英文） | 1 | 1/1 |
| `<绝对路径>/examples 里哪些地方提到了 refund？`（Grep） | 3 | **2/3** |
| `<绝对路径>/examples/README.md 的前 6 行是什么`（Read） | 2 | 2/2 |
| `用 Grep 工具在 <绝对路径>/examples 里搜 refund`（点名） | 1 | 1/1 |

## 根因（先前判断错了，这两条是修正后的）

**我先前的结论是"描述是英文、中文匹配不上"，被上面第二行推翻**：全中文带路径 3/3 通过，
有没有路径才是分水岭。准确的说法是两条：

1. **触发靠信号，不靠语义**。检索提示词里列了"网址、文件路径、命令…"这类信号，模型看到
   **绝对路径**才去检索。用户说"examples 目录下有哪些 md"（相对描述）时它不检索，直接答
   "没有能列目录的工具"——5/5 一致，不是偶发。
2. **检索是词面匹配，命中带随机**。检索词是模型每轮自己写的，同一个意图两次可以写出不同的词，
   于是 Grep 那条 2/3。描述是英文这件事**加重**了这个不稳定（中文二元组很难撞上英文词），
   票 04 给网页族搭的桥就是补这个；但它不是主因——否则全中文带路径那组不可能 3/3。

一句话：**能力可达性取决于"用户话里有没有我们恰好写进提示词的信号"和"模型这轮猜的词碰巧命中"，
两件都不该是用户承担的东西。**

## 行业怎么做（2026-11 查证）

三家原生都上了"按需加载"，但**没有一家是"全藏"**：

| | 机制 | 常驻什么 | 检索什么 |
| --- | --- | --- | --- |
| Anthropic（Tool Search Tool，2025-11-24） | 逐工具 `defer_loading: true`；检索有 regex 与 BM25 两版 | **核心内置工具（Bash / Read / Edit 等）默认 upfront 加载，且不计入"延迟比例"阈值** | MCP 与自定义工具；一次返回默认 5 个 |
| OpenAI（Responses API，gpt-5.4+） | `{"type":"tool_search"}` + `defer_loading` | 常用函数常驻 | 按 namespace 组织，建议每个 namespace < 10 个函数 |
| Gemini（Interactions API，2026-11-19 预览） | 同名字段 | **被延迟的工具仍然暴露"名字 + 描述"，只把参数 schema 挡在外面** | 模型按名索取 schema |

三条可直接引用的官方口径：

1. **Anthropic 的 SDK 把 Bash / Read / Edit 这类内置工具算作 core，upfront 加载，且不参与
   "延迟工具占上下文 10% 才启用检索"那个阈值计算**（Claude Agent SDK 文档 *Scale to many tools
   with tool search*）。**本仓库恰好把这三个也塞进了检索——这是与基线最大的一处偏离。**
2. **少于 ~10 个工具时不要用检索**，全量加载通常更快。我们现在的部署是 20–30 个（业务工具 +
   MCP + 技能 + 子 Agent），正落在"该混合"的区间，而不是"全检索"。
3. **检索治不了"描述写得烂"**：Anthropic 明确说检索是在名字与描述上跑的，`do_action` 加一行
   描述的工具怎么搜都搜不到；建议"用用户真正会说的词写描述"，并在系统提示里说明"存在哪几类
   工具"。也就是说 **prompt 优化是官方也主张的一步，但它的作用是"让模型愿意去检索"，
   不是"让模型知道清单里有什么"。**

另一种被官方采纳的折中（Gemini 那一路）：**名字 + 描述常驻，schema 延迟**。token 省在 schema 上，
而模型始终知道自己有哪些能力——它同时解掉了本票的两条根因，成本比"全常驻"低。

## 结论：这不该是 A/B 二选一

行业基线是**分层 + 描述质量 + 提示词**三件一起，不是选一条路。我们缺的是第一件，而且缺得最要紧：

- 基础工具常驻（对齐 Anthropic 的 core 判定）；长尾继续 defer + 检索。
- 描述要能被用户的话命中（框架自带的是英文，需要一层中文包装，或换语义索引）。
- 提示词继续当"催化剂"（票 04 已做），但不指望它替代清单。

## 两条候选路（保留作记录，已被上面那节取代）

**A. 高频基础工具常驻，检索只管长尾（建议）**

`Read / Glob / Grep / Write / Edit / Bash / WebFetch / WebSearch` 直接进每轮清单；检索留给
业务工具、MCP、技能、子 Agent——这些才会随部署越装越多。

- 收益确定：上面两条根因同时消失，不需要任何信号，也不靠猜词。
- 成本：每轮多约 8 个工具（几百 token），是**固定值**，不随工具集增长恶化。
- 需要 ADR-0021 记一笔：渐进式披露的边界从"全部工具"缩到"长尾工具"。

**B. 换向量索引（`index=vector`）**

治第 2 条（词面 → 语义），治不了第 1 条：模型仍然要先"想到去检索"。要它想到，还是得让它看见
一部分清单。所以 B 单独做不够，除非同时放宽触发条件到"任何要动手的请求"——而那就是"每轮都
检索一次"，成本比 A 更高且对简单对话是浪费。

## 不做什么

- 不继续往同义词表里加文件族（`目录→directory`、`搜→search`…）。上面第 2 条已经说明问题不在
  某一个词，这张表是手写的、工具描述一改就静默失效（票 04 的注释里写过维护代价）。
- 不改文档把 B2 写成"必须点名工具"。那等于承认"模型自己选不对"，而这一节验的正是这个。

## 待定

A 还是 B（或 A+B），定了再改代码与文档。用户已明确：**文档等策略定了一起改**，现在不动。
