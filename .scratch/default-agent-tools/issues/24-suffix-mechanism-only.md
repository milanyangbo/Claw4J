## 一、行业里的四条真文本

> 出处分两类。**一手**的是能直接读到的原文（jar 源码、文档里的字段）；**二手**是别人转述的，
> 字面可信但在这台机器上复核不了。

### 1. Claude Code 的运行时注入（`ToolSearch` 那一层）｜二手

> The following deferred tools are now available via ToolSearch. Their schemas are NOT loaded —
> calling them directly will fail. Use ToolSearch with query `"select:<name>"` to load tool schemas
> before calling them:

后面跟一串工具名。**两句半**：现在的状态（定义未加载）、直接调的后果（会失败）、怎么用（带上名字）。

### 2. OpenAI 客户端执行的 `tool_search`（`description` 字段）｜一手（官方文档示例代码）

> Find the project-specific tools needed to continue the task.

**一句。** 没有"必须"，没有"凡是要用工具的事"，没有反例。

### 3. Spring AI 自带的 `ToolSearchTool` 描述（我们本来就有这一层）｜一手（`spring-ai-tool-search-tool` jar 源码）

> Search for tools in the tool registry to discover capabilities for completing the current task.
> Use this when you need functionality not provided by your currently available tools.
> The search queries against tool names, descriptions, and parameter information to find the most
> relevant tools.
> Returns references to matching tools which will be expanded into full definitions you can then invoke.

**四句**，全是陈述句。注意第二句把"什么时候用"定义成**能力缺口**（not provided by your currently
available tools），不是"凡是能办的事"。

### 4. Anthropic 的定位：这段不该由你写｜二手（工程博客，经中文转述）

Tool Search Tool 是 hosted tool，自带描述；官方给的适用判断是**机制量**（工具 10+ 个、定义超
10k tokens、多 MCP server），不是提示词量。转述里给的收益是"token 降 85%"，但那**不是**
"选错工具变少"——两个指标，转述没分别给数，只能当方向读。含义是：**要不要检索由配置决定，
不由提示词劝**。

**共同形状**：陈述机制（有什么、会怎样、怎么用）／不陈述义务／不举动作例子／不列例外清单／1–4 句。

## 三、为什么分两刀：票 04 会被第二刀撤掉

下面是这轮核对里最该先说的一件事。

**"给网址/文件路径就是要用工具"那句清单，是票 04 的修复本身。** 票 04 的根因写得很明白：

> 2. **提示词把检索限定在业务动作上**：原文是"遇到查数、统计、比对这类业务问题时，先检索一次"，
>    模型读成"业务问题才检索"，于是"看个网页""读个文件"直接判为"我没有这个能力"。

修法之一就是把触发条件从"业务问题"扩到"给了网址、文件路径、命令"。而**守它的只有四条断言**
（`ModelAndToolSelectionTest` 545–548：`contains("网址")`、`contains("文件路径")`）——
没有任何评测量"给了网址却不查"。所以第二刀删掉那句，等于撤票 04 的修复，而我没有手段证明没撤坏。

分刀：

| 刀 | 改什么 | 有没有证据 | 风险 |
| --- | --- | --- | --- |
| **第一刀** | 删两个动作例子 + "不用拆关键词" | 有：L2 里 A 比 B 多的 4 条全是 `recall_session`，而这两句正好把"查历史""看网页"教给了模型 | 低。唯一没量的是"检索 query 变差"——但 `gold.yaml` 的题是人写的，不是模型生成的 query，本来就不覆盖 |
| **第二刀** | 删义务句、触发器清单、例外清单，压成 3 句 | 只有形状证据（行业都这么写），**没有本项目的效果证据** | 高。撤票 04，且当前没有量"该查不查"的手段 |

## 缺口

- **噪声比效应大**：BFCL 同代码两跑差 0.4–0.8pt，L2 60 题一格 1.7pt。所以第一刀的判据只能是
  "`recall_session` 从 4 条降到几条"这种计数，不能是"准确率涨了零点几"。
- **例子删了之后 query 质量没人量**：gold 是人写的问句，检索评测不覆盖模型自己写的 query。
  要量得先有一份"模型生成的 query → 是否命中 gold"的数据，本票不做。
- **第二刀缺的不是措辞而是量具**：`eval/tools/selection` 现在只有"不该调"的题；没有"该调"的题，
  义务句删不删就只能靠读起来像不像行业，那不是判据。
- **`ToolSearchTool` 的描述仍是 Spring AI 的**：行业主流位置是写在工具描述里，我们改不了框架
  那份。要挪过去得换掉 `ToolCallback`，收益不明、风险不小，本票不碰。

用户当天把两刀合成一刀做（「提示词还是需要的，就跟 rag 一样不要乱回答问题」），新文本四句：

```
**你一开始只看得见 toolSearchTool 一个工具；其余工具都存在，只是定义还没加载——看不到不代表没有这个能力。**
要用的时候先检索，命中之后那些工具才会变得可调用。
**检索之后仍然没有能用的工具，就直接说明情况，不要拿相近的工具硬做；参数不全就问用户，不要猜。**
检索时说清你要什么能力就行，不必拆关键词，中文英文都认。
```

四句对应：状态（含 A07 锚点）／怎么用／**许可**（行业标准的核心，等价于 BFCL prompt 形态里那句
"If none of the functions can be used, point it out"）／查询怎么写。

第三句是这次真正新增的东西：它**不是**"少用工具"的劝说，而是给模型一个合法的出口。
证据是同一模型换到带这句话的形态后 irrelevance 从 76.25% 到 88.75%（票 23），
但那两组还混着"调用形态"这个变量，所以那句话单独值多少**没量**。

### 票 04 的触发器清单为什么可以删

原句「用户给了网址、文件路径、要跑的命令…就是要用工具」是票 04 的修复。删它的依据不是"行业没这么写"，
而是**票 10 之后那批工具已经常驻**：`application.yml` 的 `pinned` 是
`[Read, Grep, Glob, Bash, WebFetch, TodoWrite]`，票 04 的四个场景（网址→WebFetch、文件路径→Read）
现在都不经过检索，清单对它们已经不起作用。这条路仍有 `pinnedToolsAreAlwaysVisible` 守着。

**未做的**：没有量。改完只跑了 `ModelAndToolSelectionTest`（绿）。要看效果必须有一组端到端数据，
而 `eval/tools/selection` 已删；BFCL 又是裸模型口径、读不到我们的提示词。

## 第一次量（2026-11-26 23:07）：63.33%，但这个数不能用——混淆被证实

做法：`patch/__init__.py` 加了 `CLAW4J_BFCL_SYSTEM_PROMPT_FILE`，在 FC 形态的
`add_first_turn_message_FC` 里把整段 `SYSTEM_SUFFIX` 作为 system message 注入（BFCL 的 FC 形态本来
不传任何 system message），240 题跑一遍。**非榜单口径**，产物在 `stale-20261126/non_live/*-fc-oursuffix.json`。

| | 裸跑 | 注入我们的整段 suffix |
| --- | --- | --- |
| `irrelevance` | 76.25%（183/240） | **63.33%**（152/240） |
| `simple_python` | 95.25% | 94.00% |

**拆开后原因一目了然**（按调用目标分）：

| | 调了给定函数 | 调 `toolSearchTool`（BFCL 里不存在） |
| --- | --- | --- |
| 裸跑 | 78 次 / 57 题错 | **0 次** |
| 注入 | 73 次 / 88 题错 | **34 次** |

我们的提示词第一句是"你一开始只看得见 toolSearchTool 一个工具"——这在我们的运行时是真的，
在 BFCL 是假的（那儿只有一个具体函数，没有检索工具）。模型照做，去调了 `toolSearchTool`
（`irrelevance_10` 的原样输出：`{"toolSearchTool": {"query": "compute derivative…"}}`）。

所以 63.33% 量的是"指令和场景冲突"，不是"提示词有害"。

**唯一有用的信号**：对**给定函数**的误调从 78 次降到 73 次。方向与"许可句"预期一致，
但幅度在噪声边缘（5 次调用 ≈ 2 个题），不能当结论。

要干净地量那句许可，只能只注入第三句（"检索之后仍然没有能用的工具，就直接说明情况，
不要拿相近的工具硬做"），把与工具面绑定的两句去掉。**那是第二次跑，需要用户点头。**

## 第二次量（2026-11-26 23:14）：只注入那句约束 → 89.58%

用户的指正定了这一版的结构：**工具取回来之后，"你只看得见检索工具"这句话就是假的**，
而系统消息会跟着工具循环进到后面每一轮（`doInitializeLoop` 一轮只跑一次，把 suffix 拼到
system message 上，之后每轮都带着它）。所以那句话不是"措辞不好"，是**只在检索之前成立**。

改法不是按轮次增删，而是换成**任何时刻都成立**的说法：

```
**工具不止眼前这些：需要的能力不在这里，就用 toolSearchTool 取出来。**
**取不到就直接说明，不要拿相近的工具硬做；参数不全就问用户，不要猜。**
检索时说清你要什么能力就行，不必拆关键词，中文英文都认。
```

量的时候只注入第二句（BFCL 里没有检索工具，写"取不到"会让模型去找它）：

```
**没有能用的工具就直接说明，不要拿相近的工具硬做；参数不全就问用户，不要猜。**
```

| 配置 | `irrelevance` | 错误题 | `simple_python` |
| --- | --- | --- | --- |
| 裸跑（BFCL 官方口径） | 76.25% | 57 | 95.25% |
| 注入整段旧 suffix | 63.33% | 88（含 34 次调 toolSearchTool） | 94.00% |
| **只注入约束句** | **89.58%**（215/240） | **25**（0 次 toolSearchTool） | 94.25% |

三件事：

1. **那句话确实值 13.3 个点**：57 题错降到 25 题错（−56%）。
2. **仍差 1 题到 90%**（216/240）。而 FC 同配置重跑的噪声就是 1–2 题——**这个门的分辨率仍然细于噪声**，
   89.58 既不能说达标，也不能说不达标。
3. **代价 1 个点**：`simple_python` 95.25 → 94.25，跌破 95 的绝对门。方向与 When2Tool 的结论一致
   （抑制是不分难度的），但幅度远小于它报的"hard 掉 20 个点"。

产物在 `stale-20261126/non_live/*-fc-constraint.json`；`result/` 里的仍是裸跑那份，基线不动。
