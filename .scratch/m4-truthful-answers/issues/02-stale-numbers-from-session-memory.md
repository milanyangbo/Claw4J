# 02: 模型抄会话记忆里的旧数字，不查库

**What to build:** 无。这条票记的是**决定不做**，以及为什么不做。

**Status:** resolved（wontfix，2026-10-27）

## 现象与证据（2026-10-27，同一份数据、7 次提问）

| 提问 | 回答 | 真值 | 工具调用 |
| --- | --- | --- | --- |
| 上周华东区成交额多少 | 128,400.00 | **99,999.00** | 1 次（7 次提问合计） |
| 上周华南区成交额多少 | 26,000.00 | 上周华南**无单** | — |
| 上上周华东区成交额多少 | 128,400.00（自报窗口 10-05~10-12，整体滑了一周） | 128,400.00（那是 10-12~10-19） | — |

源头在会话表，四天前的正确记录：

```
seq 20  10-23 10:09  USER       上周华东区成交额多少
seq 21  10-23 10:09  ASSISTANT  上周华东区成交额为 128,400.00 元。      ← 10-23 当天这是对的
seq 693 10-24 12:20  ASSISTANT  上周成交额（2026-10-12 ~ 2026-10-19）华东：128,400.00 华南：26,000.00
```

## 为什么这不是缓存的问题

- 语义缓存**有 TTL**（`claw4j.cache.time-to-live: PT1H`），`SemanticCacheCleanup` 每小时真删过期行。
- **LRU/LFU 在这里不适用**：语义缓存不是精确键命中，命中靠最近邻检索；淘汰策略解决的是"表存不下了"，
  而这里的问题是"存进去的答案本身过期了"。表里一共几十行，容量从来不是瓶颈。
- 关掉缓存也不解决：模型照样会从**会话记忆**（TTL 30 天）里念。缓存只是把错误固定了一小时。

## 为什么不修

**1. 框架没有这个能力，而这是判断依据。** 查过 Spring AI 2.0.2 的 `SemanticCacheAdvisor`（反编译字节码）：

```java
String query = extractUserText(request);
String ctx   = extractContextHash(request);         // SHA-256(系统提示词)，private，无扩展点
Optional<ChatResponse> hit = cache.get(query, ctx);
if (hit.isPresent()) return 直接返回缓存;            // 不做任何"这答案还新不新"的判断
ChatClientResponse resp = chain.nextCall(request);
if (resp.chatResponse() != null) cache.set(query, resp.chatResponse(), ctx);  // 无条件写
```

整个链路里没有"回答里的数字是否过期"这个概念。`ChatMemory` 侧同样没有——
`spring-ai-session` 只有 TTL（我们配了 30 天），没有"数值类事实不得复用"的语义。
框架不管，我们也不管，这是这条票的结论。

**2. 原方案（A：提示词硬规则"带数字必须本轮查库"）本身就是错的，不只是弱。**
"带数字"在真实对话里无法界定：

- "我刚才问的三个问题是什么"——数字是序号，不该查库；
- "去年和前年比呢"——历史对比就该用历史数据；
- "口径里的 100% 是怎么算的"——数字来自文档，不是查库；
- "你说的是 128400 还是 128,400"——同一个数的两种写法。

一条正则、一句提示词都覆盖不了。真要做，得先有"什么算业务事实"的语义层，
那是另一个功能，不是一个补丁。

**3. 它挡不住的东西比它挡住的更值钱。** 即便加上硬规则，模型仍可以在
"查了库但读错窗口"或"查了库但引用了工具返回里的旧窗口"这两种情况下给出错数字。
把"不许抄历史"当成答案，会让人以为问题解决了。

## 现在的补偿

- **偏差已记账**：`docs/agents/guardrails.md` 的已知偏差表里有这一行，
  写明"会话记忆 TTL 30 天，模型可能复述历史里的数字"。评审时不该再当缺陷报。
- **缓存不是放大器**：TTL 1 小时 + `sameEntities` 守卫，错误的传播范围被限制在
  "同一个权限、同一小时内、时间词与数字完全相同的问题"。
- **可观测**：`claw4j.tool.calls{tool=querySales}` 能看出"这一轮到底查没查库"，
  排查时先看它，别看回答。

## 如果将来真要做

方向不是"提示词加一句"，而是**让时间窗由工具给出、并且回答必须引用它**：
`querySales` 的返回值里带 `{"window": "...", "queried_at": "..."}`，
提示词要求回答里引用这个窗口。模型那时有现成的句子可抄，不需要自己算，
也不需要判断"这个数字算不算业务事实"。

它仍然不是强约束（模型还能不引用），但至少**判据在数据里，不在文本里**。
真要做到强约束，得在出站前做一次"回答里的数字能否在工具返回里找到"的核对——
那是个独立功能，代价远超这条票。
