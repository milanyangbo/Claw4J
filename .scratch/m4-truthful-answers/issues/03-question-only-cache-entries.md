# 03: 纯问答也会进语义缓存

**What to build:** 无。这条票记的是一个**决定不做**的结论，以及为什么。

**Status:** resolved（wontfix）

**问题**：2026-10-27 的试验里，"你好，你能做什么"进了 `claw4j_cache.semantic`（id=11），
跟着留一小时。它不是"查得到数的答案"，内容还会随版本变化。

**为什么不处理**：

1. **框架也不区分。** Spring AI 2.0 的 `SemanticCacheAdvisor`（`org.springframework.ai.chat.cache.semantic`，
   2.0.0-M2 起）同样只按 相似度 + `contextHash` + TTL 判断，没有"这一轮调没调工具"的概念。
   自己加一条，等于把一个特例塞进框架将来可能统一解决的地方。
2. **收益只有"少存几行"。** `sideEffectFree` 对空集合返回 true 是刻意的默认——
   没调工具就是没有外部状态参与，缓存它在语义上没错，只是没用。
3. **真有困扰有更直接的旋钮**：调小 `claw4j.cache.time-to-live`（比如 PT10M）。
   把"缓存多久"和"什么样的回答能缓存"拆成两个开关，比合成一条特例好调。

**如果将来要改**：改动点是 `CacheAdvisor.remember` 里加一个"这一轮至少调用过一个工具"的前置判断。
它需要和 `ToolCallLog` 一起测，否则失效姿势是静默的（"什么都没缓存"或"什么都缓存"）。
现在没有这个需求，不加。

**同一类的第二笔**：2026-10-27 的真链路里，`guest` 那轮被鉴权拒绝的回答
（"没有权限：角色 guest 不允许访问表 …"）也被写进了缓存（id=15，在 guest 自己的指纹下）。
如果有人当天给 guest 加了权限，一小时内他还会拿到那句"没有权限"。同样不处理——
自愈时间就是 TTL（1 小时），而"拒绝"被缓存本身不会泄露任何数据。
