# 会话：一段对话什么时候结束、能不能同时进来两条

## Problem Statement

72 张票全部收口、门禁全绿，但"会话"这个词在系统里有四个定义、四个使用者
（ADR-0026 的 Context 那张表）。表现是三个用户能看见的症状：

1. **定时任务跑进了用户的聊天记录。** 早上九点那次任务的问答与用户自己的对话落在同一段会话里，
   还共用同一份额度。用户一次工具都没调，下一句却被回"预算用尽"。
2. **连发两句话，第二句不接第一句。** 提示词在 `SessionMemoryAdvisor.before` 就拼好了，
   而第一条的答案在 `after` 才落库；两条消息各自开 run、并行跑，第二句的上下文里没有第一句的结果。
   顺带把预算的"读→判→扣"（`RunBudget:90-100`）变成一次并发超发。
3. **一段对话没有"结束"这个动作。** web 端 `chatId` 缺省等于 userId，所以一个人只有一段会话；
   它不会因为空闲或跨天而结束，只会在第 30 天被后台任务删掉（删行，不是换对话）。

这三条的共同点与 A08 那次一样：**不是代码写错了，是把一个单位的语义交给了顺手能拿到的那把键。**

## Solution

五张票，顺序有依赖。判据全部是"反例跑出来的红"，不用评测集——这是正确性问题，不是效果问题。

| 票 | 事 | 依赖 | 性质 |
| --- | --- | --- | --- |
| 01 | 会话段与指针：一段对话有开始也有结束，结束 = 换新段 | 无 | 决定一（ADR-0026） |
| 02 | 一段对话同时只有一个 run：lane 按"对话地址"加锁 | 01 | 决定二 |
| 03 | 定时任务用自己的会话，每次运行新段 | 01 | 决定三（修正 P04/P05） |
| 04 | TTL 只删旧段；`/new` 手动结束 | 01、02 | 决定一的收尾 |
| 05 | 压缩窗口从配置读，并在启动时打出来 | 无 | 参数，最小的一张 |

01 与 02 必须连着做：没有 lane，"段只轮换一次"没有保证（两条消息可能同时判定过期、同时换段）。

## 边界与判据

### 票 01 段与指针

一段对话的身份从 `claw4j:user:<owner>:<通道>:<chatId>` 变成末尾多一段。段的轮换由
`claw4j.session.reset.*` 决定：每日（`at-hour`，默认 4，时区 `claw4j.agent.zone`）或空闲
（`idle-minutes`，默认 120），谁先到算谁。**`idle` 只有这一处定义**——`claw4j.run.budget.idle-minutes`
必须删掉或指向同一个值，否则又是"两处写同一件事"。

判据：同一天连续两条的 sessionId 相等；空闲超过阈值后不相等；跨过 `at-hour` 不相等；
并发两条只轮换一次（段一致，`touched_at` 只有一次写）。

### 票 02 lane

按"对话地址"（owner + 通道 + chatId）拿 lane，拿不到就排队。**不做全局并发上限**——
那是 A12 的容量问题，不是正确性问题（ADR-0026 决定二）。

判据：同一 `chatId` 并发两条，第二条的提示词里必须含第一条的回答。旧代码上必红。

### 票 03 定时任务

`InboundMessage` 加一个"会话标识"字段（null = 用 chatId 派生），定时任务传 `cron:<taskId>:<本次时刻>`。
**不能直接把 `chatId` 改成 cron 键**：`chatId` 同时是投递地址，改了审批卡片会推到不存在的地方。
投递仍用 `chatId`，会话用新字段——这正是这条发现要拆开的两件事。

判据：同一 chatId 建任务并触发，`count(distinct session_id) = 2`，且定时那条不含用户 chatId；
两次运行之间不共享历史（第二次的提示词里没有第一次的问答）。

### 票 04 会话清理与 /new

照 OpenClaw 的 `session.maintenance` 重做（2026-11-06 修订）：删除判据从"建了多久"改成
**"多久没动"**，`mode`（默认 `warn`）/ `prune-after`（30d）/ `max-entries`（500）三个键照它的名字与语义，
cron 那一路单独按 `session-retention`（24h）留。没有手动清理入口，只有每小时一次。
`/new` 是一条**消息命令**（`/new` / `/reset`，剩下的内容透传为新段第一句），在 agent 侧解析，
所以所有通道自动都有；IM 侧不需要单独做。

判据：桶过期段一起清、活跃桶的旧段照删而当前段留着、`warn` 一行不删但数得出来、
`maxEntries` 驱逐最久没动的、cron 的 24h 与普通的 30 天不互相串、`/new` 之后段立刻换。

### 票 05 压缩窗口

判据：`claw4j.session.context-window` 写在 `application.yml` 里，启动日志打一行"窗口 / 触发阈值"。

## 与既有票的关系

- **修正 P04/P05，不重开它们。** 03 改的是它们交付的行为（定时任务借用了创建者的会话），
  按 A04 的先例在票面补一节"修正记录"，状态保持 `resolved`。
- **A10 的判据要改一句话**：从"消耗计入父 run 的预算"改成"计入父**会话**的预算，子 run 行只留审计"。
  0025 之后 run 上的 budget 列已经是审计口径，再按原话实现会做出一个没有地方可扣的东西。
- **A12 的边界要写明**：A12 只做系统并发上限、per-principal 配额、排队可见性；
  "一段会话一个 run"由本线 02 负责。不写清，做 A12 时会把 lane 再实现一遍。
- **A08 不复活。** 它要的"跨轮进度"依赖 run 跨轮存活，与本线无关（ADR-0024）。

## 不做什么

- **不做跨通道共享**（OpenClaw 的 `identityLinks`）：需要"这两个 id 是同一个人"的事实来源，不能猜。
- **不改群聊粒度**：现在按"人 + 权限"分，OpenClaw 按房间分。这是安全取舍，记在 `docs/design/session-memory.md` 里。
- **不做跨段召回**：换段之后上一段召不回来。OpenClaw 有 `sessions_history`，我们没有，也不在这一批加。
- **不做全局并发上限与配额**：A12。
- **不动 `ADR-0019`**：它有三处表述与 0025/0026 冲突（第 97 行"A04 预算按 run 累计"、
  第 167 行"A10 消耗计入父 run 的预算"、第 183 行 A12 的边界）。这几处不在代码范围里，
  但必须在收口前一次改完——见下面的收尾清单。
