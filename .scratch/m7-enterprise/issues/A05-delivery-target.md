# A05: 结果投递与回收——run 绑 principal，不绑通道

**What to build:** run 完成后的结果有了"送到哪儿"的一等登记：投递目标是一对多的表，
run 绑发起人（谁的事）而不绑"谁问的"。结果靠 `GET /api/runs/{id}` 轮询，
也可按通知策略主动推（done_only / silent / state_changes，定时任务默认 silent）。
今天"谁问的就回给谁"——跨通道收结果与定时静默都做不到。

**Blocked by:** A02

**Status:** resolved

- [x] 在飞书提问的人，能在另一个通道（或 HTTP 轮询）收到同一条 run 的完整结果
- [x] 通知策略三档生效，定时任务默认 silent：跑完不打扰人，但结果随时查得到
- [x] `GET /api/runs/{id}` 返回该 run 的状态与结果
- [x] 投递是一对多的登记，不是回调地址式的单点

## Comments

- 2026-11-01 收票。**"送到哪儿"从请求里摘出来，落成库里的一张表**
  （`V9` 的 `claw4j_run.agent_run_delivery`）：同一件事可以在飞书问、在 HTTP 续、
  在企微收结果。**主键就是那个去重**（`run_id, channel, channel_ref`），
  不靠"插入前先查一遍"——那套判重要在每个写的地方各写一遍。
- **它不是回调地址**。回调是单点、且要能被外网访问，于是"在飞书问、在企微收"
  得先给企微开一个入口。这里记的是"回到那个会话去"——一件已经存在的会话，不新开入口。
- **策略在投递时生效，不在登记时生效**：同一件事可能先被交互地问、后来被定时续跑，
  这一轮吵不吵人该由这一轮说了算。`silent` 一句都不推，**但不影响结果落库**——
  "推不推"与"存不存"的失败姿势完全不同（推失败记一条日志，存失败是审计少一行）。
- **就地回答过的那个地址要跳过，别的地址照推**：不跳过就是同一条内容出现两遍，
  人以为自己被重跑了；而"别的地址照推"正是这条要的场景。
- **全文记在 run 上（`result`），不是只留 step 的 `result_summary`**：那个是截断摘要，
  它回答"这一步得到了什么"；查结果的人要完整答案，而异步场景里没有一次请求在等着接它。
- **HTTP 不实现 `OutboundDelivery`**：它没有可推的地址（连接早就断了）。
  这不是缺一块，是设计——按轮询取结果；少一个空实现的 `send`，就少一处"看着像发了"。
- **收件地址的接口在 `core.domain.port`，不在 `channel.spi`**：ADR-0018 原本写"与 `ChatChannel`
  平级"，但那会撞 `AgentBoundaryTest` 那条"agent 不许认识 channel 包"——而挑起投递的
  恰恰是 agent（它才知道一件事什么时候做完）。边界是机器校验的、先于文档存在的，所以按它走。
- **不属于你的与没有这个 run 回同一个 404**：分成 403 / 404 等于替对方确认
  "这个 id 存在，只是不是你的"，而 run id 是唯一一个能凭空试出别人在做什么的入口。
- 用例：新文件 `RunDeliveryTest`（app，5 条：就地回答过的跳过而别的通道收到 /
  `silent` 不推但查得到 / 按 owner 判而不是按通道判 / 三档写死在约束里 /
  同一地址只留一行）+ `RunQueryControllerTest`（channel，4 条：200 带全文 /
