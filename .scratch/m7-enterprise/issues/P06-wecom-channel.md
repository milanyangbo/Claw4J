# P06: 企业微信通道——复用入站编排

**What to build:** 助手住进企业的聊天软件。企微应用消息能收能发：收 = URL 验证 + 解密 +
签名校验 + 五秒内回空串，然后完全复用入站编排的四件事（去重 → 认人 → 异步 → 回推）；
投递走 A05 的目标表，不退回到"谁问回给谁"。认人靠回调里的成员 ID 映射到现有角色。

**Blocked by:** A05（投递目标表）

**Status:** resolved

- [x] @ 应用提问后三秒内收到"收到"级别的确认，完整答案随后推回
- [x] 同一事件被重推两次只被回答一次（无人值守场景用例：通道重推）
- [x] 未配角色的企微成员得到"没有权限"，这句话不进模型、不花 token
- [x] 投递走目标表：在飞书问，企微也能收同一条 run 的结果
- [x] 真模型闭环用例：企微收发

## Comments

**五个决定，写在前面**

1. **不引 `weixin-java-cp`**。要的只有"一个回调端点 + 一次 `POST`"：加解密是 AES-256-CBC 加一个
   SHA-1 签名，两百行以内写得完，而且每一行都能被单测钉住。引一个社区包，换来的是
   "它什么时候跟进 Spring Boot 4"这类与本项目无关的维护问题（企业微信没有官方 Java SDK，ADR-0009）。
   于是包名也没有 `.sdk` 后缀：那里没有"厂商 SDK 绑定层"，只有自己写的一段 HTTP 客户端。
2. **不做被动回复，回空串 + 主动推送**。安全模式下被动回复也要现加密一段 XML，而回调只要五秒；
   更根本的是它只在"答案恰好很快"时可行，而 Text-to-SQL 从来不快。
   代价是那十几秒里对话框没有动静（企业微信客户端没有"正在输入"），所以补了一句**回执**。
3. **回执加在编排层，不加在通道里**。通道里加＝排在去重与认人之前：重推会再"收到"一次，
   被拒的人先被安抚再被告知没权限。所以 `InboundDispatcher` 多了第五件可选的事（`receipt`），
   飞书不传、行为不变。
4. **`InboundDispatcher` 不注册成 bean**，在 `wecomCallbackController` 里就地建一个。
   容器里已经有一个（飞书那份），两个同类型 bean 会让"按类型注入"直接歧义，
   而飞书的通道 bean 正是按类型拿它的。
5. **通道 `start()` 只记日志**，不探活回调地址。回调地址通不通从容器里探出来的结论经常是反的
   （反向代理、白名单）；这跟飞书"连不上就抛"不矛盾——飞书那条连接是它自己发起的。

**顺手修掉的一个真 bug（不改就会坏）**

`feishuOutboundDelivery` 原来写的是 `@ConditionalOnMissingBean`（按返回类型 `OutboundDelivery` 判）。
两个通道的投递实现是同一个类型，于是**谁先装配谁赢**，另一个永远注册不上——而"在飞书问、企微收"
恰恰需要两个实现同时在场。这条与装配顺序有关，所以是"有时候好有时候坏"的那种故障。
改成按**名字**判（`feishuOutboundDelivery` / `wecomOutboundDelivery`）。同一个坑 P03 的
`ApprovalCards` 上已经踩过一次，注释就写在那儿。

**三处静默失败（都只表现为"用户永远等不到回答"）**

- `token` 错 → 签名永远对不上 → 回调被丢弃；
- `encoding-aes-key` 错 → 解密抛异常 → 同上；
- `corp-id` 错 → 解出来的 receiveid 与它不等 → 同上。**这条检查是唯一挡得住"签名对、密钥对、
  内容却是别家企业"的东西**，所以它在解密里，不在配置校验里。

前两样在 `WecomCipher` 构造时就校验（位数、Base64、非空），第三样在解密时校验并记 WARN。

**用例**

- channel `WecomChannelTest` **19 条**：URL 验证（对/错）、文本/事件/图片三条路、重推只答一次
  （回执也只有一次）、未登记成员（不调模型、不发回执）、签名错、别家企业的 receiveid、坏报文、
  凭据构造失败、先回执后答案、投递委托、token 只换一次、42001 换一张重发、errcode 非 0 抛出、
  装配三条（配置不齐 / 齐了 / 同一人两个角色）。
  密文与签名在这一份里是**照协议另写一遍**的：用生产的加密去验生产的解密，两边一起错也照样绿。
- `ChannelBoundaryTest` 加了 **2 条**规则：`channel.wecom` 不依赖实现、也不伸手进 `channel.wecom.client`。
  与飞书那两条是同一个界，分开写是为了失败信息里能一眼看出破的是哪个通道。
- app `ApplicationAssemblyTest` 加 **1 条真模型闭环**：真 HTTP 回调（真加密、真签名）→ 真模型 →
  推回成员。回推那一层换成记录器（`@ConditionalOnMissingBean` 让替身赢），
  断言的是"先回执、答案里有 128400"。

**自己造的坑**

① `refreshToken()` 里"本地判没过期就用手上这张"的逻辑，在"平台已经判它过期"时等于**重发同一张**
——第二次照样 42001，而日志会写着"重试过了"。改成 `renewToken()`（强制换）才对，用例当时就是红的。
② `@ConditionalOnMissingBean` 不写名字＝按返回类型判，第二个同类型 bean 永远注册不上（见上）。
③ 企业微信的 `MsgId` 是数字字符串、`CreateTime` 是**秒**（飞书是毫秒）：照飞书抄会得到 1970 年。

**没做的**

- 群机器人 webhook（只能推不能收）、通讯录同步（成员仍手写）、图文卡片与被动回复、
  `safe=1` 的保密消息；
- 回调地址的自动注册（企业微信没有"用 API 设置回调"的接口，只能后台手填）；
- 多实例去重（回调是平台单点投递，单实例是既定形态，理由同 ADR-0009）。
