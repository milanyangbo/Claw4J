# P07: 审计——step 的只读投影，不新建执行表

**What to build:** 出了事查得清。step 已经是执行真相（谁、第几步、调了什么、产出什么），
审计只补发起人、批准人、决定、参数摘要（前 200 字符）与留存策略（90 天）——
另建一张执行表就是两套真相，对不上时没人知道信哪个。落点复用现有工具回调与鉴权
advisor 两个接缝，不新造概念。

**Blocked by:** A01（step 已存在）、P02（批准记录已存在）

**Status:** resolved

- [x] 任一次工具调用都能答出"这次调用是哪次批准的"，批准记录与执行记录一一对应
- [x] 能按人、按时间、按结局查审计；一次越权落一行，带工具名与角色
- [x] 审计只落参数摘要与指纹，不落完整参数——不成为另一张业务数据副本
- [x] 落地后 `heartbeat` 的重估条件另一半成立（另一半是 A04）
- [x] 审计 ≠ 评测 ≠ 观测：本票只做合规那一格（质量归 A06、Ops 归 P14，均不在本批）

## Comments

**五个决定，写在前面**

1. **加列，不建表**。另建一张 `audit_tool_call` 跑得起来，但那时"这件事调了两次还是三次"
   有两个答案：step 说一套、审计说一套，而对不上的那天没有任何一方是权威。所以只在
   `agent_step` 上加六列（`actor / actor_role / outcome / args_digest / args_summary /
   approval_id`），读的时候走**只读视图** `claw4j_run.audit_trail`——视图没有写路径，
   也就不可能与执行真相不一致。这是本票唯一的架构结论（ADR-0023）。
2. **两个写口与两个接缝一一对应**。拒绝发生在工具执行之前，`MeteredToolCallback` 根本
   看不到它，"有人试过但被拦下"只有鉴权 advisor 知道；反过来，"真的发生了"只有工具回调
   知道。所以 advisor 写 `rejected` / `awaiting_approval`，回调写 `executed`，两边都进
   `ToolCallAudit`（唯一的写口）——同一件事只有一个类在写，它才有资格说"审计与执行是
   同一份真相"。
3. **唯一索引的谓词必须带 `outcome = 'executed'`**。等审批那一行也带着同一个 `approval_id`
   （"这条停在谁身上"要能查），而它不是一次执行。一开始写成只按编号判，"先等批、后执行"
   这种**正常**流程会撞唯一约束——那等于惩罚正确的用法。改成
   `where approval_id is not null and outcome = 'executed'`，理由同时写在迁移注释与
   `RunSchemaSqlTest` 的用例里。
4. **兑现批准与执行工具之间只能靠一个进程内 map**。兑现发生在 advisor、执行发生在工具
   回调，两处拿不到同一份上下文（`ToolContext` 是每次执行现造的）。`ToolCallAudit#granted`
   的键是 `runId + 工具名 + 指纹`（指纹同源，所以"批的那次"与"跑的那次"能对上），
   TTL 10 分钟、上限 256 条，超了整份清。代价写进 ADR：多副本时那一行的 `approval_id`
   可能是空；兑现了却没执行会留下一条被 TTL 清掉的槽。丢了只影响这一条线，那一行审计仍在。
5. **留存删 run，不删"审计行"**。审计行就是 step，按 run 级联才不可能出现"有一条审计行、
   但它指向的执行记录已经没了"。审批没有外键，必须单独删，且**按 `requested_at` 而不是
   `decided_at`**——否则没人点过的那条永远不消失。

**只落摘要与指纹**

`args_digest` 走 `CallFingerprint.of(...)`（与审批表同一列同一个函数，两边能直接对上）；
`args_summary` 先 `PiiRedactor.mask` 再截 200 字符。**不落参数原文，不落产出原文**，
工具抛异常只记类型不记 message。口径是"够认出这是一次查表，不够把一张表搬进审计库"。

`docs/capability-tests.md` 新增 §10：视图的十七个列、三句查询（按人 / 按结局 / 按 run 问
"哪次批的"）、四条口径（一条批准一次执行、只落摘要、被拒也有一行、留存 90 天）。

**用例**

- `agent/ToolCallAuditTest` **13 条**（新）：执行落一行、超长参数只留 200 字 + 指纹、
  先脱敏再截断、批准落到执行行且只落一次、跨 run 不串味、被拒一行、等审批一行、
  抛异常仍算 `executed` + failed、半截参数指纹留空、不在 run 里不写、无存储空转、
  写时抛异常被吞掉、第四种 outcome 构造时被拒。
- `app/RunSchemaSqlTest` **+3（19 条）**：视图答得出谁 / 何时 / 怎么、一条批准只对应一条
  执行（含"先等批后执行"不撞约束）、留存窗口删整件旧事与陈旧审批。
- `app/ApprovalFlowTest` **+2（13 条）**：执行那一行带着放行它的审批编号、被拒落一行且
  带工具名与当时的角色。
- **门禁名额**：agent 模块测试文件已满 10 个，把 `AgentBoundaryTest` 的两条架构规则
  并进 `ModelAndToolSelectionTest`（18 + 2 = 20 条）后删掉原文件，腾出位置。
  并进去时**改成了普通 `@Test` 直接 `rule.check(...)`**，理由见下面第 ④ 条。

**自己造的坑**

① 唯一索引一开始只按 `approval_id` 判，正常流程会撞约束（自查时发现，见决定 3）。
② `writeRefusal` 从五参改成四参后，调用处没跟，编译期才报 `cannot be applied to given types`。
③ 单独跑 agent 模块全量时 `ChatPipelineTest` 报缺模型 key——是运行方式（没 `source .env`），
不是代码；`./scripts/verify.sh` 会自己载入。

还有一条是这次合并带出来的：
④ **一个类同时挂 `@Test` 与 `@ArchTest`，surefire 报告会互相覆盖**。Jupiter 引擎与 ArchUnit
引擎各跑一遍这个类，两份报告落在同一个文件名上，后跑的盖掉先跑的——合并之后那张报告只剩
2 条，另外 18 条在统计里凭空消失，而门禁的"用例条数"就是按报告文件求和的。所以合并后第一次
全量跑出来还是 **447**（与 P06 收票时一模一样），看起来像"这一票没加用例"。
改成普通测试方法 + `rule.check(importedClasses)` 后是一个引擎、一份报告，
总数才回到该有的 **465**（447 + 本票新增的 18）。**判据**：改完 agent 那份报告是 20 条，不再是 2 条。
（还有一条连带的坑：门禁数方法数是**按行匹配注解名**的，注释里提一句注解名就会被算成一个方法
——那一段注释因此改成了不含注解字的写法。）
（别处 core / channel / capability 都是"独立文件 + `@ArchTest`"，那里没有这个问题。）

**没做的**

- **子 Agent 的工具调用暂不落审计**：子链的工具上下文里没有 runId（与预算同一个原因），
  写不进任何一件事。那是 A10 的事，不是"忘了接"。
- **没有审计查询接口**：本票只保证"库里的行答得出"，读法是视图 + SQL。加一个 `GET` 会先
  把"什么样的查询叫一次审计"这件事定死，而那一格属于 P14 之后的 Ops，不在这里。
- **没有回放**：不是目的。要回答的是"谁批的"，不是"当时模型想了什么"（ADR-0016 / 0023）。

**收尾时同步的地方**：ADR-0021 的 `heartbeat` 进度与 ADR-0019 的两处同类表述已改成
"两半（A04 + P07）都到齐、重估条件成立，待重估"，结论预期（"它只是 `schedule_task`
的上层用法"）记在 ADR-0023 末条；README 的"已达"补了审计一行。
