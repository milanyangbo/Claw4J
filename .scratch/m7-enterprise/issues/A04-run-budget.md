# A04: 预算从"一轮"提到"一次 run"

**What to build:** 预算按 run 累计（工具调用次数 / token / 墙钟三项），轮预算降级为默认值
而不是上限。今天跨轮无法累计，一次跨 3 轮调 7 次工具全放行——预算管不住一件跨轮的事。
定时任务每次运行单独计。

**Blocked by:** A01

**Status:** resolved

- [x] 一次 run 跨 3 轮共调 7 次工具 → 第 7 次被拒（今天每轮重置，7 次全放行）
  —— **2026-11-05 复核：这条从来没有成立过**，见下方修正与 ADR-0025
- [x] 超预算：写明结局并停下，不抛要人猜的异常
- [x] 超预算写结局后可从库里回读，与 A01 的 run 状态一致
- [x] 落地后 `heartbeat` 的重估条件成立一半（另一半是 P07），ADR-0021 的待重开条目被引用

## Comments

- 2026-10-31 收票。**预算挂在 run 上，不是挂在轮上**：三项（工具调用 6 次 / token 10 万 /
  耗时 900 秒）落在 run 那一行上（V8 加 `budget_tokens` `budget_ms` 两列，`budget_used`
  是工具调用），跨轮不重置。轮内的 3 / 6（`ToolCallBudget`）降级为默认护栏——
  它拦的是"一轮之内绕圈"，"这件事一共烧多少"由 run 这一层说了算。
- **工具调用上限取 6，与一轮的上限同数**：判据就是"跨 3 轮的第 7 次被拒"。
  run 不是"再给几次机会"的借口，它只是让同一个上限跨轮生效。
- **扣的地方只有一处**：`MeteredToolCallback`——所有工具调用的唯一入口（父与子都过它），
  runId 从工具上下文里取（`ContextKeys.RUN_ID`，A03 放进去的）。
  它同时是"这次调用真的发生了"这个事实唯一的知情者，所以计量、调用记录、扣额度同层。
- **子 Agent 那一侧还没有 runId**：`SubagentRunner` 目前只把身份传下去，
  所以子调的工具不扣父的额度。轮内的 3 / 6 在子那一侧照旧生效。
  "子 run 挂 parent_run_id、消耗计入父"是 A10 的活，不是这里漏了一条。
- **顶不住时回一句话，不抛异常**：抛出去会被工具循环当成"这个工具坏了"，
  模型多半会换一个工具再试一次——而那正是一次新的工具调用，预算却刚刚说过"没有了"。
  回执里写明是哪一项用完（`预算用尽（工具调用 6/6 次）…`）并让它直接收尾。
- **被拒的那次不算用掉的量**：否则"还剩几次"会凭空少一次，
  而它正是下一次给不给的依据。所以是先问后扣，不是先扣再判。
- **进门先问、出门再扣**：已经撞线的 run 不再调模型，直接写结局
  （落一条 step 说明"预算用尽，没有调用模型"+ 状态 `budget_exhausted`）；
  出门扣掉这一轮的 token 与耗时，刚好烧完的那一轮停在 `budget_exhausted` 而不是 `done`。
  两者的下一步完全不同：追加预算继续 vs 没有了。
- **耗时记的是"各轮实际耗时之和"，不含等待**：一件等审批等了两天的事不该因为等待耗光预算，
  而等待期间没有任何一轮在跑——于是这一项天然不含 `suspended` 那一段，
  不需要为 P02 专门加一条例外。**流式不计 token**（汇总 usage 未必到得了这一层），记 0 而不是估算。
- **读不到用量时放行，不拦活**：库没迁、连不上，`spent` 就是空，那时预算管不住，
  而管不住的失败姿势应该是"这一轮少记一笔"，不是"把用户的活停了"——
  与 run 落库降级是同一个判断。少记多少由 `claw4j.run.errors` 暴露。
- **SQL 里做 `+=` 而不是"读出来加一遍再写回"**：后一种写法在两轮并发时会用旧值覆盖新值，
  表现是额度凭空多出来，而预算最要紧的性质就是它只会变少。
- 用例：新文件 `RunBudgetTest`（app 模块，5 条：第 7 次被拒且没真执行 / 超预算不调模型、
  写明结局、状态可从库回读 / token 与耗时记到 run 上 / 耗时是独立的一项 /
  另一件事从零开始计）。另加 1 条进 `RunSchemaSqlTest`（三列各自累加、换实例读得到）。
  **放在 app 模块是因为 agent 模块的测试文件已满 10 个**——门禁钉的是文件数。
  全量 332 绿、跳过 0、行覆盖率 agent 69.8%。
- 同步：ADR-0021 的 `heartbeat` 条目已标注"A04 已落地、P07 未落地——未到重估时点"；
  `application.yml` 写出三个上限（`claw4j.run.budget.*`）；README"已达"与
  `docs/capability-tests.md`（含一条手测：查 `agent_run` 那三个数）已同步。
- 没做的（有票才做）：子 Agent 扣父额度（A10）；**没有独立的"追加预算"接口**——
  现在的做法是调大上限后 `resume`（`budget_exhausted` 不是 `suspended`，
  `resume` 的 where 条件放得进去），要一张额度表是另一张票的事；
  ADR-0016 里那句"run 之上另有**步数**上限"本票没有落，步数由工具调用次数间接约束。
- 2026-11-05 **上面第一条判据从来没成立过；预算改挂会话**（[ADR-0025](../../../docs/adr/0025-session-scoped-budget.md)）。
  run 的寿命是一轮：`ChatClientAgentPort` 每轮收尾都 `finish(runId, DONE)`，
  下一轮 `openRun` 新开一件。所以"跨 3 轮的第 7 次被拒"在当时的实现里不可能发生——
  三轮各 6 次、一共 18 次，每一次都落在新 run 的 0/6 之内。
  V8 的列注释、`RunBudget` 类注释、`application.yml` 三处都写着"跨轮不重置"，
  **那句话当时描述的是意图，不是行为**；三处已按实际情况改写。
  现在的做法：`claw4j_run.agent_session_budget` 按 `session_id` 累计三项，
  空闲 `claw4j.run.budget.idle-minutes`（默认 120，与 OpenClaw 的 idleMinutes 同值）清零；
  会话键同时加了通道 + chatId，群聊与私聊是两段（同一条 ADR）。
  定时任务走的是同一条 `reply`，chatId 固定，所以两次运行落在同一段会话里、预算合成 2；
  跨过 idle 就清零，不会把第二天的那次卡住（要"每次运行单独计"得先给 run 一个来源字段）。
  代价与未决项（换通道记忆断、recall_session 尚未按会话过滤）记在 ADR 的 Consequences。
