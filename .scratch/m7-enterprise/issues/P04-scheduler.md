# P04: 定时调度——到点 = 创建一个 run

**What to build:** 助手会自己醒来干活了，但不引新组件：调度表 + 每 30 秒扫描 +
行级锁跳过已锁行保证多实例不重复；失败三次自动停用；到点就创建一个 run，
其余（鉴权、工具、投递）全部复用现有路径。不引 Quartz / Redis / 外部调度器
（依据单实例形态的既定裁决）。

**Blocked by:** A02（到点创建 run 走同一个入口形状）

**Status:** resolved

- [x] 说"以后每天早上九点把华东成交额发我"，模型能把它变成一个定时任务（工具族见 P05，本票只管调度）
- [x] 同一时刻起两个实例，同一条到点任务只执行一次
- [x] 实例重启不丢已定好的时间点
- [x] 连续失败三次自动停用，并收到一条带最后错误的停用通知
- [x] 无人值守场景用例：任务失败停用有人知道，不是无声失败

## Comments

- 2026-11-02 收票。**"到点"只做一件事：开一个 run**。鉴权、工具、预算、投递全部走那条现成的路，
  调度器不认识它们——它只认"这一轮有没有跑成"。四条验收里有三条（多实例、重启、错过的点不补）
  其实都是同一个决定的结果：**时间点在库里，不在进程里**。
- **新开了一个窄接口 `RunLauncher`，没有复用 `AgentPort#reply`**：后者的契约里有"就地回答的地址"，
  于是结果会回到那次请求里；定时任务那一头根本没有请求在等，结果只能按通知策略推给登记的地址。
  两者只差这一个参数，所以 `ChatClientAgentPort` 里抽了一个 `answer(message, answeredAt)`，
  `reply` 传地址、`launch` 传 null——**同一段跑法，两种交付方式**。
- **认领是一条语句**：`update … where id in (select … for update skip locked) returning …`。
  拆成"先查再改"的话，两个实例会在两者之间读到同一批行，各自都认为自己拿到了。
  `skip locked` 让后来的那个**跳过**而不是等——等会让它的整轮扫描卡在别人的一次模型调用上。
  多实例那条用例是**真并发**（两个线程 + `CyclicBarrier`），不是先后调两次 `scan()`。
- **租约与行锁管的是两件事**：行锁管"同一瞬间"，租约（`claimed_until`）管"认领之后进程崩了"。
  只有行锁的话，崩溃那一条会一直躺在"已认领"里——锁随连接消失，可没人知道该不该再跑它。
  租约用库的时钟（`now() + make_interval`），不用 JVM 的：两个时钟有偏差时，"我以为还占着"和库里的判断会各说各的。
- **失败也推进时间点**：不推进的话，30 秒后立刻重试，一次模型故障能在一分半里烧光三次机会——
  那会把"连着坏三天"和"坏了 90 秒"变成同一件事。推进之后，"连续三次"指的是三个**到点**没跑成。
- **计数与停用写在同一句 update 里**，成功那一次把计数清零：分成两句的话，第二个实例可能在这之间又跑一次，
  失败计数跨过阈值两次、发两条通知。这里问的是"还连着坏吗"，不是"一共坏过几次"。
- **cron 坏了直接停用，不走失败计数**：再试三次也不会变好，攒三次只是让它晚三天才停。
  同一类还有"这条 cron 没有下一次"（一次性日期已经过去）。
- **停用必须有人知道**：停用的那一下通过 `OutboundDelivery` 往任务登记的通道推一条带最后错误的通知。
  推不出去（HTTP 部署没有可推的通道）时只留一条 WARN——库里的 `disabled_reason` 与 `last_error` 照样查得到。
  这正是"无人值守"那一条的落点：**"没有消息"既可能是"今天没到点"，也可能是"三天前就死了"**，
  这条通知是两者唯一的区别。
- **默认静默**（`notify_policy` 列，默认 `silent`）：spec 第 16 条。说"发我"的那一类由创建者改成
  `done_only`——P05 的工具从用户原话里取，表里这一列先留着。
- **时区是一列**（可为空 = 部署时区）："早上九点"是哪个九点只能由部署回答；写成列之后，
  测试里那个答案才确定（`Asia/Shanghai`），否则用例会跟着 CI 机器的时区飘。
- **`claw4j.schedule.enabled` 没有进 `ScheduleProperties`**：它的读者是那个 `@Bean` 上的
  `@ConditionalOnProperty`。在配置对象里再声明一次就是"人人都以为自己读了的键"，
  哪天两边不一致谁也不知道以哪个为准。
- **一个真 bug，写反的约束把正常出口打死了**：`ck_agent_schedule_disabled` 一开始写成
  `check (enabled or disabled_reason is null)`——停用（`enabled = false`）并记原因时
  整条 update 被拒，于是"三次失败停用"和"cron 坏了停用"三处红。正确写法是
  `not enabled or disabled_reason is null`。值得记的是它的表现：`fail` 里 catch 住了、只留一条
  WARN，看起来像"没跑到"而不像"写不进去"——**降级口径把配置错误伪装成了业务结果**。
- **覆盖率差点红，补法受文件位限制**：agent 从 60.5 掉到 55.2（`ScheduleScanner` 92 行 +
  `ScheduleStore` 86 行，而它们只在 app 的真库用例里被跑到）。agent 的测试文件已经用满 10 个
  （P02 的记录），于是决策分支那七条寄放在 `ObservabilityTest` 里——它读的也是计数器
  （`claw4j.schedule.fired{outcome=…}`），而这个文件一直在管"跑了几次"这件事；
  库上的那一半（认领、重启、停用）在 app 的 `ScheduleFlowTest` 里用真库验。回到 61.0%。
  这一处是**已知的将就**：下次要动调度测试时，先把 agent 的两个文件并成一个腾出位置。
- 用例：app 新增 `ScheduleFlowTest`（8 条，真库 + 假模型）；`ApplicationAssemblyTest` +1
  （**真模型闭环**：库里种一行到点任务 → 直接调扫描器 → 真开出一个 run、回答落在 run 上）；
  agent `ObservabilityTest` +7（决策分支：跑成、记失败、到阈值停用并通知、cron 坏了停用、
  三种跑不起来的理由、库读不出来跳过、cron 口径）；
  `MigrationCompositionTest` 1..12、`RunSchemaSqlTest` 的表清单加了 `agent_schedule`。
  全量 **401 条全过、跳过 0**；行覆盖率 core 84.7 / channel 67.6 / capability 84.8 / agent 61.0 /
  sales 93.8 / mcp 75.0；文件数 core 6 / channel 9 / capability 10 / agent 10 / app 10，
  单文件最大 17 / 15 / 18 / 20 / 17。
- 同步：`docs/capability-tests.md` 新增"到点自己干活"一节（口径 + psql + 如实写明现在还造不出任务）、
  `README` 的"已达 / 未达"两格、`application.yml` 的 `claw4j.schedule` 五项。
- **没做的（各有归属，不是漏项）**：
  - **建任务/列任务/停用任务的工具**：P05。本票只做调度，工具族从用户原话里取 cron 与时区，
    并把"发我"翻成 `done_only`。
  - **改一个已有任务的 cron**：没有更新路径（也没有工具），要改只能删了重建。等 P05 有了"列出我的任务"
    再一起想"改"要不要单独一个动词。
  - **补跑错过的点**：刻意不做，理由在迁移注释里——停了一夜回来补三份账单没人要。
  - **单任务独立的预算**：每次运行各开一个 run，各计各的额度（A04 的口径），任务之间不共享也不隔离。
  - **扫描线程池**：串行跑，一次最多 `max-per-scan` 条。没做配额之前，"同一时刻 N 个模型调用在烧不同人的额度"
    是说不清的状态。

## 修正记录（2026-11-05，ADR-0026 / 03）

本票落地时，定时任务**借用创建者那段对话**：`ScheduleScanner` 只传了 `chatId`，
而那个字段同时担着"结果送到哪儿"和"这是哪一段会话"。于是到点那次运行跑在用户的会话里——
它的问答出现在用户的聊天记录中、继承用户私聊的上下文作答、还吃掉用户那份预算
（ADR-0025 之后额度按会话累计）。上面"没做的 · 单任务独立的预算"那一格，
在当时**不只是没做，是做不到**。

现在 `InboundMessage` 多了一个 `conversationId`，定时任务传
`cron:<taskId>:<触发时刻>`：每次运行是自己的会话，投递地址仍是原来的 `channelRef`。
`ScheduleFlowTest` 里"两次运行合成 2 次工具调用"的断言随之改成"各 1"——
那条断的不是回归，是本票当时的错误行为。
