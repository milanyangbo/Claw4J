# P05: schedule_task 工具族——一次授权，多次执行

**What to build:** 定时任务有了建 / 列 / 取消三个工具。创建时校验"这个任务需要的工具，
创建者现在都有"——跑不了当场拒，而不是每天执行时失败；执行时**重新鉴权**，
跑的是任务主人的身份而不是系统账号（系统账号等于万能身份），也不用角色快照
（角色被收回任务还能跑就是漏洞）。

**Blocked by:** P04

**Status:** resolved

- [x] 建 / 列 / 取消三个工具可从对话触发，穷举接入 capability-tests 的口径
- [x] 创建时权限校验不过 → 当场被拒，拒绝理由进对话
- [x] 把创建者的角色删掉，下一次到点必须失败并自动停用，还会通知任务主人
- [x] 每次执行重新鉴权，跑任务主人的 Principal；任务运行有独立的预算计量（每次运行单独计）
- [x] 通知走投递目标，定时任务默认 silent

## Comments

- 2026-11-02 收票。**三个工具，不是一个带 `action` 参数的**：动作名进的是角色的授权表
  （`claw4j.channel.http.roles` 里那一行），而"能不能新建"与"能不能取消"是两种授权；
  合成一个的话，给了"看看自己有哪些任务"就等于给了"能取消"。
- **"一次授权"指的是建这一下**。所以建的时候把三件事核完：cron 解析得了、要用的工具主人
  **现在**都有、这些工具里没有"每次都要人批准"的。核不过当场拒，理由原样交给模型——
  让它换个参数再来，比明天九点才发现跑不了好得多。
- **要审批的工具被挡在门外**：一条任务每天在自己醒来时要求有人点按钮，结果是每天挂一条
  没人看见的待批请求，而不是每天办成一件事。这不是"审批没做完"，是这类工具本来就不属于
  "一次授权、多次执行"的场景。
- **角色快照被换成了身份**（`V13`）：P04 存的是整份 `Principal`（含 tables / actions），
  到点直接拿它跑——那实际是一份角色快照，而快照不跟着配置变：昨天被收回的权限，
  今天的任务还带着跑完，**收权对定时任务等于没发生**。现在库里只有
  `owner_user_id` + `owner_role` + `required_tools`，每次要跑之前拿当时的角色表换一份权限
  （新的端口 `RoleDirectory`，实现放在通道那一侧——角色表是部署配置，归读配置的人管）。
- **建的时候与到点的时候问的是同一个对象**（`ScheduleAuthorization`）。分开写的话，
  两处早晚不一致，最常见的不一致是"建的时候查了权限、到点只查身份"——那条缝只在第二次
  问的时候存在，而那时已经没人看着了。
- **收权当场停用，不攒三次**：角色被删、工具权限被收回，这两样再试三次也不会变好，
  攒三次只是让主人晚三天知道。模型抽风照旧走三次计数——那才是"可能是暂时的"。
- **每次运行单独计预算**：每次到点都开一个新的 run（`runId` 传 null），额度按 run 算，
  这是 A04 已经定好的口径，本票只需要在用例里钉住"两次到点各记一笔，不是合成两笔"。
- **取消是软停用，按归属键判**：`disable(id, "创建者自己取消的")`，记录留着（谁建的、
  什么时候建的都还查得到）。按 id 判权限的话，猜中别人的编号就能停别人的任务；
  按 `SessionKeys.ownerOf(principal)` 判，别人的任务与不存在的任务还给同一句话——
  分开说等于替对方确认"这个编号存在"。
- **编号只显示前 8 位**：UUID 全长 36 位，模型抄错一位的概率不低；取消按前缀匹配，
  撞车时回一句"有几条都以这几个字开头，多写几位"，不瞎猜。
- **三个工具跟着 `claw4j.schedule.enabled` 进退**：能建任务却没有东西会跑它，
  等于让模型说出"已经定好了"而实际不会发生。与计划工具同一个判断：
  模型面前少一个工具，比"调了才发现白做"好。
- **门禁逼出来的一次合并**：agent 的测试文件位已满 10 个（P02、P04 的记录），
  这一票要新增 `ScheduleToolsTest`。把 `ToolSearchTest`（7 条）并进 `ModelRoutingTest`
  → `ModelAndToolSelectionTest`（18 条）：两件事本来就是"这一轮怎么被组装"的两面——
  用哪个模型、模型看得见哪些工具。P04 的票里写着"下次先并文件腾位"，这就算兑现了。
- **三个自己造的坑，都值得记**：
  - `jdbc.update(sql, …, new Object[]{TOOL})` → `String[]` **是** `Object[]`，直接当变参会被
    摊成一串单个参数，报的是 `BadSqlGrammar`（参数个数不对，但 SQL 看着完全正常）。
    改成 `(Object) new String[]{TOOL}`。主代码里那一处早就写了这个强转，测试里却忘了。
  - 读回来的是 `org.postgresql.jdbc.PgArray`，不是 `String[]`：`(String[]) rs.getObject(...)`
    会 `ClassCastException`，要么走 `rs.getArray(...).getArray()`，要么在测试里先转 `java.sql.Array`。
  - "建不成"那条用例一开始绿不了——因为我给调用者造了一个"什么都有"的 principal，
    而角色表已经收窄。这不是 bug：建的时候用的是**调用者的身份**（真实入口那里它就是从角色表
    算出来的），角色表只在到点复核时用。测试里造两份不一致的身份，等于是造一个不存在的世界。
- 用例：app `ScheduleFlowTest` +5（从对话里建任务并核对库里那行、没权限的工具当场拒、
  角色被删就停用并通知、工具权限被收就停用、两次到点各记一笔预算且工具用的是主人身份）；
  agent 新增 `ScheduleToolsTest`（14 条：建/列/取消、cron 与时区写错、四种建不成的理由、
  没身份、参数不是 JSON、前缀撞车）；`ObservabilityTest` +2 并改 1（身份认不出来当场停用、
  工具权限被收当场停用）；`MigrationCompositionTest` 1..13、
  `ApplicationAssemblyTest` 的真模型闭环改成种"身份"而不是快照。
  全量 **422 条全过、跳过 0**；行覆盖率 core 84.7 / channel 66.3 / capability 84.8 /
  agent 62.3 / sales 93.8 / mcp 75.0；文件数 core 6 / channel 9 / capability 10 / agent 10 /
  app 10，单文件最大 17 / 15 / 18 / 20 / 17。
- 同步：`docs/capability-tests.md` 的"到点自己干活"一节改成四条口径（多了"权限按到点重算"
  与"每次运行单独计预算"），补了三个工具的对话口径与"自己验收权"的做法；
  `README` 的"已达 / 未达"两格；`application.yml` 的 `read-only` 加了三个动作
  （给它是安全的：任务到点按创建者**当时**的权限跑，永远不比他此刻能做的更多）。
- **没做的（各有归属，不是漏项）**：
  - **改一条已有任务的 cron**：仍然没有更新路径。要改就取消重建——"改"要不要单独一个动词，
    等真有人提再说。
  - **任务幂等 / 去重**：同一个人连说两遍会建出两条。按 goal 去重看起来省事，
    但"九点报一次"和"九点报一次（上周口径）"在字符串上像、在语义上不是一回事。
  - **任务之间的配额**：每次运行各计各的，任务之间不共享也不隔离（A04 的口径）。
  - **取消后恢复**：软停用，要恢复就重建一条。恢复要重新核一遍权限，
    那等于把"建"那条路再走一遍，不如就让它走一遍。

## 修正记录（2026-11-05，ADR-0026 / 03）

上面"任务之间的配额：每次运行各计各的"这句，在本票落地时并不成立——
每次运行确实各开一个 run，但它们**共用创建者那段会话**，而额度从 ADR-0025 起是按会话累计的。
结果：任务烧掉的工具调用记在用户头上，用户一句话没说就被回"预算用尽"。

现在定时任务的会话标识是 `cron:<taskId>:<触发时刻>`（`InboundMessage#conversationId`），
每次运行是自己的段，额度真的各计各的；`schedule_task` 存的收件地址不受影响。
详见 ADR-0026 决定三与 `.scratch/adr-0026-session-boundary/issues/03-cron-owns-its-session.md`。
