# P01: ToolPermission 加第三个分量 Approval

**What to build:** 权限从"能不能"变成"能不能 + 要不要批"。`Approval{NONE, REQUIRED}`
默认 NONE——审批只加在真正有副作用的动作上（跑脚本包、发邮件、交脚本草稿），不给"读一下"。
"有权限"与"要审批"是两件事，审批不替代鉴权。同时建审批请求表。
全仓构造点极少（两个工厂 + MCP 入口），调用点不用改。

**Blocked by:** None (can start immediately)——按真实依赖，P01 不 gate 在任何 A 票上

**Status:** resolved

- [x] 20 个工具的默认放行面一个都不变（全部 NONE）——**票面写 20，实际是 21**（A03 加的 `update_plan`）
- [x] 标了 REQUIRED 的动作在无批准记录时被拦，拒绝理由传回对话而不是无声失败
- [x] 审批请求表落库，表结构用 SQL 用例钉住（含变异）
- [x] 门禁本地 `./mvnw clean verify` 通过

## Comments

- 2026-11-01 收票。**"要不要批"成了权限的第三个分量，默认 `NONE`**：全仓 main 代码里
  `requiringApproval` **零调用**（grep 过），21 个工具的放行面一个都没变。验收第一条靠这条事实
  加上 core 的单测（`read` / `of` 出来的 `needsApproval()` 为 false），不再另写一份"工具清单"
  去对——那种清单每加一个工具就要改一次，改漏了还照样绿。
- **审批不是鉴权的分支，是并行的第二道门**：`grantedTo` 一个字都不看 `approval`。
  判据是拒绝话术——合成一条就再也分不清"没权限"（找管理员改角色配置）与"等你批"
  （找审批人点按钮），收到它的人只会去问同一件事，而能解决它的人一直没被找到。
  用例两个方向都钉了：没这个动作的人，标了要审批也是**不授予**；有这个动作的人，
  这条权限本身是授予的（拦在更后面那道门）。
- **两道门在同一个位置**（`AuthorizationAdvisor`），因为约束是同一条：判定必须在
  **工具执行之前**发生，且**流式路径**也要过。分成两处实现，早晚有一处漏掉流式
  （ADR-0007 记的就是这个坑）。但两次拦截的 outcome 分开记：`denied` / `needs_approval`——
  运维看到"今天拒了 40 次"要能直接知道该去改配置还是该去找人点按钮。
- **等审批那句话里写死"这一轮不要重试"**：工具调用是同步的，模型看不到"批了没有"。
  不说这一句，它下一轮会把同一个请求原样再发一遍——而重发既不会变成批准，又把真正的进展挤掉。
  这句就是"拒绝理由传回对话而不是无声失败"（验收第二条）的落点；同时它与
  `DENIAL_PREFIX` 分开成一个常量，测试断言的是"以哪句开头"，不是措辞。
- **表叫 `approval_request`（照 ADR-0020 的名字），落在 `claw4j_run`**：它跟 run / step 是同一批
  迁移、同一个开关（`claw4j.run.enabled`）。三处判断：
  - **过期不是一种状态，是时间**：有效 = `status = 'granted'` 且 `expires_at > now()`。
    另立一个 `expired` 状态的话，要么库里有个谁都没写的状态，要么得有个定时器去改它，
    而"现在还有效吗"本来一行比较就能答。
  - **`run_id` 可空、不设外键**：审批记录的寿命比 run 长，级联删掉等于抹掉"谁批过"的留痕，
    而 P07 的审计恰恰要按它回答"这次调用是哪次批准的"。空表示这次调用不在一个 run 里（子 Agent，A10）。
  - **两个约束就是"含变异"那一面的着力点**：删掉 `ck_approval_request_status`，
    多一个拼错的 `granted` 之后查询按 `status = 'granted'` 过滤会把它当成"没批准"
    （记录看起来是批过的，行为是没批）；删掉 `ck_approval_request_decided`，
    没有决定时间的 `granted` 就是一条追不回来的断言。任删一条，
    `approvalRequestPinsItsStatusAndDecision` 立刻红。
- **写用例时被咬了一次，值得记**：'maybe' 那一行第一次是撞在 `ck_approval_request_decided` 上，
  不是状态那一条——PG 不保证约束的检查顺序。所以那一行显式带上 `decided_at`，
  让它"只可能撞状态约束"，否则用例红在别处，看起来像"状态约束根本不存在"。
  这与"判据要打在具体那一条上"是同一件事。
- **账本读失败按"没有批准"处理，方向与 `JdbcRunStore` 相反**：那边落不进去只少一行审计
  （对话照常），这边读不出来却要决定"放不放一个还没人批过的动作"。同一个词（降级）
  在两条路上指向两个方向，所以这里的 catch 返回空而不是"算了放过去"。
  顺带得到第二个好处：库没迁（迁移默认关着）时表不存在，标了要审批的动作一律被拦——
  没有审批设施的环境里，收紧的那一侧才是安全的。
- **有效期在 SQL 里比（`now()`），不在 Java 里比**：`expires_at` 是库的时钟，
  拿 JVM 时钟去比会在两者有偏差的部署里让一批批准提前或延后作废，而那种事故没有日志可查。
- **MCP 的 yml 没加 `approval` 键**：ADR-0020 说这张票"调用点一处都不用改"，
  而且"哪个外部动作必须有批"是部署决定，它的落点该是有名单、有卡片的审批策略（P09），
  不是"谁记得在 yml 里补一行"。`McpEndpoints` 只把第三个分量显式写成 `NONE`，
  让"接进来的 MCP 工具默认不需要审批"是一句可读的代码。
- 用例：core `AuthorizationDecisionTest` +2（两个工厂默认不带审批 / 标了要审批也不改鉴权结论）、
  agent `InboundSecurityTest` +2（无批准被拦、话术不是"没权限" / 有批准就放行，
  并钉住账本被问的是"人 + **工具名**"而不是动作名）、app `RunSchemaSqlTest` +2
  （两个约束与变异 / 有效批准的四条口径：是这个人、是这个工具、没过期、是批不是拒）。
  **agent 模块测试文件已满 10 个、`ChatPipelineTest` 已满 20 方法**，所以新用例落在 core 与 app；
  `JdbcApprovalLedger` 的库行为在 app 那份里验（与 `JdbcRunStore` 同一个做法）。
  全量 351 条全过、跳过 0；行覆盖率 core 84.1 / channel 67.9 / agent 64.9 / capability 84.8。
- 同步：`MigrationCompositionTest` 1..10；`README` 的"已达 / 未达"两格
  （P01 的维度与审批表已就位，P02 挂起等批、P03 名单与卡片仍未做）。
- **没做的（各有归属，不是漏项）**：
  - **没有任何工具被标成 REQUIRED**：这是验收第一条要求的（默认放行面不变），
    "哪些动作必须批"是部署与策略的事（P09 的 tools profile）。
  - **没有写审批请求的代码**：P01 只做到"没有批准就被拦"。发起请求、把 run 标 suspended、
    批准后由服务端 resume 是 P02；审批人名单与飞书卡片是 P03。所以这张表现在只被读、不被写
    （用例里直接插行），`expires_at` 也没有默认值——"默认十分钟"是策略，写在 P02 的代码里，
    写在表上会让"改了配置但库里还是十分钟"这种偏差看不见。
  - **账本按"人 + 工具"判，还不看参数**：同参数才复用一次批准是 P02 的核心（参数指纹），
    那一条要带着"指纹退化成只算工具名就必须变红"的变异用例一起落。
  - **"批一次用一次"还没有落点**：`approval_request` 上没有用量标记，那一列归 P02。
