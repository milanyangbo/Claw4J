# M7：run 驱动 + 企业能用（A01–A05 + P01–P07）

Status: ready-for-agent
Date: 2026-10-30
裁决依据: ADR-0016（run/step 边界）、ADR-0017（副作用幂等）、ADR-0018（出站投递）、
ADR-0019（agent 线 A01–A12）、ADR-0020（平台线 P01–P19）、ADR-0021（明确不做）

## Problem Statement

系统里没有任何一个地方能表达"这件事还没做完"：一次 `prompt().call()` 就结束，"继续"是
一段新对话；预算记的是轮不是事；计划只活在上下文里。同时，助手不能替人做主——
没有审批（有副作用的动作只能"永远不给"）、不会自己醒来（定时缺失）、不在企业的聊天软件里
（企微缺失）、出了事查不了（审计缺失）。权限是"全有或全无"，企业里最高频的那句
"这一次能不能破例"没有答案。

## Solution

把"一次事"做成系统里的第一等身份：**Run（一次执行）+ Step**。一次提问或被恢复的执行都属于
同一个 run，中间断开能被 `resume(runId)` 接上；预算按 run 累计；计划写进 step，压缩后仍能读到
进度；结果按投递目标送到人。在此之上加四件企业能力：**批了才执行**（审批指纹 + 飞书卡片）、
**到点干活**（调度表 + `schedule_task` 工具族，跑任务主人的 Principal）、**企微通道**
（复用入站编排）、**审计**（step 的只读投影）。

全部走现有路径：审批 gate 挂在鉴权之后的同一条 advisor 链上，审计挂在现有工具回调上，
不新开"自己跑一次 Agent"的旁路（ADR-0020 的唯一硬约束）。

## User Stories

1. 作为提问人，我要让助手做一件一轮做不完的事，中途断了回来再说一句"继续"，它接着做而不是从头重来。
2. 作为提问人，我想问"这件事做到第几步了"，得到明确进度而不是"我不清楚"。
3. 作为提问人，长对话被压缩之后，助手仍记得我们定下的计划做到第几步、哪些已完成。
4. 作为提问人，助手要做的动作被提交审批时，我想得到一个明确的审批编号与"批准后再问一次即可"的说法。
5. 作为提问人，批准之后同样的问题再问一次就能执行，不用重新解释背景。
6. 作为提问人，结果能送到另一个通道：在飞书问，在企微（或 HTTP 轮询）收同一条 run 的结果。
7. 作为提问人，我的请求被拒时，拒绝的理由会传回给对话，而不是无声失败。
8. 作为审批人，我想在飞书卡片上看到工具名、参数摘要、谁提的，并就地一键批准或拒绝。
9. 作为审批人，我拒绝时写的理由要回给模型，让它不在原地反复请求同一件事。
10. 作为审批人，我点了批准的授权只能用一次，且十分钟后自动过期。
11. 作为审批人，提问人不能批准自己的请求——自行批准等于没有审批。
12. 作为审批人，超时未批的请求自动过期，卡片就地显示"已过期"。
13. 作为任务主人，我说"以后每天早上九点把华东成交额发我"，模型能把它变成一个定时任务。
14. 作为任务主人，建任务时若我现有的权限跑不了这个任务，当场被拒，而不是每天执行时失败。
15. 作为任务主人，我的角色被收回后，任务下一次执行被拒并自动停用，还会通知我。
16. 作为任务主人，我的定时任务默认静默完成，不打扰我，但结果随时能查到。
17. 作为任务主人，任务连续失败三次后自动停用，并收到一条带最后错误的停用通知。

18. 作为企微用户，@ 应用提问后三秒内收到"收到"级别的确认，完整答案随后推回。
19. 作为企微用户，同一事件被重推两次时只被回答一次。
20. 作为未配角色的企微成员，我得到"没有权限"的答复，且这句话不进模型、不花 token。
21. 作为运维，进程重启之后我能答出每一个 run 做到了第几步。
22. 作为运维，预算超限的 run 停下来并写明结局，而不是抛一个要人猜的异常。
23. 作为运维，同一时刻起两个实例，同一条到点的定时任务只执行一次。
24. 作为运维，实例重启不会丢掉已经定好的执行时间点。
25. 作为合规，任一次工具调用都能答出"这次调用是哪次批准的"，批准记录与执行记录一一对应。
26. 作为合规，我能按人、按时间、按结局查审计；一次越权落一行，带工具名与角色。
27. 作为合规，审计只落参数摘要与指纹，不落完整参数——审计表不成为另一张业务数据副本。
28. 作为运维，一次 run 里连续多次工具调用（比如跨三轮调了 7 次）按 run 累计预算，第 7 次被拒。

## Implementation Decisions

- **Run（一次执行）是第一等身份**：入口造 run，一次提问或一次 `resume` 都不新建 run；
  `resume(runId)` 是唯一续跑方法，三个入口（用户再说一句、HTTP 的 resume 入口、
  审批通过后的服务端续跑）都走它。
- **Step 只落在 run 边界上**：工具循环内部的每次尝试**不是** step、不写库（ADR-0016 的硬边界）。
  step 的 kind 至少有：模型轮、工具调用汇总、计划。
- **计划外置**：计划是 step 的一种，带状态（待做 / 已做 / 跳过）与序号；会话压缩后模型从库里读进度，
  而不是从上下文里猜。
- **预算按 run 累计**：工具调用次数、token、墙钟三项；轮预算降级为默认值而不是上限；
  超限即停并写结局。定时任务每次运行单独计。
- **投递目标**：run 绑 Principal（谁的事），不绑"谁问的"；投递是一对多的登记；
  结果靠 `GET /api/runs/{id}` 轮询 + 按通知策略主动推（done_only / silent / state_changes，
  定时任务默认 silent）。
- **审批是权限表上的第三分量**：`Approval{NONE, REQUIRED}`，默认 NONE——审批只给有副作用的动作
  （跑脚本包、发邮件、交脚本草稿），不给"读一下"；"有权限"与"要审批"是两件事，审批不替代鉴权。
- **审批指纹是核心**：`sha256(工具名 + 按 key 递归排序后的规范化参数)`。不排序的话模型换个参数顺序
  就是一次"新"请求，审批被它自己绕过。**它与幂等键形状相似、口径相反**：幂等键含 runId 与 step 序号
  （区分每一次执行），审批指纹不含（跨执行复用一次批准）。混用的事故是双向的。
- **授权（grant）的生命周期**：一次用完即废 + 默认十分钟过期；拒绝也落一行并把理由回灌模型。
- **审批人是独立名单**：与业务角色分开配置；提问人不能批自己的请求；审批入口是 HTTP 接口 +
  飞书交互卡片（走现有长连接，不需要公网回调地址）。
- **定时调度不引新组件**：调度表 + 每 30 秒扫描 + `select … for update skip locked` 保证多实例
  不重复；失败三次自动停用；到点 = 创建一个 run，其余全部复用（不引 Quartz / Redis / 外部调度器，
  依据 ADR-0009 的单实例形态）。
- **`schedule_task` 工具族**（建 / 列 / 取消）：创建时校验"这个任务需要的工具，创建者现在都有"；
  每次执行**重新鉴权**，跑的是任务主人的 Principal 而不是系统账号，也不用角色快照——
  角色被删，下一次执行就拒绝并停用。
- **企微通道**：应用消息为主（能收能发）；收 = URL 验证 + 解密 + 签名校验 + 五秒内回空串；
  复用入站编排的四件事（去重 → 认人 → 异步 → 回推）；认人靠回调里的成员 ID 映射到现有角色。
- **审计是 step 的只读投影**，不新建执行表：补发起人、批准人、决定、参数摘要（前 200 字符）、
  留存策略（90 天）。落点复用现有工具回调与鉴权 advisor 两个接缝，不新造概念。
- **模块方向不变**：channel → core ← agent（ADR-0010）；一切模型调用从同一条 advisor 链进（ADR-0007）。

## Testing Decisions

- **只测外部行为**：HTTP 响应、指标计数、库里的行。不测内部方法，不为测试暴露内部状态。
- **零新增接缝**，四条现有缝打完所有用例：
  1. **HTTP 缝**：`POST /api/chat`（含流式）进；`GET /api/runs/{id}` 与审批接口是功能本体的一部分。
  2. **指标缝**：`claw4j.tool.calls{tool, outcome}` 回读判定工具被调；run 落地后新增的 run 指标同缝回读。
  3. **SQL 缝**：V6–V8 三个迁移用 SQL 用例钉表结构与唯一键（先例：语义缓存那批 SQL 用例，
     连列型与唯一键一起钉，并做变异）。
  4. **真模型缝**（ADR-0011）：闭环用例连真模型跑——"被卡住 → 批准 → 放行"、
     "断点 → resume → seq 连续"、企微收发。mock 只证明装配成立。
- **变异验证是硬要求**：把审批指纹退化成只算工具名，"批准后改参数仍被拦"的用例必须变红；
  把幂等键与审批指纹混用，两个方向的用例都必须变红。
- **无人值守三场景各有一条用例**（会自己醒来的系统，出事时没人在旁边）：审批超时、任务失败、
  通道重推。
- **门禁沿用本地 `./mvnw clean verify`**（checkstyle / spotbugs / 结构规则 / 覆盖率下限），
  不引 CI——这是既定决策，不是遗漏。

## Out of Scope

- M8 / M9 的全部票：A06–A12（评测集、检索分词、长 run 上下文、失败回灌、子 Agent 预算、
  并行执行、配额）与 P08–P19（凭据句柄、审批策略升级、知识库、反向 MCP、钉钉 / Slack、
  OTel、多 agent 配置、插件契约、沙箱加固、doctor、WebSocket）。
- 审批流引擎（多级会签、转交、超时升级）——一个"谁批 + 批没批"的二元状态覆盖九成诉求。
- 任务链 / 依赖编排（A 完成再跑 B）、失败自动重试到成功（无人值守时它是预算杀手，ADR-0021 已否决）。
- 通讯录同步、扫码登录——认人靠回调成员 ID 或网关注入（ADR-0007 的边界）。
- `heartbeat` 常驻自唤醒——等 A04（run 级预算）与 P07（审计）落地后按 ADR-0021 重估。
- CI 与任何自动触发门禁——门禁就是本地 verify。

## Further Notes

- **顺序是挂得上挂不上，不是优先级**：M7a 的五张（A01–A05）必须先于 M7b 的七张（P01–P07）全部完成——
  P04/P05 挂 A02 的 `resume`，P06 挂 A05 的投递目标，P01→P02→P03 是硬链。依赖图见 ADR-0019。
- 实现中发现与六条 ADR（0016–0021）不一致时，先回来改 ADR 再写代码；它们是已接受的裁决，
  不是过时的文档。
- 票的拆分由 `/to-tickets` 完成：一个票一个文件，落在 `issues/NN-*.md`，编号从 01 起，
  与 ADR-0019/0020 的 A/P 编号一一对应，不另起编号。

     P01 的 Comments 里已经声明过这次取舍，这一条只是把它记到需求旁边。
  2. **通知策略的中间态没有生产者**：`done_only` 与 `silent` 可达，`state_changes` 那一档的
     `NotifyPolicy#announcesChange` 至今没有调用方。挂起时推出去的是审批卡片（`ApprovalCards`），
     不是这条通知——两件事在两个地方，别把它们当成一条链路已通。
  3. **过期卡片的"就地显示"没有发生**：过期在判定时生效（`decide` 拒绝过期请求、卡片渲染时
     不带按钮），但没有任何东西回头去改那张已经发出去的卡——`@Scheduled` 里没有这一类任务。
     用户故事 12 只兑现了前半句。
