# A07 · 工具检索要能看懂中文

**Status:** ready-for-agent
**Blocked by:** A06（已落地，`ea5e11b`）。这张票的"有没有变好"要用 A06 的报告去读，不再靠肉眼。

## 为什么

`RegexToolIndex` 把 query 按 `[\s,;:.!?()\[\]{}"']+` 切开。中文整句没有空格，
于是整句变成**一个** token，再当成**一个子串**去匹配工具名与描述——
"回忆以前说过的话"在描述里找不到这么长的一串，命中 0 个工具。

现在系统是怎么绕开它的：`ToolSearch.SYSTEM_SUFFIX` 里明写着

> 检索时用 2~4 个**空格分隔的关键词**描述你需要的能力……不要写成完整的一句话——
> 检索按词匹配，整句会被当成一个词，什么都匹配不到。

**这段话是补丁，而且是把实现缺陷写进给模型的话里。** 它有两个代价：

1. 模型每次检索前都得先做一次本该我们做的分词；
2. 它一旦不照做（中文场景很常见），检索返回空，而提示词里另一句"看不到合适的工具
   **不代表没有这个能力**"又不让它说没有 —— 于是它要么说"我再试试"，要么拿一个
   不合适的工具硬凑。

所以这张票的**第一收益是删掉那段补丁，第二收益才是命中率**。顺序不能反：
只改索引不改提示词，等于留着一段教模型绕一个已经不存在的限制的话，比不改更糟。

## 现状核实（照源码核过，不是照 ADR 抄的）

| 事实 | 在哪儿 |
| --- | --- |
| 切词 | `query.split("[\\s,;:.!?()\\[\\]{}\"']+")`：只认空白与标点，中文整句不切 |
| 长度过滤 | `token.length() >= 2` 丢掉单字；**但全都丢光时会回落到未过滤的原始 token**，所以纯单字 query 仍能命中，混合的（`退 退款`）才会丢掉 `退` |
| 匹配 | `pattern.matcher(description).find()`：每个 token 做**子串**匹配，token 之间是 OR |
| 打分 | 名字命中 ×2 + 描述命中 ×1 + 位置奖励，**按命中次数累加** |
| 结果数 | `maxResults` 默认 5，上限 10（`ToolSearchProperties`） |
| 可覆盖点 | `convertQueryToRegexPattern` 是 `protected`；`doSearch` / `calculateMatchScore` 是 `private` |
| 模式长度 | `MAX_PATTERN_LENGTH = 200`，超了从**尾部**一个一个删 token |
| 停用词 | 英文表（a / an / the / is …），对中文零作用 |
| 空 query | 返回 `.*` → **匹配全部工具**，等于把渐进式披露静默关掉 |

最后一行是顺带发现的洞，与中文无关，但修它的成本只有两行，顺手堵掉（见判据五）。

## 三个候选，选一个

ADR 只给了"二元切分或词典分词二选一"，实际摆着的是三条路：

| 方案 | 改动量 | 新依赖 | 中文 | 结论 |
| --- | --- | --- | --- | --- |
| 继承 `RegexToolIndex`，覆盖 `convertQueryToRegexPattern` 做 CJK 二元组 | ~50 行 | 无 | 有解 | **选它** |
| 自己实现 `ToolIndex`（接口 4 个方法） | ~150 行 | 无 | 有解 | 不选：会话隔离、清理、并发要重写一遍 |
| `LuceneToolIndex` + CJKAnalyzer / SmartChineseAnalyzer | 依赖 + 改不动 | lucene-core 等 | 最好 | 不选，理由见下 |

第三条为什么不选，**不是因为它不好，是因为它现在接不上**：
`LuceneToolIndex` 的构造函数里写死了 `this.analyzer = new StandardAnalyzer()`，
没有留注入 `Analyzer` 的口子；而 `lucene-core` 在 `spring-ai-tool-search-tool` 的 pom 里是
`optional=true`，也就是当前根本没有它。要用就得 fork 一份框架类（升级时跟着改），
或者自己实现 `ToolIndex`（退回第二条）。两个都比第一条贵，而第一条已经够过判据。

**以后什么时候该换**：工具数到几百、需要 TF-IDF 与倒排索引时。那时换的落点只有一个 bean
（`AgentAutoConfiguration#toolIndex()`），下面的判据不用重写。

## 二元组怎么切（技术核心）

"回忆以前说过的话" → `回忆 / 忆以 / 以前 / 前说 / 说过 / 过的 / 的话`。

五条规则，每条都对应一个真实的坑：

1. **只切 CJK 段，ASCII 段照旧**。`回忆 recall 以前` 里的 `recall` 不能被打散成
   `re/ca/ll`——现在的英文行为不能变差，这是判据二。
2. **噪声二元组靠排序吃掉，不做阈值**。`忆以`、`前说`、`过的` 这类跨词切分在别的描述里
   也可能出现，而匹配是 OR + 子串，命中一个就算命中。但分数按**命中次数**累加，
   "噪声命中 1 个"会排在"真命中 4 个"之后，`maxResults` 默认只有 5，基本进不来。
   在 pattern 层做阈值只能靠"少生成"，而少生成要词典——那就是第二条路了。
3. **中文停用字不单独成词，含它就保留**。`的`、`了`、`吗` 不单独生成二元组，但
   `过的` 这种含停用字的照样保留：删了会漏掉"以前"这类真词，而保留的代价被上一条消化。
4. **200 字符截断是可接受的降级**。一句 40 字的话约 39 个二元组、连分隔符约 117 字符，
   够用；再长会从尾部截掉，截掉的是句尾虚词。
5. **单字段要保住框架那个回落**。`退` 切不出二元组；框架原实现的处理是"全被过滤光时
   退回未过滤的 token"，我的覆盖版本必须保留这个语义，否则单字 query 从"能命中"
   退化成"空结果"——那是一次静默的能力回退。

**同义扩展**（ADR 要求的那半句）做成一张 4 组、8 个说法的小表，只在整句里出现左词时追加上右词：

| 说法 | 追加 |
| --- | --- |
| 回忆 / 想不起 / 之前说过 | 历史 会话 |
| 退货 / 退换 | 无理由 售后 |
| 成交额 / 卖了多少钱 | 销售 金额 |
| 审批 / 谁批 | 权限 负责人 |

这张表只解决"同一个意思两种说法"，**不解决"我描述得模糊"**——后者要靠向量检索，
属于 ADR-0021 记的"不做"，重开条件是工具数到几百。

## 落点（四处，一个都不能漏）

1. **新类** `ChineseToolIndex extends RegexToolIndex`，只覆盖 `convertQueryToRegexPattern`，
   外加把空 query 的 `.*` 兜底改成"返回一个什么都不匹配的模式"。
2. **`AgentAutoConfiguration#toolIndex()`** 换实现。它是 `@ConditionalOnMissingBean(ToolIndex.class)`
   且返回接口类型，所以只改这一行，`chatClient()` 那边不用动。
3. **`ToolSearch.SYSTEM_SUFFIX`**：删掉"空格分隔关键词 / 整句会被当成一个词"那两句，
   换成"用一句自然语言说清你要什么能力"。
   **"看不到合适的工具不代表没有这个能力"那句必须留**——那是另一次实测的结论
   （不写它，模型会直接答"我没有工具"然后结束），与分词无关。
4. **四处 `new RegexToolIndex()` 的测试**（两个文件）：`ModelAndToolSelectionTest`（597、635）、
   `SubagentDelegationTest`（330、417）。这些是**整条链**的用例，换索引要一起换，
   否则测的还是旧实现。

`SubagentRunner` / `SubagentAutoConfiguration` 收的是 `ToolIndex` 接口，不用改。

## 怎么测：一条方法、三组输入（因为门禁已经顶格）

`claw4j-agent` 已经是 **10 个测试文件**（上限），`ModelAndToolSelectionTest` 是
**20 个方法**（上限）。所以这张票的用例只能是**置换**，不能是新增：

| 要验什么 | 落在哪儿 |
| --- | --- |
| 中文整句命中该命中的工具 | 原地改写 `chineseQueryNeedsSpaces`——它现在断言的正是这个缺陷 |
| 空格关键词 query 不变差 | 同上，第二段 |
| 20 → 100 个工具时答案不变差 | 同上，第三段 |

一条方法里放三段不是"一条测三件事"：它们**同一个入口**（`ToolIndex#search`）、
**同一种断言形状**（结果里有没有那个工具），差的只是输入规模——与
`retryableClassificationTable` 拿一张表跑多行是同一个写法。

"20 → 100" 这条**只能用生成的假工具来造**：现在注解式工具只有 **3 个**
（`querySales`、`searchDocs`、`systemStatus`），加上 6 处手工构造的 `ToolDefinition`
（`RecallSessionTool`、`ScheduleTools`、`UpdatePlanTool`、`SubagentDelegation`、
脚本包与生成器）与 MCP 转入的，容器里加起来也不到 20 个。
100 个真实工具这个仓库变不出来，而 ADR-0021 的"领先 2（行为不随工具数量变化）"
要的正是这个动作。造法是固定的：一层跟业务无关的假工具（名字与描述取自一张表），
按 20 个一组加到 100 个，同一组 query 每轮都断言"该命中的还在前 5 里"。

## 不做什么

- **不做向量检索 / embedding 索引**。ADR-0021 已裁，重开条件是工具数到几百。
  这一版要的是"中文整句不空手而归"，二元组够。
- **不引任何分词库**（jieba、Ansj、HanLP）。引一个词典就是引一份长期维护成本，
  而它的收益在"专业词切得准"，不在"整句能不能命中"。
- **不改打分公式**。`calculateMatchScore` 是 private，改它等于 fork 框架类；
  排序不动，正是这张票能只改一个方法的原因。
- **不新增配置项**。切分策略不是"部署之间会不同"的东西，做成 `claw4j.tool-search.*`
  只会多一个没人调的开关。要换实现换 bean（已经有这条路）。
- **不给单字 query 加特殊逻辑**。它靠框架那个"全过滤光就退回原始 token"的回落本来就是通的，
  本票只要保证覆盖之后不弄丢它。单字匹配天然过度召回，那是排序与 `maxResults` 的事。

## 代价与已知局限

- **二元组的假阳性是真实的**。`过的`、`以前` 会让不相干的工具进到第 4、5 位。
  排序能压住大部分，但 `maxResults` 调大（比如 10）时会更明显。判据里只断言"该命中的
  在前 5 里"，不断言"其它的不许出现"——后者现在做不到，写进去就是给自己埋假红。
- **同义词表会腐**。那张小表是手写的，工具描述改了它不会跟着改。它的失败方式很安静：
  某个说法不再被扩展，命中率掉一点，没人发现。所以表要短，且每一组都要能指到一条用例。
- **`convertQueryToRegexPattern` 返回的是正则**，不是 token 列表。所有切分逻辑最后都要
  拼回一个合法正则（含 `(?i)` 前缀与分组括号），拼错的表现是 `PatternSyntaxException`
  被吞掉、返回空结果——看起来像"没有匹配"，不像"代码写错了"。测试要能区分这两者。
- **它仍然是词面匹配**。"上次那个客户" 里没有任何一个二元组出现在描述里，还是命中不了。
  这条不靠本票解决，靠 A09 的失败回灌让模型换一种说法。

## 验收判据

- [ ] **中文整句命中该命中的工具**：`search("回忆以前说过的话")` 的结果里第一页有
      `recall_session`。反例：只把切词正则换成正则分组、不做二元组 → 命中仍是 0。
- [ ] **空格关键词不变差**：`search("回忆 历史 会话")` 仍然命中同一个工具。
      反例：为了过第一条把 ASCII 段也打散（`re/ca/ll`）→ 英文 query 全线掉。
- [ ] **20 → 100 个工具时答案不变差**：同一组 8 条 query，工具从 20 加到 100，
      每条断言"该命中的还在前 5 里"。反例：只测 20 个工具的版本 → 这条判据等于没验。
- [ ] **英文 query 不变**：`search("sales revenue last week")` 的结果与改之前一致。
- [ ] **空 query 不返回全部**：`search("")`、`search("   ")` 返回 **0** 个工具。
      反例：保留 `.*` 兜底 → 模型随便发个空查询就把 5 个工具全拿走，渐进式披露静默失效。
- [ ] **提示词里不再要求空格分词**：`ToolSearch.SYSTEM_SUFFIX` 不含"空格"，
      但**仍然**含"不代表没有这个能力"。反例：连后者一起删 → 模型答"我没有工具"（实测过）。
- [ ] **索引 bean 真的换掉了**：`AgentAutoConfiguration` 起的上下文里
      `ToolIndex` 是 `ChineseToolIndex`；`SubagentRunner` 那条链用的也是它。
      反例：只改 bean 没改测试构造 → 测试绿的是旧实现。
- [ ] **切分结果可断言，不是黑盒**：能单测"给定 query 产出哪些 token"。
      反例：只断言"搜出来的工具对" → 换实现时说不清是哪一步变了。
- [ ] **非法正则不会静默变空**：构造一条会拼出非法模式的中文 query，
      断言的是"报错或明确降级"，不是"返回空结果"。反例：吞掉 `PatternSyntaxException`
      当无匹配 → 与"这个词真的没有对应工具"分不开。
- [ ] **评测不倒退**：`./scripts/eval.sh` 的 `tools` 类 8 条在改前改后各跑一次，
      报告里 `tools-*` 的 `answerHit` 不少。反例：只跑单测就交差（A06 之前就是这么自述的）。
- [ ] `./scripts/verify.sh` 全绿，跳过 0，`claw4j-agent` 文件数仍 ≤10、每文件方法数 ≤20、
      行覆盖率不低于 60%，既有用例除被置换那条外一条不改地通过。

## 落地时先确认的三件事

1. **`indexTools` 什么时候被调、会不会重复追加**。`RegexToolIndex` 的 `indexTool` 是
   `SessionIndex.addTool` 直接 `add`，同一会话里调两次就是两份（counter 递增、不去重）。
   如果 advisor 每轮都索引一遍，索引会随请求数增长——那"20 → 100"这条判据的基数是假的，
   而且打分会被重复条目放大。**先跑一次、打印索引大小**，确认了再动手。
   （这条是"读了代码"不是"跑过"，照 A06 的规矩：写在最前面，实现第一件事就是验它。）
2. **`convertQueryToRegexPattern` 的返回值被 `Pattern.compile` 直接编译**，
   不经过任何清洗。我拼出来的串必须自带 `(?i)` 与分组括号，否则大小写与 OR 语义都会变，
   而表现是"分数低了一点"，不会报错。先写一条最简单的断言把形状钉住。
3. **评测里 `tools` 类那 8 条的现状**。`tools-schema-question` 已经是 `expectTools: []`，
   另外 7 条里有 4 条依赖"模型自己去检索"。改索引会同时改提示词，所以改前必须先跑一遍留基线，
   否则改完分不清是索引的功劳还是提示词的。
